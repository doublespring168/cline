# Cline 多模型接入的实现方式

> 本文专门回答：Cline 是使用模型官方 SDK、自己实现一套 SDK，还是直接使用 API + 通信协议接入？
> 结论依据：`src/core/api`、`src/shared/messages`、`src/shared/net.ts`、`package.json` 和各 Provider Handler。

## 1. 一句话结论

**Cline 采用混合方案：自己实现了一层轻量的统一 Agent/Provider Adapter，但没有重新实现一套通用 LLM 网络 SDK。底层有的使用厂商官方 SDK，有的使用 OpenAI SDK 调用 OpenAI-compatible API，有的直接用 `fetch`/Axios 实现 REST/SSE，还有的通过 VS Code API 或本地 CLI 连接。**

更准确地说：

```text
不是：所有 Provider 都使用各自官方 SDK
也不是：Cline 重写了 HTTP、SSE、鉴权、重试的完整通用 SDK

而是：
Cline 自研统一 Adapter/Message/Stream/Tool 层
  + 有选择地复用官方 SDK
  + 复用 OpenAI SDK 作为兼容协议客户端
  + 对私有协议手写 HTTP/SSE 或调用 CLI/IDE API
```

## 2. Cline 自己实现的是什么

### 2.1 `ApiHandler` 是适配器接口，不是网络 SDK

`src/core/api/index.ts` 的 `ApiHandler` 只要求 Provider 实现：

- `createMessage()`：接收系统 Prompt、历史消息和可选工具，返回 `ApiStream`；
- `getModel()`：返回 Model ID 和 `ModelInfo`；
- 可选 `getApiStreamUsage()`；
- 可选 `abort()`。

这层不向上层暴露 SDK Client，也不要求 Provider 使用相同 HTTP Endpoint。

### 2.2 统一输入消息

`src/shared/messages/content.ts` 定义 `ClineStorageMessage`，包含：

- `user` / `assistant` Role；
- Text、Image；
- Thinking / Redacted Thinking；
- Tool Use / Tool Result；
- Tool ID、Call ID、Response ID；
- Reasoning Details、Signature 和加密思考数据。

这是 Cline 自研的“中间表示”，但整体语义和块结构接近 Anthropic Messages。

### 2.3 统一输出流

`src/core/api/transform/stream.ts` 把所有 Provider 输出归一为：

```ts
type ApiStreamChunk =
  | { type: "text"; text: string; ... }
  | { type: "reasoning"; reasoning: string; ... }
  | { type: "tool_calls"; tool_call: ... }
  | { type: "usage"; inputTokens: number; outputTokens: number; ... }
```

Agent 主循环只消费这个格式，不直接依赖 Anthropic/OpenAI/Gemini 的 Stream Event。

### 2.4 自研的格式转换层

`src/core/api/transform` 实现了中间格式到各协议的转换：

| 文件 | 转换目标 |
| --- | --- |
| `anthropic-format.ts` | Anthropic Messages，包括 Cache/Thinking/Tool Block 清理 |
| `openai-format.ts` | OpenAI Chat Completions Messages/Tool Calls |
| `openai-response-format.ts` | OpenAI Responses API Input Items |
| `gemini-format.ts` | Gemini Content/Part/Function Response |
| `mistral-format.ts` | Mistral Chat Messages |
| `ollama-format.ts` | Ollama Messages |
| `vscode-lm-format.ts` | VS Code `LanguageModelChatMessage` |
| `r1-format.ts` | DeepSeek/R1 特殊格式 |
| `o1-format.ts` | o1 类模型特殊输入 |

### 2.5 自研的 Tool Schema 适配

`src/core/prompts/system-prompt/spec.ts` 中同一 `ClineToolSpec` 可转成：

- OpenAI Function Tool；
- Anthropic Tool `input_schema`；
- Gemini Function Declaration。

`ToolCallProcessor` 则合并 OpenAI-compatible 流中被拆分的 Function Name、ID 和 Arguments。

### 2.6 自研的共通模型运行能力

Cline 还在 SDK 之上统一实现：

- `withRetry()` 重试/退避；
- Token、Cache 和 Cost 归一；
- Reasoning Effort/Thinking Budget 转换；
- 原生 Tool Calling 与 XML Tool Calling 两条路线；
- Abort/Cancel；
- Prompt Variant 和 Model Family 匹配；
- Context Window 差异管理；
- 代理、自签证书和多宿主网络适配。

这些组成“Cline 模型适配层”，但不应称为对外的完整 LLM SDK。

### 4.3 复用其他 SDK 调用兼容协议

| Provider | 复用的 SDK | 实际情况 |
| --- | --- | --- |
| `minimax` | Anthropic SDK | MiniMax M2 使用 Anthropic-compatible Messages Endpoint，不是 Anthropic 模型 |
| `aihubmix` | Anthropic + OpenAI + Google GenAI | 按 Model ID 路由到三类协议，还有 OpenAI Responses 分支 |
| `oca` | OpenAI + Anthropic SDK | 按模型 `ApiFormat` 路由 Chat/Responses/Messages，鉴权 Header 由 OCA 实现 |

这三个 Provider 最能说明：“使用了某家 SDK”和“连接了某家模型服务”不是同一件事。SDK 可以只用于语法兼容的 API。

### 4.4 手写 HTTP/REST/SSE 的 Provider

| Provider | 实现 | 为什么不只用通用 SDK |
| --- | --- | --- |
| `asksage` | `fetch` POST `/query`，解析定制 JSON | AskSage 请求/回应不是标准 Chat Completions |
| `dify` | `fetch` 调 `/chat-messages`，手动解析 SSE，实现文件上传、停止和会话 API | Dify App API 有独立 Event/Conversation 语义 |
| `openai-codex` | 先用 OpenAI Responses SDK，失败后手写 SSE，可选 WebSocket | ChatGPT Codex Backend、OAuth Header 和 WebSocket 扩展特殊 |
| `sapaicore` | Orchestration Mode 用 SDK；其他部署用 Axios 手写多种 Payload/Stream | 一个 Provider 包含多类下游协议 |

`openrouter`、`cline`、`litellm` 等也有用 Axios/fetch 补充查询 Model/Usage/Cost 的 Endpoint，但其核心生成流仍主要由 OpenAI SDK 处理。

### 4.5 不是 HTTP SDK 的接入

| Provider | 通道 | 实现 |
| --- | --- | --- |
| `claude-code` | 本地进程 stdin/stdout `stream-json` | `integrations/claude-code/run.ts` 用 `execa` 运行 `claude` |
| `vscode-lm` | VS Code Language Model API | `vscode.lm.selectChatModels()` + `LanguageModelChat.sendRequest()` |

它们不使用 Cline 内的 API Key 去直连公网 Model Endpoint，而是把连接/授权委托给本地 CLI 或 IDE Host。

## 5. 为什么大量 Provider 复用 OpenAI SDK

OpenAI Chat Completions 已成为许多模型平台的兼容协议。在 Cline 中，复用 `openai` SDK 带来：

- 统一的 Request Type；
- SSE Async Iterable；
- `chat.completions.create()` 和 `responses.create()`；
- Chat Tool/Function Type；
- Error 类型和 Abort Signal；
- 只需替换 `baseURL`、`apiKey`、Header 就能连接兼容平台。

但兼容并不意味完全一致，所以每个 Handler 仍可能要区别处理：

- `reasoning_content`、`reasoning`、`reasoning_details`；
- `<think>` 标签；
- `max_tokens` 与 `max_completion_tokens`；
- Prompt Cache 命中/写入字段；
- Tool Call 是否支持；
- Usage 是否在流尾返回；
- 价格、成本和生成 ID；
- 消息 Role 和图像格式。

## 6. `createOpenAIClient` 是什么，不是什么

`src/shared/net.ts` 的 `createOpenAIClient()` 只是对官方 OpenAI Client 的小型工厂包装：

- 注入 Cline 外部基础 Header；
- 注入项目统一 `fetch`；
- 让 VS Code/独立 Host 获得正确代理支持。

它没有重新实现 Chat Completions 协议，返回的仍是 `new OpenAI(...)`。

`src/shared/net.ts` 另外提供：

- VS Code 下使用 Host 已配置的 Global Fetch；
- Standalone/JetBrains/CLI 下用 Undici `EnvHttpProxyAgent`；
- `getAxiosSettings()` 强制 Axios 使用同一 Fetch Adapter；
- `NODE_EXTRA_CA_CERTS` 与企业代理证书路径配合。

这个网络层是 Cline 自研的“宿主网络适配”，不是 LLM 协议 SDK。

## 7. Native Tool Calling 和 XML Tool Calling 的实现差异

### 7.1 原生路线

```text
ClineToolSpec
  → OpenAI/Anthropic/Gemini Tool Schema
  → Handler.createMessage(..., tools)
  → Provider 原生 Function/Tool Call
  → Provider Handler 转成 ApiStreamToolCallsChunk
  → ToolExecutor
```

要成为完整 Native Tool Provider，Handler 必须同时：

1. 接收 `tools` 参数；
2. 转成 Provider 需要的 Schema；
3. 把 Schema 放入实际 API Request；
4. 把流中 Tool Call 名、ID、Arguments 还原；
5. 在下轮请求中正确回传 Tool Result。

### 7.2 XML 路线

```text
System Prompt 说明 <read_file>...</read_file>
  → 模型输出普通文本
  → parseAssistantMessageV2()
  → ToolUse
  → ToolExecutor
```

这条路线不要求 Provider API 原生支持 Functions，是 Cline 能适配大量模型的关键。代价是：

- 模型必须稳定遵循 XML；
- 参数类型实际上主要是文本；
- 流式部分 XML 需要增量解析；
- 并行 Tool Calling 与原生 Call ID 语义更弱。

### 7.3 不能用签名推断实际能力

某个 Handler 的 `createMessage` 在 TypeScript 中即使少声明了参数，也因方法参数协变/结构类型而可以满足 `ApiHandler`。因此判断原生工具必须检查实际 Request Body。

例如：

- `AnthropicHandler`、`GeminiHandler`、`OpenAiNativeHandler`、`BedrockHandler` 真正透传工具并解析 Call；
- `AIhubmixHandler.createMessage(systemPrompt, messages)` 当前未接收主调用传入的 `tools`，它的多 SDK 路由不等于完整 Native Tool Adapter；
- `AskSageHandler`、`DifyHandler`、`HicapHandler` 当前主要依赖 XML Prompt 能力。

## 8. Reasoning/思考适配不是 SDK 自动完成的

Cline 自己统一了多种推理输出：

| 来源 | Handler 需要识别的数据 |
| --- | --- |
| Anthropic | `thinking_delta`、`signature_delta`、`redacted_thinking` |
| OpenAI Chat 兼容平台 | `reasoning_content`、`reasoning`、`reasoning_details` |
| OpenAI Responses | Reasoning Item、Summary Delta、Encrypted Content |
| Gemini | `part.thought`、`thoughtSignature`、Thought Token Count |
| 开源 R1 风格 | `<think>` 文本标签 |

同样，Thinking Budget/Reasoning Effort 也需要按协议转换：Anthropic Budget/Adaptive Thinking、OpenAI `reasoning_effort`、Gemini Thinking Budget/Level 的字段和约束并不相同。

## 9. 新增一个模型 Provider 的完整路线

### 9.1 第一步：确定协议家族

先回答：

- 是 Anthropic Messages-compatible？
- 是 OpenAI Chat Completions-compatible？
- 是 OpenAI Responses-compatible？
- 是 Gemini GenerateContent-compatible？
- 有官方 SDK，且 SDK 对 Proxy/Streaming/Abort 的支持比直接 HTTP 更合适？
- 是否有私有 SSE Event、自定义鉴权或 Conversation ID？

如果完全 OpenAI-compatible，通常复用 `createOpenAIClient()` + `convertToOpenAiMessages()` + `ToolCallProcessor` 成本最低。

### 9.2 第二步：建立 Provider 类型和配置

1. 在 `src/shared/api.ts` 的 `ApiProvider` 增加 ID。
2. 在 `src/shared/storage/state-keys.ts` 增加 Base URL、Model ID、Feature 等 Settings Field。
3. API Key/Client Secret 必须加入 `SECRETS_KEYS`，不能当普通 Global State 保存。
4. 在 `src/shared/storage/provider-keys.ts` 补 Provider → Key、Model ID Key、Default Model 映射。
5. 若要通过 ProtoBus 往返，在 `proto/cline/models.proto` 增加 `ApiProvider` 枚举和配置字段，然后重新生成 Proto。
6. 更新 `src/shared/proto-conversions/models/api-configuration-conversion.ts`。

### 9.3 第三步：实现 Handler

在 `src/core/api/providers/<provider>.ts` 实现：

- 懒初始化 Client；
- 缺失凭证和 Model ID 的清晰错误；
- `createMessage()` 请求格式；
- Stream Event → `ApiStreamChunk`；
- Tool Calls；
- Reasoning；
- Usage/Cache/Cost；
- `getModel()`；
- 可选 `abort()`；
- `@withRetry()` 策略。

对于使用 Fetch/Axios 或允许注入 Fetch 的 SDK，应使用 `@/shared/net` 的 `fetch`、`createOpenAIClient` 或 `getAxiosSettings()`，否则 Standalone/JetBrains/CLI 代理可能失效。但 Bedrock AWS SDK 使用自己的 Runtime Client，源码还留有“AWS SDK proxy support”的 TODO，不应强行套用 `shared/net` 的 Fetch。

### 9.4 第四步：注册工厂

在 `src/core/api/index.ts`：

1. Import Handler；
2. 在 `createHandlerForProvider()` 新增 `case`；
3. 正确从 Plan/Act 分别取 Model ID、Reasoning Effort 和 Thinking Budget；
4. 传入 `onRetryAttempt`、`ulid` 等共通上下文。

### 9.5 第五步：模型目录和 UI

- 静态模型：在 `src/shared/api.ts` 建 `models/defaultModelId/ModelId` 常量；
- 动态模型：在 `src/core/controller/models` 实现 Refresh RPC 和 Cache；
- 在 `src/shared/providers/providers.json` 增加下拉项；
- 在 `webview-ui/src/components/settings/providers` 新增 Provider 配置组件；
- 在 `ApiOptions.tsx` 导入并按 Provider 渲染；
- 更新 `providerUtils.ts` 的默认值、Plan/Act 字段复制和归一逻辑。

### 9.6 第六步：Prompt 和 Tool Calling

- 给模型 ID 匹配正确 Prompt `ModelFamily`；
- 确认是否可使用 Native Tool Variant；
- 如支持原生 Tool，在 `ClineToolSet.getNativeConverter()` 中选对 Schema；
- 如不支持，验证 XML Tool Prompt 的遵循能力；
- 验证 Tool Use/Result 回传后下一轮的协议顺序。

### 9.7 第七步：测试矩阵

至少测试：

- 无 Key/错 Key/401/403/429/5xx；
- 首 Token、中途断流、Abort、Retry；
- Text + Reasoning + Usage；
- 单 Tool、多 Tool、分片 Arguments、Tool Result；
- Image Support；
- Plan/Act 不同 Model；
- Context Window/Max Tokens；
- Proxy 和自签证书；
- Settings 重载后 Key 不泄漏；
- 动态 Model 目录失败时的缓存/默认降级。

## 10. 如果只想增加“一个新模型”而非新 Provider

不要默认新建 Handler。先判断：

### 10.1 现有 Provider 已能接收任意 Model ID

如 OpenAI-compatible、OpenRouter、LiteLLM、Ollama、LM Studio，通常只需：

- 在 UI 选择/输入 Model ID；
- 补充准确 `ModelInfo`；
- 如 Prompt 行为特殊，增加/调整 Prompt Variant Matcher；
- 如 Tool/Reasoning 字段特殊，在现有 Handler 加小范围分支。

### 10.2 只是新增静态目录条目

在 `src/shared/api.ts` 添加：

- Model ID；
- `contextWindow`；
- `maxTokens`；
- `supportsImages`；
- `supportsPromptCache`；
- `supportsReasoning` / Thinking Config；
- 价格；
- 必要时 `apiFormat`、`supportsTools`、`supportsStreaming`。

一个错误的 `ModelInfo` 可能比没有条目更危险：它会导致 Context 超限、错误开启图像/原生工具、使用错 API 格式或计费不准。

## 11. 当前实现中值得注意的不一致

### 11.1 SDK 存在不代表 Provider 正在使用

`@google-cloud/vertexai` 就是直接例子：依赖存在，当前 Provider 主路未 Import。二次开发时应以 Handler Import 和实际 Client Call 为准。

### 11.2 OpenAI SDK 存在不代表连接 OpenAI

DeepSeek、Qwen、xAI、Groq、Fireworks、W&B 等都使用 `openai` npm 包，但 Base URL、Key、模型和账单都属于各自平台。

### 11.3 Handler 存在 `tools` Type 不代表完整工具支持

要追到实际 Request Body 和 Stream Parser。只有 Schema 发出去并能解析 Tool Call/Result，才是真正 Native Tool Calling。

### 11.4 手写 HTTP 不一定比 SDK 低级

Dify 有自己的 Conversation ID、File Upload、Stop Task 和 Event Type，用官方 OpenAI SDK 反而无法表达这些语义。OpenAI Codex 也需要为特定后端和 WebSocket 增加手写兜底。

## 13. 最终回答

| 问题 | 准确答案 |
| --- | --- |
| 是否直接用官方 SDK？ | **部分是。** Anthropic、OpenAI、Gemini、Vertex Claude、Bedrock、Mistral、Cerebras、Ollama、SAP Orchestration 等使用对应 SDK。 |
| 是否自己实现了一套 SDK？ | **没有重写完整底层 SDK，但自己实现了统一 Adapter、Message、Stream、Tool、Retry、Cost 和 Prompt 层。** |
| 是否通过 API + 通信协议接入？ | **大量是。** 特别是使用 OpenAI SDK 调用兼容 API 的二十多个 Provider，以及 AskSage、Dify、Codex、SAP 的手写 HTTP/SSE 分支。 |
| 是否还有其他方式？ | **有。** `claude-code` 通过本地 CLI，`vscode-lm` 通过 VS Code Language Model API。 |

因此，从架构角度最恰当的命名是：

> **多协议、多客户端的 Provider Adapter 架构，以 Cline 自研中间消息/流/工具协议统一上层 Agent。**
