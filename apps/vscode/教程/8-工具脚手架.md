# Cline 提供给大模型的工具与扩展脚手架

> 分析范围：`apps/vscode` 当前源码，重点是“大模型在 Agent 循环中实际能看到、选择和调用什么”。
> 核心证据：`src/shared/tools.ts`、`src/core/prompts/system-prompt`、`src/core/task/ToolExecutor.ts`、`src/core/task/tools`、`src/services/mcp`。

## 1. 先给出结论

Cline 不是只给模型几个函数，而是提供了一套分层的 Agent 能力脚手架：

```text
模型可见能力
  ├─ Cline 内置工具
  ├─ MCP 动态工具、资源和 Prompt
  ├─ Skills 按需加载的专项指令
  └─ Subagents 并行子智能体/可配置子智能体

模型行为脚手架
  ├─ Rules / AGENTS.md / Cursor / Windsurf 规则注入
  ├─ Workflows / Slash Commands / MCP Prompts
  ├─ Plan / Act、Focus Chain、审批和权限
  └─ Hooks 在任务和工具生命周期旁路执行

宿主实行层
  ├─ ToolExecutorCoordinator 路由
  ├─ Tool Handler 实现
  ├─ Auto Approve / 人工审批 / Hooks
  └─ VS Code、文件系统、终端、浏览器、MCP 等真实能力
```

需要特别注意：

- `ClineDefaultTool` 枚举中有名字，不等于该工具每一轮都会暴露给模型。
- 工具是否可见受 Prompt Variant、Plan/Act 模式、模型原生 Tool Calling 能力、用户本地设置和运行时上下文共同决定；远程 Feature Flag 已删除。
- `focus_chain` 当前是参数依赖占位符，不是一个独立可执行 Handler。
- `condense`、`summarize_task`、`report_bug`、`new_rule` 有解析和执行能力，但只在特定命令或上下文管理场景中把定义临时告诉模型，不在常规 Tool Registry 的 23 个 Prompt Spec 中。
- Rules、Workflows 和 Hooks 不是普通“模型函数工具”；它们分别是 Prompt 指令、用户触发的 Prompt 宏和宿主侧生命周期脚本。

## 2. 一次工具调用的完整脚手架

### 2.1 工具身份层

`src/shared/tools.ts` 的 `ClineDefaultTool` 是内置工具 ID 的权威集合，`toolUseNames` 则给 XML 解析器和 Handler 注册器使用。

这一层解决：

- 模型输出的工具名如何被稳定识别；
- 不同 Prompt Variant 如何引用同一个逻辑工具；
- Handler、审批设置和本地消息如何共享同一 ID。

`setDynamicToolUseNames()` 还允许 Subagent 配置动态扩展 XML 可识别工具名。

### 2.2 Tool Spec 层

`src/core/prompts/system-prompt/spec.ts` 定义 `ClineToolSpec`：

- `id`：内部稳定 ID；
- `name`：真正告诉模型的名称；
- `description`：使用语义；
- `parameters`：参数、是否必填、类型和 JSON Schema 补充字段；
- `contextRequirements`：运行时可见性条件；
- `variant`：适用的模型 Prompt Family。

同一份 Spec 可被转成三类原生函数协议：

| 转换函数 | 目标格式 | 主要 Provider |
| --- | --- | --- |
| `toolSpecFunctionDefinition` | OpenAI `type:function` + JSON Schema | OpenAI 及大部分 OpenAI-compatible Provider |
| `toolSpecInputSchema` | Anthropic `name/input_schema` | Anthropic、Bedrock、MiniMax、Vertex Claude |
| `toolSpecFunctionDeclarations` | Gemini `FunctionDeclaration` | Gemini、Vertex Gemini |

### 2.3 Registry 与 Prompt Variant 层

`src/core/prompts/system-prompt/tools/init.ts` 把 23 类 Tool Spec 注册到 `ClineToolSet`；其中 `focus_chain` 是仅供参数依赖的占位符，所以真正可执行的常规工具数量少一个，另有动态 Subagent 工具。

`src/core/prompts/system-prompt/registry/ClineToolSet.ts` 负责：

- 按 `ModelFamily` 保存工具变体；
- 按 Prompt Variant 声明的 `tools` 列表选择工具；
- 按 `contextRequirements` 剪枝；
- 为配置型 Subagent 生成动态 Tool Spec；
- 为每个已连接 MCP Server 生成原生 Tool Spec；
- 选择 OpenAI / Anthropic / Gemini 格式转换器。

Prompt Variant 位于 `src/core/prompts/system-prompt/variants/*/config.ts`。例如：

- Generic/Next-gen 主要使用系统 Prompt 中的 XML 工具说明；
- `native-gpt-5`、`native-gpt-5-1`、`native-next-gen`、`gemini-3`、`xs` 声明 `use_native_tools: 1`；
- 只有 Variant 声明原生工具、全局开关也允许时，`getNativeTools()` 才返回函数 Schema。

### 2.4 模型输出解析层

项目同时支持两条路线：

1. XML 工具：`parseAssistantMessageV2()` 从模型文本中解析 `<read_file>...</read_file>` 等块，源码在 `src/core/assistant-message/parse-assistant-message.ts`。
2. 原生工具：各 Provider Handler 把 OpenAI `tool_calls`、Anthropic `tool_use`、Gemini `functionCall`、Responses API `function_call` 归一为 `ApiStreamToolCallsChunk`。

`src/core/task/StreamResponseHandler.ts` 和 `src/core/task/index.ts` 把流式参数片段累积为 `ToolUse`，之后交给 `ToolExecutor`。

### 2.5 Handler 执行层

`src/core/task/ToolExecutor.ts` 是统一执行入口，`ToolExecutorCoordinator.ts` 是 Registry/Router，`src/core/task/tools/handlers` 是真实实现。

典型路径是：

```text
ToolUse
  → 是否已注册
  → Plan 模式写操作限制
  → 参数/路径/.clineignore 校验
  → Auto Approve 或等待用户审批
  → PreToolUse Hook
  → Handler.execute()
  → PostToolUse Hook
  → checkpoint / UI 消息 / 本地日志
  → tool_result 追加到下一轮模型上下文
```

## 3. 常规可暴露给模型的内置工具

下表包含 22 个可执行的常规工具类型和 1 个动态 Subagent 工具家族。“可调用”仍然表示满足当前 Variant 和运行时条件时可调用，不表示所有模型每轮均可见。

| 工具 | 主要功能 | 执行实现 | 可见性/风险要点 |
| --- | --- | --- | --- |
| `ask_followup_question` | 向用户追问并等待回答 | `AskFollowupQuestionToolHandler.ts` | 交互工具，不修改工作区 |
| `attempt_completion` | 宣布任务完成，可附带结果/演示命令 | `AttemptCompletionHandler.ts` | Agent 循环终止语义；可配置完成二次检查 |
| `execute_command` | 在 VS Code Terminal 或后台进程运行 Shell 命令 | `ExecuteCommandToolHandler.ts`、`integrations/terminal` | 高风险；经命令权限、审批和 Hook |
| `read_file` | 读取文件、指定行段或多文件内容 | `ReadFileToolHandler.ts` | 受路径和 `.clineignore` 校验 |
| `write_to_file` | 创建/整体写入文件，通过 Diff 界面展示 | `WriteToFileToolHandler.ts` | Plan 严格模式受限，需审批或 Auto Approve |
| `replace_in_file` | 按 SEARCH/REPLACE 局部修改文件 | 共用 `WriteToFileToolHandler.ts` | Plan 严格模式受限；校验匹配和 Diff |
| `apply_patch` | 以 OpenAI/Codex 风格 Patch 一次修改多处内容 | `ApplyPatchHandler.ts`、`PatchParser.ts` | 主要给 native GPT 系列 Variant；取代其 `write/replace` |
| `search_files` | 正则搜索工作区文件内容 | `SearchFilesToolHandler.ts`、Ripgrep Service | 读取型，结果会截断 |
| `list_files` | 列出目录，可递归 | `ListFilesToolHandler.ts`、Glob Service | 读取型，有数量上限 |
| `list_code_definition_names` | 列出源码定义/符号概要 | `ListCodeDefinitionNamesToolHandler.ts`、Tree-sitter | 用于先建立结构视图 |
| `browser_action` | 启动、点击、输入、滚动、截图、关闭受控 Chromium | `BrowserToolHandler.ts`、`services/browser` | 要求模型支持图像且用户未禁用浏览器工具 |
| `web_fetch` | 抓取 URL 并提取可供模型阅读的内容 | `WebFetchToolHandler.ts`、`UrlContentFetcher` | 受本地 Web Tools 设置限制 |
| `web_search` | 执行网络搜索并返回结果 | `WebSearchToolHandler.ts` | 受 Web Tools 开关和 Provider 支持限制 |
| `use_mcp_tool` | 调用指定 MCP Server 的指定 Tool | `UseMcpToolHandler.ts`、`McpHub.callTool()` | XML 路径使用 `server_name/tool_name/arguments`；通常需审批 |
| `access_mcp_resource` | 读取 MCP Resource URI | `AccessMcpResourceHandler.ts`、`McpHub.readResource()` | 资源读取也进入审批流 |
| `load_mcp_documentation` | 加载 MCP 开发/配置文档，帮助模型创建 Server | `LoadMcpDocumentationHandler.ts` | 只在 MCP 相关上下文有意义 |
| `new_task` | 用总结和新任务创建独立会话 | `NewTaskHandler.ts` | 并非所有 Variant 均包含 |
| `plan_mode_respond` | Plan 模式向用户返回计划/请求切换 | `PlanModeRespondHandler.ts` | 与 Plan/Act 状态机绑定 |
| `act_mode_respond` | 从特定计划流切换或回应 Act 模式 | `ActModeRespondHandler.ts` | 只在部分 native Variant 声明 |
| `generate_explanation` | 根据 Git Ref 生成多文件 Diff 解释和行级评论 | `GenerateExplanationToolHandler.ts` | 主要由 `/explain-changes` 引导调用 |
| `use_skill` | 按名字懒加载 `SKILL.md` 的完整指令 | `UseSkillToolHandler.ts` | 只有可用 Skill 时出现；子智能体 UI 输出有专门处理 |
| `use_subagents` | 最多并行启动 5 个进程内研究子智能体 | `SubagentToolHandler.ts`、`SubagentRunner.ts` | 需 `subagentsEnabled`；子智能体内禁止再次嵌套 |
| `use_subagent_<name>` | 调用 `~/Documents/Cline/Agents/*.yaml` 配置的特定子智能体 | 动态路由到 `SubagentToolHandler.ts` | 名字由 `SubagentToolName.ts` 生成，可限定模型、工具、Skill 和 System Prompt |

### 3.1 `focus_chain` 为什么不应列为独立工具

`focus_chain.ts` 的 Spec 没有参数和描述，源码也明确标注“Placeholder to act as tool dependency”。

`ToolExecutorCoordinator` 对 `ClineDefaultTool.TODO` 返回 `undefined`，没有 Handler；`PromptBuilder` 会跳过无参数且无描述的 Spec，原生 Tool 也因描述为空而被过滤。

它实际作用是：

- 开启 Focus Chain 时，给其他工具动态加入 `task_progress` 检查清单参数；
- ToolExecutor 在工具完成后调用 `updateFCListFromToolResponse()`；
- 状态写到任务目录的 Focus Chain 文件。

因此它是“进度参数脚手架”，不是模型应单独调用的函数。

## 4. 仅在特定指令中可调用的内部工具

| 工具 | 何时把定义告诉模型 | Handler | 判定 |
| --- | --- | --- | --- |
| `condense` | 用户输入 `/compact` 或 `/smol`，`commands.ts` 注入专用 XML 定义 | `CondenseHandler.ts` | 真正可调用，但非常规 Spec |
| `summarize_task` | 旧上下文管理触发临界时，`contextManagement.ts` 强制模型总结 | `SummarizeTaskHandler.ts` | 内部上下文交接工具 |
| `report_bug` | `/reportbug` 注入参数和收集问题的流程 | `ReportBugHandler.ts` | 特定 Slash Command 工具 |
| `new_rule` | `/newrule` 要求模型写入 `.clinerules/*.md` | 共用 `WriteToFileToolHandler.ts` | 特定 Slash Command 工具；`commands.ts` 声称 Plan/Act 均可用，但当前开启 Strict Plan Mode 时 `ToolExecutor` 会把它作为写工具阻断，存在实现/提示不一致 |

这些名字仍在 `ClineDefaultTool`、`getToolUseNames()` 和 Handler Registry 中，所以 XML 解析与执行链路完整；差异是常规 System Prompt 不宣传它们。

## 5. MCP 脚手架

### 5.1 MCP 为模型扩展了什么

MCP Server 可提供：

- Tools：可执行函数；
- Resources：按 URI 读取的文本、图像、音频或 Blob；
- Resource Templates：带参 URI 模板；
- Prompts：可以通过 `/mcp:<server>:<prompt>` 注入消息的 Prompt 模板；
- Notifications：Server 主动通知，转成聊天消息。

实现在 `src/services/mcp/McpHub.ts`，使用 `@modelcontextprotocol/sdk`。

### 5.2 三种连接方式

| 配置 `type` | SDK Transport | 用途 |
| --- | --- | --- |
| `stdio` | `StdioClientTransport` | 启动本地 MCP 子进程，通过 stdin/stdout 通信 |
| `sse` | `SSEClientTransport` | 兼容旧版远程 SSE MCP Server |
| `streamableHttp` | `StreamableHTTPClientTransport` | 新版远程 HTTP 传输，带重连管理 |

远程 SSE/HTTP 支持 MCP OAuth，`McpOAuthManager.ts` 保存动态注册信息和 Token；配置也支持 `${env:NAME}` 环境变量展开。

### 5.3 XML 模式与原生函数模式

XML 模式下，模型看到聚合工具：

```xml
<use_mcp_tool>
  <server_name>server</server_name>
  <tool_name>tool</tool_name>
  <arguments>{"key":"value"}</arguments>
</use_mcp_tool>
```

原生 Tool Calling 模式下，`mcpToolToClineToolSpec()` 把每个 Server Tool 直接注册为独立函数：

```text
<server-short-uid>0mcp0<original-tool-name>
```

`StreamResponseHandler` 再把动态名字还原成 `server_name/tool_name`，最后仍由 `UseMcpToolHandler` 执行。工具名超过 64 个字符时不注册，以避免 Provider API 拒绝 Schema。

### 5.4 安全边界

- 禁用的 Server 不会暴露给模型；
- Tool 可有 MCP 级别的 `autoApprove`，仍受 Cline 审批流统一管理；
- `PreToolUse` / `PostToolUse` Hook 同样覆盖 MCP Tool；
- 返回文本超过上限会截断，图像只在当前模型支持时送回模型；
- 本地 MCP 配置、审批和 `.clineignore`/Hook 安全策略仍然生效；不再接收企业 Remote Config 限制。

## 6. Skills 脚手架

### 6.1 Skill 不是代码插件

Skill 是“可发现、可匹配、按需加载的 Prompt 包”。每个 Skill 目录至少包含：

```text
<skill-name>/
  SKILL.md
```

`SKILL.md` 必须带 YAML Frontmatter 的 `name` 和 `description`，且 `name` 必须与目录名相同。

### 6.2 扫描位置

`getSkillsDirectoriesForScan()` 当前扫描：

| 范围 | 路径 |
| --- | --- |
| 项目 | `.clinerules/skills/*/SKILL.md` |
| 项目 | `.cline/skills/*/SKILL.md` |
| 项目 | `.claude/skills/*/SKILL.md` |
| 项目 | `.agents/skills/*/SKILL.md` |
| 全局 | `~/.cline/skills/*/SKILL.md` |
| 全局 | `~/.agents/skills/*/SKILL.md` |

同名冲突由本地磁盘扫描顺序处理；当前没有远程 Skill 来源。

### 6.3 模型真正如何使用 Skill

1. System Prompt 的 `SKILLS` 段只注入已启用 Skill 的名字和描述，不立即注入全文。
2. 模型判断任务匹配时调用 `use_skill(skill_name)`。
3. `UseSkillToolHandler` 实时重新发现 Skill，读取 Frontmatter 之后的指令正文。
4. Skill 指令作为 Tool Result 返回给模型，模型继续当前任务。

这是懒加载设计，可避免大量 Skill 全文每轮占用 Context。

## 7. Subagents 脚手架

### 7.1 通用并行子智能体

`use_subagents` 接收 `prompt_1` 到 `prompt_5`，`UseSubagentsToolHandler` 为每个 Prompt 创建 `SubagentRunner`，通过 `Promise.allSettled()` 并行执行。

默认子智能体能力由 `SubagentBuilder.ts` 限制为：

- `read_file`；
- `list_files`；
- `search_files`；
- `list_code_definition_names`；
- `execute_command`，但 System Prompt 要求只做只读操作；
- `use_skill`；
- `attempt_completion`。

子智能体有独立模型请求和工具循环，但复用主任务的工作目录和基础服务；结果、Tool Call 数、Token、成本和 Context 使用量汇总回主智能体。

### 7.2 可配置子智能体

`AgentConfigLoader.ts` 监听：

```text
~/Documents/Cline/Agents/*.yaml
```

配置可包含：

- `name`、`description`；
- `modelId`：覆盖当前 Provider 的模型 ID；
- `tools`：限制子智能体可使用的 `ClineDefaultTool`；
- `skills`：预配置可加载 Skill；
- Markdown 正文：自定义 System Prompt。

每个配置会生成独立的 `use_subagent_<sanitized-name>` 工具，这才是动态配置真正进入模型调用面的位置。

## 8. Hooks 脚手架

### 8.1 Hooks 不是模型直接选择的 Tool

Hooks 是宿主侧脚本拦截器。模型不会输出“调用 Hook”，而是任务状态或 ToolExecutor 在固定生命周期自动调用。

当前 `HookFactory.Hooks` 支持 9 类：

| Hook | 触发点 | 是否可影响模型流程 |
| --- | --- | --- |
| `TaskStart` | 新任务开始 | 可取消，可添加 `contextModification` |
| `TaskResume` | 恢复历史任务 | 可取消，可补充 Context |
| `TaskCancel` | 用户取消任务 | 主要做清理/通知 |
| `TaskComplete` | 任务成功完成 | 主要做验证、报告或外部触发 |
| `PreToolUse` | 已审批、真正执行工具前 | 可阻断危险工具，可补充 Context |
| `PostToolUse` | 工具成功或失败后 | 可追加处理信息或请求取消 |
| `UserPromptSubmit` | 用户 Prompt 送入 Agent 前 | 可取消或修改上下文 |
| `Notification` | 需要通知时 | 用于外部通知副作用 |
| `PreCompact` | 会话压缩前 | 可在压缩前留存/补充信息 |

### 8.2 目录和协议

Hook 从工作区 `.clinerules/hooks` 和全局 `Documents/Cline/Hooks` 发现。Unix 为可执行脚本，Windows 支持 PowerShell；具体文件名规则在 `src/core/hooks/utils.ts`。

脚本通过 stdin 接收 JSON，stdout 返回：

```json
{
  "cancel": false,
  "contextModification": "optional context",
  "errorMessage": ""
}
```

`HookProcess` 提供 30 秒超时、AbortSignal、stdout/stderr 流式 UI；`contextModification` 上限约 50 KB。模板由 `src/core/hooks/templates.ts` 生成。

## 9. Rules 和外部指令脚手架

Rules 会进入 System Prompt，因此能约束模型，但它们不是可调用函数。

| 类型 | 位置 | 加载方式 |
| --- | --- | --- |
| Cline 项目规则 | `.clinerules` 文件或目录 | 排除 `workflows/hooks/skills`，其余规则合并注入 |
| Cline 全局规则 | `Documents/Cline/Rules` | 对所有工作区注入 |
| Cursor | `.cursorrules`、`.cursor/rules/*.mdc` | 格式化后注入 |
| Windsurf | `.windsurfrules` | 格式化后注入 |
| Agents | 递归 `AGENTS.md` | 顶层存在时才递归搜索，合并并标注相对路径 |

Rule 可带 YAML Frontmatter 条件，`rule-conditionals.ts` 会根据请求文本、模式、文件/路径等证据决定是否激活。各类规则有 Toggle State，不是扫描到就必然启用。

## 10. Workflows、Slash Commands 和 MCP Prompts

### 10.1 Workflows

Workflow 是由用户输入 `/name` 触发的 Prompt 宏，不是模型主动函数。

位置：

- 项目 `.clinerules/workflows`；
- 全局 `Documents/Cline/Workflows`。

`parseSlashCommands()` 读取内容并包装为：

```xml
<explicit_instructions type="workflow-name">
...
</explicit_instructions>
```

同名时项目 Workflow 优先于全局 Workflow。

### 10.2 内置 Slash Commands

`src/core/slash-commands/index.ts` 当前处理：

- `/newtask`；
- `/smol` / `/compact`；
- `/newrule`；
- `/reportbug`；
- `/deep-planning`；
- `/explain-changes`。

它们的本质是为当前用户消息注入严格指令，部分指令会临时开启第 4 节的内部工具。

### 10.3 MCP Prompt

`/mcp:<server>:<prompt>` 由 `McpHub.getPrompt()` 取得 MCP Prompt，再作为 `<mcp_prompt>` 指令注入用户消息。它是“用户选 Prompt”，不是“模型调 Prompt Tool”。

## 11. 哪些不应误认为模型工具

| 能力 | 不是模型 Tool 的原因 |
| --- | --- |
| VS Code Commands | 由用户点击、快捷键或 Extension Host 调用，不经 Tool Spec |
| Checkpoints | 任务和写工具周边自动建立，模型无直接 checkpoint 函数 |
| Diff View | 写入 Handler 的人机审核 UI，不是单独 Tool |
| Auto Approve | ToolExecutor 的策略层，不由模型决定 |
| `.clineignore` | ToolValidator/ClineIgnoreController 的宿主权限边界 |
| Rules | System Prompt 指令注入 |
| Workflows | 用户 Slash Command 宏 |
| Hooks | 宿主生命周期脚本 |
| MCP Marketplace | 用户安装/配置 Server 的 UI 和目录，安装后 Server Tool 才进入模型调用面 |

## 12. 工具可见性的决策条件

某个工具最终能否给模型使用，至少要检查：

1. 工具是否在当前 Prompt Variant 的 `tools` 列表中；
2. Tool Spec 的 `contextRequirements` 是否满足；
3. 当前是 XML 路线还是 Native Tool Calling 路线；
4. Native 路线的 Variant 是否标记 `use_native_tools: 1`；
5. 用户是否开启 `nativeToolCallEnabled`；
6. 模型是否支持图像，决定 `browser_action` 是否可用；
7. Web Tools、Skills、Subagents、MCP 等功能开关是否启用；
8. 当前是 Plan 还是 Act，执行时是否禁止写工具；
9. 当前是否子智能体运行，子智能体不能再调 `use_subagents`；
10. MCP Server 是否已连接且未禁用。

## 13. 新增一个真正可由模型调用的工具

完整改造点不只是写一个 Handler，而是：

1. 在 `src/shared/tools.ts` 增加稳定 `ClineDefaultTool` ID。
2. 在 `src/core/prompts/system-prompt/tools/<tool>.ts` 定义 `ClineToolSpec`，包含参数和上下文条件。
3. 在 `tools/init.ts` 注册 Spec，并在需要的 Variant `config.ts` 将 ID 加入 `tools`。
4. 如果 XML 格式引入新参数，更新 `toolParamNames`。
5. 在 `src/core/task/tools/handlers` 实现 `IToolHandler`，需流式 UI 时实现 `IPartialBlockHandler`。
6. 在 `ToolExecutorCoordinator.toolHandlersMap` 注册 Handler。
7. 将风险类别接入 Auto Approve、Plan Mode 限制、Path Validator 和 `.clineignore`。
8. 在 Handler 中走统一审批和 Tool Result 通道，不要把结果只显示在 UI 而不返回模型。
9. 增加 XML 解析、Native Schema、参数错误、拒绝、Hook、取消和多工具并行测试。

## 15. 总结

Cline 给大模型的脚手架可以分为三类：

- “模型能主动调用”：常规内置工具、动态 MCP Tools、`use_skill`、`use_subagents` 和配置型 Subagent Tools。
- “模型在特定指令下调用”：`condense`、`summarize_task`、`report_bug`、`new_rule`。
- “不是 Tool，但改变模型行为或执行边界”：Rules、Workflows、MCP Prompts、Hooks、Plan/Act、Focus Chain、审批、`.clineignore` 和 Checkpoints。

理解这三类边界，才能在二次开发时正确回答“这个能力是否真的给到了模型”。
