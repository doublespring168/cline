# 聊天记录转存到独立目录（Markdown）

> 本文目标：在不破坏 Cline 现有恢复机制的前提下，把一个会话中客户端**实际观测到的**用户、大模型、工具、Hook、子代理等事件，以会话名为维度转存到另一个目录，并全部以 Markdown 保存。分析依据为 `src/core/task`、`src/core/api`、`src/core/context`、`src/core/storage`、工具处理器和 Hook 实现。

## 1. 先明确可实现的边界

当前项目的 `ui_messages.json` 和 `api_conversation_history.json` 是“当前状态投影”，会更新、覆盖、截断和删除；它们不适合直接复制成审计日志。改造应增加**追加式事件归档层**，原有 JSON 仍负责任务恢复。

归档可以做到：

- 保存用户输入、图片和普通附件的入口信息；
- 保存发送给模型的规范化请求、模型可见的文本/reasoning/tool call/usage 流、最终响应和中断/错误；
- 保存工具调用参数、审批、开始/结束、原始结果及送回模型的截断结果；
- 保存终端、MCP、浏览器、文件编辑、Hook、子代理等客户端收到的输出；
- 保存上下文压缩、删除范围、文件读取去重等变换前后的元数据。

归档不能凭客户端代码恢复：供应商服务端没有返回的隐式 CoT、内部草稿、采样 token、路由/检索中间过程，或者被 SDK 丢弃的原始网络事件。文档中应明确标记 `unavailable`，不能伪造“完整思考”。如果要求线级网络重放，还需在各 Provider 的 HTTP/SDK 边界安装脱敏 observer。

## 2. 建议的目录和文件格式

建议由配置项指定归档根目录，例如 `archiveRoot`，每个 task 使用不可变 taskId 防止同名会话覆盖：

```text
<archiveRoot>/
└── <safeSessionName>--<taskId>/
    ├── 会话.md                 # 由事件重建的人类可读索引/时间线
    ├── manifest.md             # schema、会话名、taskId、模型、隐私策略
    ├── events/                 # 每个事件一个不可变 Markdown
    │   ├── 000001-user-input.md
    │   ├── 000002-api-request.md
    │   ├── 000003-stream-chunk.md
    │   ├── 000004-tool-call.md
    │   └── ...
    ├── requests/               # 可选：完整请求快照/哈希
    ├── tools/                  # 可选：工具的大结果和 stdout/stderr
    ├── attachments/            # 普通文件的快照/提取文本元数据
    └── assets/                 # 图片、超大输出等二进制或原始文件
```

目录名必须经过跨平台清理（去掉 `/\\:*?"<>|`、控制字符、`.`/`..`、保留长度上限），建议使用“会话标题第一行 + `--` + taskId”。taskId 仍是唯一主键；不要只用用户可编辑的标题。

每个事件文件使用 YAML frontmatter，正文可放 Markdown 和 JSON：

````yaml
---
schemaVersion: 1
sequence: 42
eventId: "1700000000000-42-abc123"
ts: "2026-07-14T12:34:56.789Z"
taskId: "1700000000000"
sessionName: "修复登录问题"
kind: assistant_output
source: provider
requestId: "req-7"
callId: null
partial: false
enteredContext: true
redactionApplied: true
---

## 角色

assistant

## 规范化内容

模型输出文本……

## 结构化载荷

```json
{"type":"text","text":"模型输出文本……"}
```
````

实现时不要固定使用三个反引号包围正文；正文可能本身包含代码围栏，应选择未出现的 fence 长度，或把载荷写为单独的 `.json`/`.txt` 资产并在 Markdown 中引用。

## 3. 新增的核心抽象

### 3.1 `TaskArchiveSink`/`SessionArchiveService`

在 `src/core/task` 或 `src/core/storage` 新增与业务解耦的接口，建议最小 API：

```ts
type ArchiveEvent = {
  kind: string
  source: string
  ts?: number
  requestId?: string
  callId?: string
  payload: unknown
  enteredContext?: boolean
  partial?: boolean
}

interface TaskArchiveSink {
  append(event: ArchiveEvent): Promise<void>
  writeAsset(name: string, data: Uint8Array | string): Promise<string>
  flushProjection(): Promise<void>
  close(): Promise<void>
}
```

`TaskArchiveSink` 只负责序列化、排队、原子写入和脱敏，不负责理解模型业务。`SessionArchiveService` 负责按 task 建立 sink、派生会话名、恢复已有 sequence、生成 `会话.md` 投影。

在 `Controller.initTask`/任务创建处建立 sink，在 `getTaskWithId`/恢复任务处重新打开同一目录；不要在每次 Webview 消息时重新猜测会话目录。

### 3.2 追加而非重写

每个 task 使用 mutex/串行队列，sequence 单调递增。事件先写临时文件，再 `rename` 到 `events/`；写完事件后再更新 `会话.md` 临时文件并原子替换。崩溃恢复时扫描事件文件、按 sequence 排序并重建 projection。不要把全部记录放在一个不断重写的 Markdown 文件中，否则进程中断会造成半条记录和并发覆盖。

事件应是 immutable；`clineMessages` 的 `update`、`delete`、`overwrite` 只能产生新的 `ui_update`/`ui_delete`/`state_projection` 事件，不能修改历史事件。这样才能解释“界面现在显示什么”和“曾经发生过什么”的差异。

## 4. 源码插点与应记录内容

### 4.1 用户输入和附件

`Task.startTask` 会调用 `say("task", task, images, files)`，并把 `<task>`、图片 block、`processFilesIntoText(files)` 的结果加入 API 历史。`Task.handleWebviewAskResponse` 的原始审批按钮、文本、图片和文件目前主要在 `TaskState` 内存中，应在入口立即追加事件：

- `user_input`：原始文本、规范化文本、时间、模式和来源；
- `attachment_added`：原路径、文件名、大小、mtime、SHA-256、MIME、是否图片、提取方式和截断标记；
- 图片 data URL 解码到 `assets/`，正文只写相对路径和哈希；
- 普通文件在入口复制快照或读取快照，避免用户随后修改文件导致无法复现；原文件不可读也要写失败事件；
- 不要把巨大 base64 内嵌进会话主文件。

`process-files.ts` 对文本有 20 MB 输入限制、约 400 KB 的最终文本截断，并会清理 IPYNB 输出；归档应同时保存原文件元数据和“实际送入模型的提取文本”，而不是误称为完整附件内容。

### 4.2 API 请求、流和最终响应

在 `Task.attemptApiRequest`、`StreamResponseHandler`/流协调器及 Provider 调用边界增加三层事件：

1. `api_request`：模型/provider/mode、context window、system prompt 哈希或脱敏快照、实际发送的 history、工具 schema、参数、删除范围、请求 ID。
2. `stream_chunk`：统一的 `text`、`reasoning`、`tool_calls`、`usage` chunk，记录 sequence、累计/增量标记、结束原因和原始 provider 类型。
3. `assistant_output`/`api_request_end`：最终拼接的 `thinking`/`redacted_thinking`、文本、tool_use、模型信息、token/cost、finish reason、重试/取消/错误。

当前 `say`/`ask` partial 消息会更新同一条 UI 记录，不能从 UI 文件还原每一个 delta；归档若需要逐 delta，必须在 stream handler 收到 chunk 时追加 `stream_chunk`。如果只需最终语义，可只存聚合事件并写明 `partial=false`。

若要 wire fidelity，在 `src/core/api/providers/*` 的 HTTP/SDK 请求前后安装 observer，记录已脱敏 body、状态码、SSE/WS 事件和 SDK 错误。Authorization、API key、cookie、签名和 URL 中的 secret 必须在 observer 之前或序列化层统一删除；不能直接 dump SDK request。

### 4.3 工具执行

`ToolExecutor`/`ToolExecutorCoordinator` 是统一入口，工具处理器包括命令、文件读写、浏览器、MCP、搜索、任务/子代理等。每次工具调用至少追加：

- `tool_call_started`：工具名、native/XML 形态、callId、参数、模型请求 ID、用户审批结果；
- `tool_call_output`：开始/结束时间、stdout/stderr、UI 展示文本、原始结果、错误/退出码；
- `tool_result_to_model`：经过 `ToolResultUtils`、图片包装、`truncateContent` 后真正放入下一轮 user 消息的结果；
- `tool_call_finished`：成功、拒绝、取消或异常。

原始结果和送模型结果必须分开。MCP/资源处理器会在入模型前截断；文件和浏览器结果也可能只保留摘要。终端大输出由 `CommandOrchestrator` 写临时 `large-output` 日志，UI/API 只留首尾摘要和路径；归档应在生成临时文件时复制到 `assets/`，否则 `ClineTempManager` 的约 50 小时清理或 2 GB 上限会使旧会话失效。

### 4.4 Hooks 和子代理

`src/core/hooks/hook-executor.ts` 的启动、状态、流输出、结果、取消、错误都应成为 `hook` 事件；若 Hook 的 `contextModification` 进入模型上下文，额外标记 `enteredContext: true`，仅 UI 状态则标记 false。

`SubagentRunner` 当前内部 conversation 主要在内存，父任务只得到 status/summary/usage。若“全部输出”包含子代理，必须给每个子代理建立 `parentTaskId`、`subagentId` 和独立 sequence，记录其 request/chunk/tool/result/final summary；否则只能诚实声明归档的是父任务可见摘要。

### 4.5 上下文变换

在 `ContextManager.getNewContextMessagesAndMetadata` 前后追加 `context_compaction`：

- 变换前 API history 长度/哈希、deleted range、模型窗口和触发 token；
- 文件读取去重、重复内容替换、half/quarter/none/lastTwo 选择；
- 压缩 summary、Required Files、继续提示和文件内容；
- 变换后实际发送 history 哈希与 provider 格式；
- 自动/手动 `/smol`、`/compact`、context-window error 重试。

`context_history.json` 只保存覆盖操作，不包含完整旧文本；归档要把“原内容哈希、替换内容、原因、实际进入上下文”作为独立事件，才能解释模型看到的版本。

## 5. Markdown 投影设计

`会话.md` 不是唯一事实源，而是从 events 重建的可读索引。建议按时间/sequence 分段：

```markdown
# 修复登录问题

- taskId: `1700000000000`
- 开始: 2026-07-14T12:00:00Z
- 模型: `provider/model`

## 1. 用户输入

…

## 2. 模型响应（请求 req-7）

### 文本
…

### 工具调用
- `execute_command`, callId `call-1`

### 工具结果
[查看事件](events/000006-tool-result.md)
```

长文本和二进制用相对链接；正文中记录 `sha256`、原始字节数、实际嵌入字节数和截断原因。manifest 至少包含 `schemaVersion`、taskId、会话名、工作区、创建/结束时间、模型/provider、客户端版本、隐私/脱敏策略、事件计数和最后 sequence。

## 6. 配置、隐私和生命周期

建议增加：

- `archiveEnabled`：默认关闭或首次使用明确征得同意；
- `archiveRoot`：目录选择器/绝对路径，禁止路径穿越；
- `archiveRawStreamChunks`、`archiveCopyAttachments`、`archiveIncludeSubagents`；
- `archiveRedaction`、保留天数、最大单文件/总目录大小；
- 删除会话时是否同步删除本地归档、备份和远端副本。

归档可能包含源码、密钥误输出、终端日志、截图、Cookie 和个人信息。目录尽量使用 0700、文件 0600（平台支持时），脱敏字段要记录 `redactionApplied`，并提供显式“删除会话及资产”操作。`.clineignore` 只影响项目读取，不等于归档隐私策略；远端 S3/R2/Azure 同步也不能默认视为已删除。

## 7. 测试和验收清单

1. golden 测试：固定任务生成稳定 frontmatter、sequence、链接和哈希。
2. 并发测试：流式 chunk、工具输出、Hook 同时到达仍严格有序，重启后可 rebuild。
3. 崩溃测试：写临时文件/rename 前后断电，不能产生伪造完整事件。
4. 端到端测试：新任务、恢复、checkpoint、compact、模型切换、取消、重试和删除。
5. 载荷测试：图片、不可读附件、20 MB 文件、超大终端、MCP、浏览器、子代理。
6. 安全测试：密钥/Authorization/cookie 脱敏、Windows 名称、路径穿越、权限和保留策略。
7. 真实性测试：对照 provider 返回事件；隐藏 CoT、未返回的中间过程必须显示“不可获得”，不能生成替代文本。

## 8. 推荐实施顺序

先实现 `TaskArchiveSink`、manifest、事件序列和脱敏；再接入用户/assistant/API/tool 四类主链路；随后接入终端/MCP/Hook/子代理和附件快照；最后实现 context 变换、崩溃重建、设置 UI 和生命周期策略。这样即使后续某个工具尚未接入，也不会影响现有任务 JSON 的恢复。
