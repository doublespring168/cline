# Cline 模型连接、通信协议与凭证存储

> 分析范围：`apps/vscode` 当前模型配置、Provider Handler、格式转换、认证和存储源码。
> 权威 Provider 清单：`src/shared/api.ts` 的 `ApiProvider`；实际实例化入口：`src/core/api/index.ts`。

## 1. 核心结论

1. 当前代码定义了 **43 个 Provider ID**，`createHandlerForProvider()` 对它们都有分支。
2. “可连接的模型”不是一张固定表：部分 Provider 在 `src/shared/api.ts` 中内置模型目录，OpenRouter、Cline、LiteLLM、Ollama、LM Studio、OCA 等则在运行时拉取或允许输入任意 Model ID。
3. 项目没有发明一种统一网络协议。底层并存 Anthropic Messages、OpenAI Chat Completions、OpenAI Responses、Gemini GenerateContent、AWS Bedrock Converse/InvokeModel、Dify/AskSage 私有 REST、VS Code LM API 和本地 CLI。
4. Cline 在这些协议上面定义了自己的 `ApiHandler` 适配层，把输出归一为 `text | reasoning | tool_calls | usage` 四类流式事件。
5. 大部分 API Key 不再以 VS Code SecretStorage 作为当前主存储，而是写入 `~/.cline/data/secrets.json`（或 `CLINE_DIR`覆盖目录）。文件权限设为 `0600`，但内容是明文 JSON，并非 OS Keychain 加密容器。

## 2. 统一适配边界

`src/core/api/index.ts` 定义：

```ts
interface ApiHandler {
  createMessage(
    systemPrompt: string,
    messages: ClineStorageMessage[],
    tools?: ClineTool[],
    useResponseApi?: boolean
  ): ApiStream
  getModel(): { id: string; info: ModelInfo }
  getApiStreamUsage?(): Promise<ApiStreamUsageChunk | undefined>
  abort?(): void
}
```

这个接口隐藏了 Provider 差异：

```text
ClineStorageMessage + System Prompt + ClineTool
  → Provider Handler
  → 消息/Tool Schema 格式转换
  → SDK、HTTP/SSE、WebSocket、VS Code API 或 CLI
  → Provider 原生流
  → ApiStreamChunk(text/reasoning/tool_calls/usage)
  → Task Agent 循环
```

`src/core/api/transform/stream.ts` 是输出协议，而不是网络协议。

## 5. 不同协议如何被适配

### 5.1 内部消息形状

`ClineStorageMessage` 定义在 `src/shared/messages/content.ts`，整体接近 Anthropic `user/assistant + content blocks` 形状，并扩展：

- text/image；
- thinking/redacted thinking；
- tool_use/tool_result；
- `call_id`、response id、reasoning details/signature。

它是 Cline 的持久化/运行时中间格式，不意味着所有 Provider 走 Anthropic API。

### 5.2 请求转换

| 转换器 | 作用 |
| --- | --- |
| `transform/anthropic-format.ts` | 清理内部扩展字段，处理 Thinking、Cache 和 Tool Block |
| `transform/openai-format.ts` | 转成 Chat Completions messages/tool_calls/tool results，修正 Tool Call ID |
| `transform/openai-response-format.ts` | 转成 Responses API 异构 `input` item，保持 reasoning 与 function call 顺序 |
| `transform/gemini-format.ts` | 转成 Gemini Content/Part，保留 Thought Signature |
| `transform/mistral-format.ts` | 转成 Mistral 消息 |
| `transform/ollama-format.ts` | 转成 Ollama Message |
| `transform/r1-format.ts` | 处理 R1/DeepSeek 风格推理消息 |
| `transform/vscode-lm-format.ts` | 转成 `LanguageModelChatMessage` |

### 5.3 工具 Schema 适配

`src/core/prompts/system-prompt/spec.ts` 将同一 `ClineToolSpec` 转成：

- OpenAI Function Tool；
- Anthropic `input_schema` Tool；
- Gemini Function Declaration。

Bedrock 另在 `providers/bedrock.ts` 映射为 `ToolConfiguration`；Responses API Handler 把 Chat Tool 转成 Responses Function Tool。

### 5.4 流式响应适配

无论 Provider 返回：

- Anthropic `text_delta/thinking_delta/input_json_delta`；
- OpenAI `delta.content/delta.tool_calls/reasoning_content`；
- Responses `response.output_text.delta/function_call_arguments.delta`；
- Gemini `Part.text/Part.functionCall/Part.thought`；
- Bedrock Converse Event；

Handler 都需转成 `ApiStream` 的四种 Chunk。`ToolCallProcessor` 专门合并 OpenAI-compatible 分片的 Tool ID、Function Name 和 Arguments。

## 6. 推理/思考内容适配

不同协议的思考信息并不等价：

| 协议 | 常见形式 | Cline 处理 |
| --- | --- | --- |
| Anthropic | `thinking` / `redacted_thinking` + signature | 转成 `reasoning`，保留签名或加密 Data 以便下轮回传 |
| OpenAI Chat | `reasoning_content`、部分平台 `reasoning`/`reasoning_details` | 转成 `reasoning`，OpenRouter details 可原样保留 |
| OpenAI Responses | Reasoning Item/Summary/Encrypted Content | 保持 Item ID、Summary 和对应输出顺序 |
| Gemini | `thought` + `thoughtSignature` | 转成 `reasoning`，保留 Signature |
| R1/开源兼容模型 | `<think>...</think>` | 部分 Handler 在字符串层分离 Thinking 与 Text |

如果 Provider 只返回不可见的内部推理，Cline 无法凭空获取。项目只能存储/展示 Provider 真正在 API 中返回的 Reasoning、Summary、Signature 或加密块。

## 7. 工具调用支持并不完全一致

### 7.1 原生 Tool Calling

只有当：

- Prompt Variant 标记 `use_native_tools: 1`；
- 用户启用 Native Tool Calls；
- Provider Handler 把 `tools` 参数真正发给 API；
- Handler 能把 Tool Call Delta 还原成 `ApiStreamToolCallsChunk`；

才是完整原生 Tool Calling。

### 7.2 XML Tool Calling 兜底

对不传函数 Schema 的 Provider，System Prompt 可以说明 XML Tool 格式，模型输出文本后由 `parseAssistantMessageV2()` 解析。

因此看到 Handler 导入 OpenAI SDK，不能直接推导该 Provider 的每个模型都有原生 Tool Calling。例如 `AIhubmixHandler.createMessage()` 当前没有接收/透传 `tools` 参数，它虽然使用三家 SDK，当前主路并不等于完整原生工具适配。

## 8. API Key 和其他凭证的存储机制

### 8.1 当前主存储位置

`src/shared/storage/storage-context.ts` 创建：

```text
~/.cline/data/globalState.json
~/.cline/data/secrets.json
~/.cline/data/workspaces/<workspace-hash>/workspaceState.json
```

若设置 `CLINE_DIR`，根目录可被覆盖。

`secrets.json` 由 `ClineFileStorage` 原子写入，创建模式是 `0o600`。它的安全属性是“仅文件所有者读写”，不是内容加密。

### 8.2 设置是如何被分流的

`StateManager.setApiConfiguration()` 遍历配置：

- `isSecretKey(key)` 为真：写 `secretsCache`，然后批量持久化到 `secrets.json`；
- `isSettingsKey(key)` 为真：写 Global State；
- `getApiConfiguration()` 再把 Settings 与 Secrets 合并给 Handler Factory。

`src/shared/storage/state-keys.ts` 的 `SECRETS_KEYS` 包含主要 Provider Key，例如：

```text
apiKey, openRouterApiKey, openAiApiKey, openAiNativeApiKey,
awsAccessKey, awsSecretKey, awsSessionToken, awsBedrockApiKey,
geminiApiKey, deepSeekApiKey, qwenApiKey, mistralApiKey,
liteLlmApiKey, groqApiKey, huggingFaceApiKey, ...
```

还包含 OAuth JSON：

```text
cline:clineAccountId
openai-codex-oauth-credentials
ocaApiKey / ocaRefreshToken
mcpOAuthSecrets
```

### 8.3 VS Code SecretStorage 迁移的真实情况

`src/hosts/vscode/vscode-to-file-migration.ts` 明确说明：历史版本曾用 `ExtensionContext.globalState/workspaceState/secrets`，当前激活时会把它们迁移到文件存储，并且不覆盖已有文件值。

因此二次开发时不应把“代码中有 VS Code `context.secrets` 迁移读取”误解为“当前所有 Key 仍保存在 VS Code 加密 SecretStorage”。

## 9. 特殊认证路径

| Provider/场景 | 实际凭证来源 | 存储/刷新 |
| --- | --- | --- |
| Anthropic 及多数 Key Provider | Settings UI 输入 API Key | `StateManager` → `secrets.json` |
| OpenRouter OAuth | 浏览器授权获得 Code，调 `/api/v1/auth/keys` 换 Key | 最终写 `openRouterApiKey` |
| Cline/Cline Pass | Cline Auth Access/Refresh Token，或显式 `clineApiKey` | `cline:clineAccountId` 存 JSON Auth Info，Provider 通过 `AuthService.getAuthToken()` 取有效 Token |
| OpenAI Codex | OpenAI OAuth Authorization Code + PKCE | `openai-codex-oauth-credentials` 存 Access/Refresh/Expiry/Account ID；请求前 5 分钟缓冲刷新 |
| Qwen Code | Qwen CLI/OAuth 凭证文件 | 默认 `~/.qwen/oauth_creds.json`；Handler 到期刷新后原路径改写 |
| Claude Code | Claude Code CLI 自身登录/环境 | Cline 不保存该 CLI 的凭证；子进程自行解决 |
| AWS Bedrock | Access/Secret/Session Token、Bearer API Key、Profile 或 AWS Default Chain | Key 字段在 secrets.json；Profile/Region/Endpoint 在 Settings；Default Chain 可从环境/共享配置读 |
| Azure OpenAI | API Key 或 `DefaultAzureCredential` | Key 在 secrets.json；无 Key 且启用 Azure Identity 时从 Azure Credential Chain 取 Token |
| Vertex AI | Google Application Default Credentials | Cline 只保存 Project/Region 等非秘密设置；Google 凭证由 ADC 环境/工具链管理 |
| VS Code LM | VS Code 模型扩展的授权 | Cline 不保存 Provider Key；`sendRequest` 时 VS Code 展示授权说明 |
| OCA | OCA OAuth Access/Refresh Token | `ocaApiKey`、`ocaRefreshToken`，`OcaAuthService` 刷新并生成 OCI Header |
| SAP AI Core | OAuth Client ID/Secret 换 Access Token | Client ID/Secret 为 Secret，Token URL/Base URL/Resource Group/Deployment 为 Settings；Handler 运行时换 Token |

## 10. 密钥存储的风险与改造建议

### 10.1 当前风险

- `0600` 可阻止其他普通系统用户直接读文件，但无法防止同一用户权限下的恶意进程、备份泄漏或磁盘被复制。
- `secrets.json` 是可读 JSON，不应被打包、上传、放入日志或版本库。
- Remote Config 和普通用户 Key 可在内存中合并，日志和遥测不应序列化整个 `ApiConfiguration`。
- Qwen Code、Claude Code、ADC、AWS Profile 等凭证不在 Cline SecretKeys 内，备份/迁移 Cline 数据时不会自动携带它们。

### 10.2 若改为更强安全存储

建议保留 `StateManager` 接口，只替换 `StorageContext.secrets` 适配器：

1. VS Code 形态使用 `ExtensionContext.secrets`；
2. macOS/Linux/Windows Standalone 形态接入 Keychain/libsecret/Credential Manager；
3. 提供从现有 `secrets.json` 的一次性迁移；
4. 迁移成功后安全删除旧值，并保留可回滚的版本 Sentinel；
5. 不要改变 `SecretKeys`、`setSecret/getSecretKey` 对上层的契约。

## 12. 总结

Cline 的模型连接层是“多协议 Provider Adapter”，不是“全部请求一个统一后端”：

- Anthropic、Gemini、Bedrock、OpenAI Native 等走各自原生协议；
- 大量平台复用 OpenAI-compatible Chat Completions；
- OCA、SAP AI Core、AIhubmix 根据模型再做二级协议路由；
- Dify、AskSage、VS Code LM、Claude Code 使用专用通道；
- 所有响应最后被归一为 `ApiStream`，供同一 Agent 循环消费。

在密钥方面，当前实现的准确表述是：**API Key 与 OAuth JSON 主要保存在权限为 `0600` 的本地明文 JSON 文件，历史 VS Code SecretStorage 会迁移进来；部分 Provider 则委托 CLI、ADC、AWS/Azure Credential Chain 或自身 OAuth 文件。**
