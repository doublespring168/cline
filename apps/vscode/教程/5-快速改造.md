# Cline VS Code 快速熟悉与改造指南

> 目标：在不破坏协议、状态和 Agent 主循环的前提下，快速建立心智模型并开始修改。  
> 建议先阅读同目录的 `1-架构模式.md`、`2-技术栈.md`、`3-项目功能.md`、`4-模块关系.md`。

## 1. 先建立正确预期

这个项目约有 1,351 个源码文件、23 万行，不适合从 `src` 第一行开始顺序阅读。快速上手的正确方法是：

1. 先跑通构建和 Extension Development Host；
2. 掌握五条关键调用链；
3. 根据改造类型只深入一条链；
4. 修改前找到对应测试和协议；
5. 每次只跨越一个架构边界。

五条关键链是：

```text
启动链：extension -> common -> VscodeWebviewProvider -> Controller
任务链：UI -> TaskService -> Controller.initTask -> Task
模型链：Task -> Prompt/Context -> ApiHandler -> ApiStream
工具链：Tool Call -> ToolExecutor -> Handler -> Service/Host
状态链：StateManager -> State Stream -> ExtensionStateContext -> React
```

掌握它们比记住每个文件更重要。

## 2. 第一阶段：建立可运行基线

## 2.1 环境准备

仓库使用 Node 22：

```bash
nvm install 22
nvm use 22
node --version
npm --version
```

当前目录是：

```text
cline/apps/vscode
```

安装后端和 Webview 两套依赖：

```bash
npm run install:all
```

不要只在根目录执行一次 `npm install` 后就开始构建，因为 `webview-ui` 有独立的 `package.json` 和 `package-lock.json`。

## 2.2 生成协议代码

```bash
npm run protos
```

这一步会生成：

- `src/shared/proto`
- `src/generated`
- `webview-ui/src/services/grpc-client.ts`
- VS Code ProtoBus 与 Host Bridge 装配代码

这些目录当前可能不存在，但大量源码通过 `@generated` 或 `@shared/proto` 引用它们。构建失败时首先确认 Proto 是否生成成功。

## 2.3 建立一次完整构建

```bash
npm run check-types
npm run build:webview
node esbuild.mjs
```

预期输出：

```text
dist/extension.js
webview-ui/build/assets/index.js
webview-ui/build/assets/index.css
```

也可以运行完整生产检查：

```bash
npm run package
```

它会执行类型检查、Webview Build、Lint 和生产 Extension Bundle。

## 2.4 启动开发宿主

最直接的方式：

```bash
code --extensionDevelopmentPath="$PWD" --disable-workspace-trust "$PWD"
```

开发监听建议开三个终端：

```bash
npm run watch:esbuild
```

```bash
npm run watch:tsc
```

```bash
npm run dev:webview
```

在 macOS 且安装了 tmux 时，可以直接使用：

```bash
bash scripts/run-extension-host.sh
```

该脚本会生成 Proto、构建 Webview、启动三类 Watcher，并打开 Extension Development Host。

## 2.5 先记录基线

改造前至少保存：

- `git status --short`；
- `npm run check-types` 结果；
- `npm run test:unit` 结果；
- `npm run test:webview` 结果；
- Extension Development Host 中的基本 Chat/Settings 页面截图或录屏。

如果基线本身失败，应先确认是环境问题还是当前分支已有问题，不要把既有失败归因于自己的改动。

## 5. 常见改造的完整步骤

## 5.1 新增一个 UI—Core RPC

1. 在合适的 `proto/cline/<domain>.proto` 增加 message/rpc；
2. 执行 `npm run protos`；
3. 在 `src/core/controller/<domain>/<rpcName>.ts` 实现 Handler；
4. 不要手工修改生成的 Service Map；
5. Webview 使用生成的 `<Domain>ServiceClient.<rpcName>()`；
6. 补充 Handler Unit Test；
7. 如果是 Streaming RPC，在取消时注册 `GrpcRequestRegistry` cleanup；
8. 运行 Proto lint、类型检查和 Webview Test。

## 5.2 新增设置项

1. 在 `src/shared/storage/state-keys.ts` 定义 key、类型和 default；
2. 判断它属于 Global、Workspace、Task 还是 Secret；当前版本不再从云端 Remote Config 覆盖本地设置；
3. 执行 `node scripts/generate-state-proto.mjs` 或 `npm run protos`；
4. 在 `StateService.updateSettings` 或专用 RPC 中处理；
5. 在 `Controller.getStateToPostToWebview()` 暴露需要的状态；
6. 更新 `ExtensionStateContext` 初始值；
7. 增加 Settings UI；
8. 检查读取优先级：Remote > Session > Task > Global；
9. 增加 State Keys 和 UI Tests。

切勿只给 React 加一个 `useState` 就认为功能完成，否则刷新 Webview 或切换任务后会丢失。

## 5.3 新增内置工具

1. 在 `ClineDefaultTool` 添加名字；
2. 在 `core/prompts/system-prompt/tools` 定义描述、参数和启用条件；
3. 必要时给旧 Prompt 系统增加兼容；
4. 在 `tools/handlers` 实现 `IToolHandler`/`IPartialBlockHandler`；
5. 在 `ToolExecutorCoordinator` 注册；
6. 决定是否属于 `READ_ONLY_TOOLS`；
7. 配置 Auto Approve、Plan 限制和路径校验；
8. 接入 PreToolUse/PostToolUse Hook；
9. 定义 Chat 展示；
10. 增加 Handler、Prompt 和 E2E Test。

工具有三个同步面：**模型看到的定义、后端执行逻辑、用户看到的展示**。缺少任意一个都会产生不完整功能。

## 5.4 新增模型 Provider

1. 实现 `ApiHandler`；
2. 把供应商流转换为标准 `ApiStreamChunk`；
3. 在 `createHandlerForProvider()` 注册；
4. 在 Shared API Configuration/Secret Keys 中增加字段；
5. 更新 State Proto 和 Conversion；
6. 增加 Controller Model Refresh/Get Handler；
7. 增加 `components/settings/providers/<Provider>.tsx`；
8. 更新 Provider Utils、默认模型、价格和能力判断；
9. 测试 text、reasoning、tool_calls、usage、abort、retry；
10. 测试 Plan/Act 独立配置。

可以先参考与目标 API 最接近的现有 Provider，而不是从最复杂的 Cline/OpenRouter Provider 复制。

## 5.5 修改 Prompt

1. 先确认当前模型走 `system-prompt` 还是 legacy；
2. 确认 Variant Matcher；
3. 优先修改一个 Component 或 Tool Spec；
4. 避免直接在 Task 中拼大段 Prompt；
5. 更新 Snapshot/Integration Test；
6. 用至少一个原生 Tool Call 模型和一个 XML Tool 模型验证；
7. 检查 Token 增量和上下文窗口。

## 5.6 增加新的宿主能力

1. 修改 `proto/host/*.proto`；
2. 执行 Proto 生成；
3. 在 `hosts/vscode/hostbridge/<service>` 实现 VS Code Handler；
4. 生成 Host Client Interface；
5. 通过 HostProvider 暴露；
6. 为 External Host 实现同一 RPC；
7. Core 只调用 Port，不直接导入 `vscode`；
8. 增加 VS Code 与 External 两种测试。

## 6. 状态改造必须理解的四类状态

| 状态 | 位置 | 注意事项 |
| --- | --- | --- |
| Extension Settings | StateManager | 有 Remote/Session/Task/Global 优先级 |
| Task Runtime | TaskState | 多个 flag 有并发与合法组合要求 |
| Persistent Conversation | MessageStateHandler | API History 与 UI Messages 必须同步 |
| React Projection | ExtensionStateContext | 不是权威来源，只是后端投影与局部 UI 状态 |

### 6.1 Task ID 与 ULID

- `taskId` 常用于磁盘目录和历史定位；
- `ulid` 用于任务、请求和日志的稳定关联；不再用于远程遥测。

不要混用，也不要在恢复历史时无条件生成新 ULID。

### 6.2 消息时间戳

`ClineMessage.ts` 时间戳被 Webview 虚拟列表和增量更新当作稳定标识。源码明确避免在完成 partial message 时随意重写 timestamp。修改消息逻辑时必须保留这个约束。

### 6.3 API History 与 UI Messages

- API History 是下一次模型调用的上下文；
- Cline Messages 是用户界面和任务历史；
- 两者通过 `conversationHistoryIndex` 和 deleted range 对齐。

只改其中一个会导致恢复、Checkpoint 或上下文压缩错误。

## 7. 流式与取消改造的红线

新增任何长期异步功能时，都要回答：

1. 谁创建它？
2. 谁持有 AbortController？
3. 用户点击 Cancel 时如何停止？
4. Webview Unmount 时如何退订？
5. Task Dispose 时如何释放？
6. Extension Deactivate 时是否会留下 Timer/Watcher/Process？

项目已有的配对规则：

```text
subscribeToX -> 返回 unsubscribe
GrpcRequestRegistry.registerRequest -> cancel cleanup
setInterval -> dispose/clearInterval
chokidar.watch -> close
child process -> HookProcessRegistry/termination
ApiStream -> api.abort + iterator.return
Presentation Scheduler -> reset/dispose
```

不要只实现“成功结束”，忽略取消、错误和 Extension Reload。

## 8. 生成代码规则

以下通常是生成物，不应手工维护：

- `src/shared/proto`
- `src/generated`
- `webview-ui/src/services/grpc-client.ts`

源文件是：

- `proto/**/*.proto`
- `src/shared/storage/state-keys.ts`（部分 State Proto）
- `scripts/generate-*.mjs`

如果生成结果不对，应修改 Proto 或生成脚本，再重新运行 `npm run protos`。

## 9. 宿主边界改造原则

`src/core` 中新增功能时先问：它是 Agent 逻辑，还是 VS Code 能力？

- Agent 逻辑：放 Core；
- VS Code API：放 `hosts/vscode`；
- 可抽象 IDE 能力：定义 Port/Host Proto；
- 终端、Diff 等已有抽象：扩展 Interface 和 VS Code 实现；
- 不要因为只保留 VS Code 就让 Core 到处直接导入 `vscode`。

当前 Core 中已有少量 VS Code 泄漏，新代码不应继续扩大。

## 10. 安全改造检查

涉及文件、命令、网络和自动批准时必须检查：

- `.clineignore` 是否生效；
- 路径是否规范化并限制在工作区；
- Multi-root 路径是否带 Root；
- Shell 命令是否经过 Permission Controller；
- 工具是否需要用户批准；
- YOLO/Auto Approve 的本地权限边界是否正确；
- PreToolUse Hook 能否取消；
- 操作前是否需要 Checkpoint；
- Secret 是否进入日志、普通 Proto State 或聊天记录；
- Webview 内容是否经过 DOMPurify/CSP；
- 远程 URL、MCP Server 是否经过 Schema 和 Allowlist。


- `core/controller/grpc-recorder` 可记录请求/响应；
- 每个 ProtoBus 请求有 `request_id`；
- Streaming Request 必须观察 `is_streaming` 和 cleanup；
- HostBridge 请求在 Extension Host 内按生成的 Handler Map 分发。

### 12.4 Agent 调试

优先记录：

- taskId/ulid；
- 当前 mode/provider/model；
- TaskState 关键状态；
- Assistant Content Block；
- Tool Name/Params/Result；
- conversationHistoryIndex；
- abort/retry 状态。

不要把 API Key、Token、完整 Secret 或用户敏感文件写入日志。

## 13. 推荐的第一批改造

若目标是熟悉项目，不建议第一天就拆 Task。可以按风险从低到高：

1. 修改一个 Welcome/Settings 文案并跑 Webview Test；
2. 新增一个只读的 State RPC；
3. 给已有工具增加一个参数校验和 Unit Test；
4. 新增一个简单只读 Tool；
5. 修改一个 Prompt Component；
6. 扩展一个 Provider 设置字段；
7. 最后再改 Task Loop、Checkpoint、Auth 或 Storage Migration。

## 14. 如果目标是大规模重构

建议顺序：

### 第一步：固定行为

- 为要拆的 Controller/Task 路径增加 Characterization Test；
- 使用 gRPC Recorder 保存典型会话；
- 固定 State 和 Message Snapshot；
- 建立性能基线。

### 第二步：先抽 Port，不改行为

优先抽取：

- AuthPort；
- TaskStateProjector；
- CheckpointPort；
- ToolExecutionContext；
- ModelRequestRunner；
- ConversationRepository。

### 第三步：打断双向依赖

优先处理：

```text
Controller <-> Auth
Controller <-> Storage
Task <-> Hooks
Task <-> Checkpoints
UI Chat <-> MCP/Settings
```

### 第四步：显式状态机

将 TaskState 大量布尔字段逐步收敛成状态联合类型和事件迁移；先包裹旧逻辑，再替换内部实现。

### 第五步：拆分 UI Context

把 Backend State、Navigation、Models、MCP、Task Stream 分开，并引入 selector，降低重渲染和改动传播。

## 18. 最终建议

快速改造这个项目的核心原则是：

> **沿调用链修改，不沿目录猜测；先固定行为，再拆依赖；把协议、状态、取消、安全和跨平台视为功能的一部分。**

最值得先掌握的五个文件是：

```text
src/extension.ts
src/core/controller/index.ts
src/core/task/index.ts
src/core/storage/StateManager.ts
webview-ui/src/context/ExtensionStateContext.tsx
```

最值得先掌握的三个扩展点是：

```text
ApiHandler
ToolExecutorCoordinator
HostProvider
```

掌握这八个入口后，再进入具体 Feature 包，修改效率会比全量平铺阅读高很多。
