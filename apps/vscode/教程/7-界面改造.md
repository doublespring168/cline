# 将聊天界面移到右侧的改造指南

> 目标布局：聊天区域位于 VS Code 右侧，原来位于聊天右边的代码编辑器、Diff 或其他工作区内容位于聊天左侧。本文先说明当前源码的真实边界，再分别给出 Secondary Side Bar、主侧栏换边、右侧 WebviewPanel 和插件内部双栏四类实现方案。
>
> 分析范围：当前 `apps/vscode/package.json`、`src`、`webview-ui/src`、测试与构建脚本；分析日期：2026-07-14。本文只给出改造方案，不直接修改产品源码。

## 1. 先给出结论

当前正式 VS Code 扩展不是一个“左栏聊天 + 右栏内容”的 React 页面，而是：

```text
VS Code Workbench
├── Primary Side Bar（通常在左侧）
│   └── Cline WebviewView
│       └── React ChatView（内部为单列）
├── Editor Area
│   └── 代码编辑器、Notebook、Diff 等 VS Code 原生编辑器
├── Secondary Side Bar（通常在右侧，可选）
└── Panel（通常在底部：终端、输出、问题等）
```

因此，“聊天换到右侧、原有右侧区域换到左侧”通常有四种含义：

| 目标 | 正确方案 | 是否需要修改源码 | 推荐度 |
| --- | --- | --- | --- |
| 右侧聊天，左侧仍保留 Explorer/SCM，中间为编辑器 | 把 Cline View Container 移到 Secondary Side Bar | 否；只需提供引导 | 最高 |
| 整个主侧边栏从左换到右，编辑器自然位于它左边 | 修改 `workbench.sideBar.location` | 否；可选增加确认命令 | 中 |
| 聊天作为右侧编辑器标签固定打开 | 把 `WebviewView` 改为 `WebviewPanel`，使用 `ViewColumn.Beside` | 是，改动较大 | 特定产品形态使用 |
| 在插件自己的 Webview 内交换两个自定义 React 区域 | 在 `App.tsx` 上层建立双栏布局 | 是；但不能承载 VS Code 原生编辑器 | 仅限自定义内容 |

推荐最终布局：

```text
┌──────────────────┬──────────────────────────────────┬────────────────────┐
│ Primary Sidebar  │ Editor / Diff / Notebook         │ Secondary Sidebar  │
│ Explorer / SCM   │ 原来的右侧工作内容               │ Cline Chat         │
│ 左侧             │ 中间偏左                         │ 右侧               │
└──────────────────┴──────────────────────────────────┴────────────────────┘
```

这条路径能保留 VS Code 原生编辑器、Diff、Notebook 和终端行为，风险远低于把聊天重构成编辑器面板。

## 2. 当前界面源码是怎样组织的

### 2.1 VS Code 清单决定初始容器

`apps/vscode/package.json` 当前贡献：

```json
{
  "contributes": {
    "viewsContainers": {
      "activitybar": [
        {
          "id": "claude-dev-ActivityBar",
          "title": "Cline",
          "icon": "assets/icons/icon.svg"
        }
      ]
    },
    "views": {
      "claude-dev-ActivityBar": [
        {
          "type": "webview",
          "id": "claude-dev.SidebarProvider",
          "name": "",
          "icon": "assets/icons/icon.svg"
        }
      ]
    }
  }
}
```

`viewsContainers.activitybar` 表示扩展默认向 Activity Bar/Primary Side Bar 贡献容器。当前没有第二个聊天 View，也没有一个 React“右侧区域”。

`apps/vscode/src/registry.ts` 根据包名生成运行时视图 ID：

```ts
const ClineViewIds = {
  Sidebar: name + ".SidebarProvider",
}
```

清单中的 View ID 和这里必须一致。完成第 6 篇教程中的独立插件改名后，示例会变成 `acme-agent.SidebarProvider`。

### 2.2 Extension Host 注册的是 WebviewView

`apps/vscode/src/extension.ts` 注册：

```ts
vscode.window.registerWebviewViewProvider(
  VscodeWebviewProvider.SIDEBAR_ID,
  webview,
  { webviewOptions: { retainContextWhenHidden: true } },
)
```

`apps/vscode/src/hosts/vscode/VscodeWebviewProvider.ts` 实现的是：

```ts
vscode.WebviewViewProvider
```

它保存 `vscode.WebviewView`，并通过以下能力工作：

- `resolveWebviewView` 初始化 HTML、脚本和消息监听；
- `webviewView.show(...)` 显示或聚焦聊天；
- `onDidChangeVisibility` 通知 React 聊天已经可见；
- `retainContextWhenHidden` 保留输入框、滚动和组件状态；
- `postMessage` 把 Extension Host 状态推送给 React。

这说明聊天当前属于 Side Bar View，而不是 Editor `WebviewPanel`。

### 2.3 React 内部是单列聊天

入口链路：

```text
apps/vscode/webview-ui/src/main.tsx
→ App.tsx
→ components/chat/ChatView.tsx
→ components/chat/chat-view/components/layout/ChatLayout.tsx
```

`App.tsx` 在欢迎页之外会挂载设置、历史、MCP、Worktrees 和 ChatView。Cline Account 页面已删除。源码特别强调不能根据页面状态卸载 ChatView，因为其中保存了：

- 用户尚未发送的输入；
- `disableInput`/按钮状态；
- Ask Response Promise；
- 选中的图片与文件；
- 消息展开和滚动状态。

当前采用 `isHidden` 隐藏 ChatView，而不是销毁再创建。

`ChatView.tsx` 的结构为：

```text
ChatLayout
├── Main Content
│   ├── Navbar
│   ├── TaskSection 或 WelcomeSection
│   └── MessagesArea（React Virtuoso 虚拟列表）
└── Footer
    ├── AutoApproveBar
    ├── ActionButtons
    └── InputSection / ChatTextArea
```

`ChatLayout.tsx` 使用纵向 Grid/Flex：

```css
display: grid;
grid-template-rows: 1fr auto;
width: 100%;
height: 100%;
```

这里还有一个容易误判的实现细节：`ChatLayoutContainer` 的直接子节点只有 `MainContent`；`ChatView` 传入的主内容和 `footer` 都被包在 `MainContent` 这个纵向 Flex 容器中。因此 `footer` 上的 `gridRow: "2"` 并没有跨过组件边界去占据外层 Grid 的第二行，输入区实际依靠前一个 `flex-1` 内容区被推到底部。若后续重做内部双栏，应先整理这层 DOM/Grid 关系，不能只改 `grid-template-columns`。

所以在 React 中查找 `flex-row-reverse` 或交换两个组件顺序，并不能把 VS Code 编辑器移到聊天左边。

### 2.4 原来的“右侧区域”属于 VS Code

`apps/vscode/src/hosts/vscode/VscodeDiffViewProvider.ts` 通过原生命令打开 Diff：

```ts
vscode.commands.executeCommand("vscode.diff", originalUri, modifiedUri, title, {
  preserveFocus: true,
})
```

代码编辑器、Diff 和 Notebook 都由 VS Code Editor Area 管理，不是 Webview DOM。React 无法把原生编辑器作为 `<div>` 子组件放到左栏，也不能用 CSS 调换它与 Webview 的顺序。

## 3. 方案一：把聊天移动到 Secondary Side Bar

这是实现“左侧工作区 + 中间编辑器 + 右侧聊天”的推荐方案。

### 3.1 用户操作

在 VS Code 中：

1. 打开 Cline；
2. 显示 Secondary Side Bar：`View` → `Appearance` → `Secondary Side Bar`；
3. 右键 Cline 的 Activity Bar/View Container 标题；
4. 选择 `Move to Secondary Side Bar`；
5. 保持 Explorer、Search、SCM 等在 Primary Side Bar；
6. 拖动右侧分隔线调整聊天宽度。

不同 VS Code 版本的菜单文字可能略有差异，也可以直接把 Cline 容器拖到 Secondary Side Bar。VS Code 会在用户布局状态中记住移动结果。

移动后的结构：

```text
左：Explorer / Search / SCM
中：代码编辑器 / Cline Diff / Notebook
右：Cline Chat
下：Terminal / Output / Problems
```

### 3.2 为什么通常不需要改源码

View Container 被用户移动后：

- View ID 仍是 `claude-dev.SidebarProvider`；
- `registerWebviewViewProvider` 仍然有效；
- `webviewView.show(true/false)` 会在新位置显示；
- `FocusChatInput`、Add to Chat、终端添加到聊天不需要改协议；
- React 仍只看到自己的 Webview 宽高，不关心宿主在左还是右；
- `retainContextWhenHidden` 仍会保留聊天输入和滚动状态。

这正是宿主布局和业务 UI 分离的好处。

### 3.3 为什么不应在 `package.json` 中发明右侧容器键

当前扩展引擎为：

```json
"engines": {
  "vscode": "^1.84.0"
}
```

当前清单使用稳定的 `viewsContainers.activitybar` 贡献方式。不要自行把它改成未经当前扩展清单 Schema 支持的 `auxiliarybar`、`secondarySidebar` 等键；无效贡献点会导致清单校验失败或被忽略。

`panel` 贡献点指的是底部 Panel，不等于右侧 Secondary Side Bar：

```json
"viewsContainers": {
  "panel": []
}
```

把 `activitybar` 改成 `panel` 只会把聊天移到底部，不会实现本文目标。

### 3.4 产品源码应该做什么

由于扩展不应未经同意重排用户的整个 Workbench，推荐只做引导：

- 在首次使用说明中增加“将聊天移动到右侧”；
- README 或“布局帮助”页面提供操作截图；
- 提供“打开布局帮助”命令，而不是自动修改全局布局；
- 不依赖 Cline 永远位于 Primary Side Bar；
- E2E 同时覆盖聊天位于 Primary 和 Secondary 两种情况。

如果第 6 篇教程已经把插件改名为 Acme Agent，文案、命令和 View ID 应全部使用新品牌，但移动原理相同。

## 4. 方案二：把整个 Primary Side Bar 放到右侧

如果你只需要最简单的两块布局：

```text
改造前：[Cline/Primary Side Bar][Editor]
改造后：[Editor][Cline/Primary Side Bar]
```

可以在 VS Code 用户设置中使用：

```json
{
  "workbench.sideBar.location": "right"
}
```

也可以执行命令面板中的 `View: Toggle Primary Side Bar Position`。

该方案的副作用是 Explorer、Search、SCM 和其他 Primary Side Bar 容器也会一起到右侧。若要求 Explorer 保持左侧、聊天单独在右侧，应使用方案一。

### 4.1 可选的插件命令

如果产品确实需要提供一键设置，必须先取得用户确认，不应在 `activate()` 时静默执行：

```ts
const choice = await vscode.window.showInformationMessage(
  "是否将 VS Code 主侧边栏移动到右侧？这也会移动 Explorer、Search 和 SCM。",
  { modal: true },
  "移动到右侧",
)

if (choice === "移动到右侧") {
  await vscode.workspace
    .getConfiguration("workbench")
    .update("sideBar.location", "right", vscode.ConfigurationTarget.Global)
}
```

配套要求：

- 在 `apps/vscode/package.json` 中显式贡献命令；
- 在 `apps/vscode/src/registry.ts` 中注册同一个命令 ID；
- 在 `apps/vscode/src/extension.ts` 中实现命令；
- 提供恢复为 `left` 的命令；
- 只修改用户明确选择的 Global Setting；
- 不在工作区设置中强制团队所有成员使用相同布局。

## 5. 方案三：把聊天改成右侧 WebviewPanel

仅当产品明确要求“聊天是 Editor Area 中固定打开在右边的标签页”，并且可以接受较大的宿主重构时，才使用此方案。

目标：

```text
Editor Group 1（左）                 Editor Group 2（右）
┌──────────────────────────────┐    ┌──────────────────────┐
│ 源码 / Diff / Notebook       │    │ Cline WebviewPanel   │
└──────────────────────────────┘    └──────────────────────┘
```

### 5.1 WebviewView 与 WebviewPanel 的差异

| 能力 | 当前 WebviewView | 改造后的 WebviewPanel |
| --- | --- | --- |
| 所属区域 | Side Bar View | Editor Group |
| 创建方式 | 清单 View + `registerWebviewViewProvider` | `createWebviewPanel` |
| 显示方式 | `webviewView.show()` | `panel.reveal()` |
| 位置 | 用户可移动的 View Container | `ViewColumn`/Editor Group |
| 可见事件 | `onDidChangeVisibility` | `onDidChangeViewState` |
| 关闭后 | VS Code 管理 View | Panel 被销毁，需要重建 |
| 上下文保留 | `retainContextWhenHidden` | `retainContextWhenHidden`，但关闭仍销毁 |
| 恢复 | View 自动解析 | 需要 Serializer 或手动重新打开 |

### 5.2 不要同时创建两个 WebviewProvider

`apps/vscode/src/core/webview/WebviewProvider.ts` 当前只有一个静态实例：

```ts
private static instance: WebviewProvider | null = null
```

每个 Provider 构造时还会创建一个 `Controller`。因此不能简单地保留 `VscodeWebviewProvider`，再 `new` 一个 Panel Provider；否则会：

- 覆盖全局 `WebviewProvider.instance`；
- 创建两套 Controller 和任务状态；
- 两个 Webview 争用消息和焦点；
- Dispose 任意一个后破坏另一个。

正确做法是二选一：

1. Panel 完全替代 Sidebar；或
2. 一个 Provider/Controller 管理两种 Surface，并明确唯一活动 Surface。

若不需要同时显示两处，优先使用“Panel 完全替代 Sidebar”。

### 5.3 修改命令注册表

在 `apps/vscode/src/registry.ts` 增加：

```ts
const ClineCommands = {
  // ...现有命令
  OpenChatOnRight: prefix + ".openChatOnRight",
}
```

在 `apps/vscode/package.json` 同步贡献：

```json
{
  "command": "cline.openChatOnRight",
  "title": "Open Chat on the Right",
  "category": "Cline",
  "icon": "$(layout-sidebar-right)"
}
```

如果已经执行独立插件改名，应使用 `acme-agent.openChatOnRight`，不能继续使用 `cline.*`。

### 5.4 重构 VscodeWebviewProvider

把 `apps/vscode/src/hosts/vscode/VscodeWebviewProvider.ts` 从只保存 `WebviewView` 改为保存 `WebviewPanel`。核心结构可以按以下方式设计：

```ts
export class VscodeWebviewProvider extends WebviewProvider {
  private panel?: vscode.WebviewPanel
  private panelDisposables: vscode.Disposable[] = []

  public async openInRightEditor(preserveFocus = false): Promise<void> {
    if (this.panel) {
      this.panel.reveal(vscode.ViewColumn.Beside, preserveFocus)
      await sendShowWebviewEvent(preserveFocus)
      return
    }

    const panel = vscode.window.createWebviewPanel(
      `${ExtensionRegistryInfo.name}.chatPanel`,
      "Cline",
      {
        viewColumn: vscode.ViewColumn.Beside,
        preserveFocus,
      },
      {
        enableScripts: true,
        retainContextWhenHidden: true,
        localResourceRoots: [vscode.Uri.file(HostProvider.get().extensionFsPath)],
      },
    )

    this.panel = panel
    panel.webview.html =
      this.context.extensionMode === vscode.ExtensionMode.Development
        ? await this.getHMRHtmlContent()
        : this.getHtmlContent()

    this.setWebviewMessageListener(panel.webview)

    panel.onDidChangeViewState(
      async ({ webviewPanel }) => {
        if (webviewPanel.visible) {
          await sendShowWebviewEvent(true)
        }
      },
      undefined,
      this.panelDisposables,
    )

    panel.onDidDispose(
      () => {
        this.panel = undefined
        while (this.panelDisposables.length) {
          this.panelDisposables.pop()?.dispose()
        }
      },
      undefined,
      this.panelDisposables,
    )

    await sendShowWebviewEvent(preserveFocus)
  }

  override isVisible(): boolean {
    return this.panel?.visible ?? false
  }
}
```

这段代码是结构示例，落地时还要同步现有私有方法和生命周期。尤其注意：

- `getWebviewUrl()` 改用 `this.panel.webview.asWebviewUri(...)`；
- `getCspSource()` 改用 `this.panel.webview.cspSource`；
- `postMessageToWebview()` 改为向 `this.panel?.webview` 发送；
- `setWebviewMessageListener` 需要允许 Panel 复用，并清理旧监听器；
- `onDidChangeVisibility` 改为 `onDidChangeViewState`；
- `webviewView.show()` 改为 `panel.reveal()`；
- 首次创建 Panel 时应等待 React/Webview Ready 握手或暂存 Show Event，避免订阅尚未建立就发送聚焦事件；
- `dispose()` 在扩展停用时关闭 Panel 并调用 `super.dispose()`；
- 用户关闭 Panel 时不要立即调用 `super.dispose()`，否则 Controller 和静态 Provider 被销毁，命令无法重新打开聊天。

### 5.5 修改扩展激活逻辑

Panel-only 模式下，`apps/vscode/src/extension.ts` 不再注册 Sidebar Provider：

```ts
// 删除 Panel-only 模式下的这一段：
vscode.window.registerWebviewViewProvider(...)
```

注册打开命令：

```ts
context.subscriptions.push(
  vscode.commands.registerCommand(commands.OpenChatOnRight, async () => {
    await webview.openInRightEditor(false)
  }),
)
```

原来的 `FocusChatInput` 应统一走新方法：

```ts
vscode.commands.registerCommand(commands.FocusChatInput, async (preserveEditorFocus = false) => {
  await webview.openInRightEditor(preserveEditorFocus)
  sendShowWebviewEvent(preserveEditorFocus)
})
```

不要同时从 `openInRightEditor` 和命令处理器重复发送两次 Show Event，最终实现选择一个发送位置即可。

### 5.6 修改所有“打开 Sidebar”的调用

当前以下逻辑依赖 `${SidebarId}.focus`：

| 文件 | 当前行为 | Panel 模式改法 |
| --- | --- | --- |
| `apps/vscode/src/hosts/vscode/commandUtils.ts` | 执行 `FocusChatInput` | 保留，内部改为打开 Panel |
| `apps/vscode/src/hosts/vscode/hostbridge/workspace/openClineSidebarPanel.ts` | 执行 `${Sidebar}.focus` | 改为执行 `FocusChatInput` |
| `apps/vscode/src/extension.ts` 的 `openClineSidebarForTaskUri` | 聚焦 Sidebar 并轮询可见实例 | 改为 `openInRightEditor` 并等待 Panel Ready |
| Add to Chat/Explain/Improve/Fix | 先打开 Webview，再提取上下文 | 确保不丢失活动编辑器上下文 |
| Worktree 自动打开 | 调 Host Bridge 打开 Sidebar | 重命名或让桥接方法兼容 Chat Surface |

建议把带宿主位置含义的名字逐步中性化：

```text
openClineSidebarPanel → openChatSurface
SIDEBAR_ID            → CHAT_VIEW_ID（仅保留 View 时）
getSidebar()          → getChatFrame()
```

当前只有 VS Code 消费者；Proto/Host Bridge 重命名时仍应同步生成代码、Handler、Webview Client 和测试，避免契约漂移。

### 5.7 保留编辑器焦点和选择

`getContextForCommand()` 当前先调用 `showWebview()`，再读取：

```ts
vscode.window.activeTextEditor
```

Panel 获得焦点后，活动编辑器上下文可能变化。改造时应先快照编辑器、选择区和诊断，再显示聊天：

```ts
const editor = vscode.window.activeTextEditor
const selection = range instanceof vscode.Range ? range : editor?.selection
const selectedText = editor && selection ? editor.document.getText(selection) : ""
const filePath = editor?.document.uri.fsPath

await showWebview(options?.preserveEditorFocus ?? false)
```

对于“Add to Chat”“终端添加到聊天”等非打断式入口，使用 `preserveFocus: true`。只有用户明确执行 `Jump to Chat Input`（命令 ID 为 `cline.focusChatInput`）时才让 Panel 获取焦点。

### 5.8 处理 Panel 关闭和草稿

当前 `App.tsx` 不卸载 ChatView，是为了保留输入草稿和 Promise 状态；Sidebar 隐藏时又有 `retainContextWhenHidden`。但用户关闭 WebviewPanel 会销毁整个 React 页面。

必须选择一种策略：

1. 用 `vscode.setState/getState` 保存未发送草稿、选中文件和 UI 状态；
2. 把关键草稿通过 gRPC/Extension State 存在 Extension Host；
3. 使用 `registerWebviewPanelSerializer` 在窗口重载后恢复 Panel；
4. 明确关闭会丢弃草稿，并在有草稿时提示用户。

Ask Response Promise 和正在执行的任务不能只存在 React 中。任务生命周期应继续由 Controller/StateManager 管理，Panel 重建后重新订阅并获取最新状态。

### 5.9 调整 Panel 模式的主题

当前：

- `apps/vscode/webview-ui/src/main.css` 的 `body` 使用 `--vscode-sideBar-background`；
- `ChatView.tsx` Footer 使用 `--vscode-sidebar-background`；
- `WebviewProvider.getHtmlContent()` 的页面标题为 Cline。

聊天进入 Editor Group 后，建议使用统一产品变量：

```css
:root {
  --chat-surface-background: var(
    --vscode-editor-background,
    var(--vscode-sideBar-background)
  );
}

body,
#root {
  background: var(--chat-surface-background);
}
```

不要直接把所有 `sideBar` 变量替换为 `editor` 变量；按钮、输入框、列表和 Code Block 应继续使用对应的 VS Code Semantic Color。

## 6. 方案四：在 Webview 内建立自定义双栏

只有当“原有右侧区域”本身也是你准备在 React 中实现的自定义区域，例如任务列表、文件树、预览、计划面板时，才使用本方案。

当前仓库没有这样的右侧 React 组件。必须先明确新组件，例如：

```text
WorkspacePane：自定义任务/文件/预览区
ChatPane：当前 App/ChatView
```

不能把 VS Code 原生 TextEditor、Diff Editor 或 Terminal 作为 `WorkspacePane` 嵌入。

### 6.1 在 App 上层交换顺序

建立 `apps/vscode/webview-ui/src/components/layout/SplitWorkbenchLayout.tsx`：

```tsx
import type { ReactNode } from "react"

interface SplitWorkbenchLayoutProps {
  workspace: ReactNode
  chat: ReactNode
}

export function SplitWorkbenchLayout({ workspace, chat }: SplitWorkbenchLayoutProps) {
  return (
    <main className="grid h-screen w-full min-h-0 overflow-hidden grid-cols-[minmax(280px,1fr)_1px_minmax(360px,1fr)]">
      <section className="min-w-0 min-h-0 overflow-hidden">
        {workspace}
      </section>

      <div
        aria-hidden="true"
        className="bg-[var(--vscode-sideBar-border,var(--vscode-panel-border))]"
      />

      <section className="min-w-0 min-h-0 overflow-hidden">
        {chat}
      </section>
    </main>
  )
}
```

顺序已经是“原右区在左，聊天在右”。在 `App.tsx` 中，应该把现有页面切换整体放入 `chat`，并继续让 ChatView 常驻：

```tsx
<SplitWorkbenchLayout
  workspace={<WorkspacePane />}
  chat={
    <ChatSurface>
      {showSettings && <SettingsView ... />}
      {showHistory && <HistoryView ... />}
      {showMcp && <McpView ... />}
      {showAccount && <AccountView ... />}
      {showWorktrees && <WorktreesView ... />}
      <ChatView isHidden={showSettings || showHistory || showMcp || showAccount || showWorktrees} ... />
    </ChatSurface>
  }
/>
```

不要写成：

```tsx
{activeView === "chat" && <ChatView />}
```

否则切换页面会卸载 ChatView，丢失输入、附件、滚动与交互 Promise。

### 6.2 加入可拖动分隔条

双栏产品通常需要可调整宽度。推荐：

- 用 Pointer Events，而不是只监听鼠标；
- 分隔条设置 `role="separator"` 和键盘操作；
- 宽度限制在合理区间，例如左侧最小 280px、聊天最小 360px；
- 使用 `ResizeObserver` 获取实际容器宽度；
- 把比例保存在 Webview State，而不是写死像素；
- 窄于断点时切换为单栏/抽屉，不要把聊天压成不可用宽度。

状态示例：

```ts
const [chatRatio, setChatRatio] = useState(0.42)

const chatWidth = Math.max(360, containerWidth * chatRatio)
const workspaceWidth = Math.max(280, containerWidth - chatWidth - 6)
```

不要仅使用 `window.innerWidth`。当 Webview 位于 Side Bar、Secondary Side Bar 或 Editor Group 时，真正需要观察的是布局容器。

### 6.3 修改 ChatLayout 的嵌套高度约束

`ChatLayout.tsx` 当前包含：

```css
height: 100%;
min-height: 100vh;
```

嵌入双栏后推荐改成：

```css
height: 100%;
min-height: 0;
min-width: 0;
```

并确保每一层都有：

```text
外层：h-full min-h-0 overflow-hidden
Chat 主区：flex-1 min-h-0 min-w-0
MessagesArea：h-full min-h-0 overflow-hidden
Virtuoso：grow min-h-0
Footer：flex-none
```

缺少 `min-h-0` 会让消息列表撑开父容器，导致输入框离开底部；缺少 `min-w-0` 会让长代码、路径或 Diff 撑破聊天栏。

### 6.4 修复弹层定位

双栏后需要审查：

| 文件 | 当前假设 | 双栏风险 |
| --- | --- | --- |
| `ChatTextArea.tsx` | 输入区占整个 Webview 宽度 | 内部栏变窄后按钮可能拥挤 |
| `ContextMenu.tsx` | 以输入区左右 15px 定位 | 若定位父级正确通常可保留 |
| `SlashCommandMenu.tsx` | `left/right: 15px` | 必须保证相对 ChatPane 定位 |
| `ServersToggleModal.tsx` | 使用 `document.documentElement.clientWidth` | 会按整个 Webview 而不是聊天栏计算箭头 |
| `AutoApproveModal.tsx` | 已用 `ResizeObserver` | 可作为响应式实现参考 |
| 全屏 Settings/Account Modal | 可能使用 `fixed`/`w-screen` | 可能覆盖左侧 WorkspacePane |

`ServersToggleModal` 应基于 ChatPane 或按钮容器：

```ts
const containerRect = chatPaneRef.current?.getBoundingClientRect()
const buttonRect = buttonRef.current?.getBoundingClientRect()

const rightPosition =
  containerRect && buttonRect
    ? containerRect.right - (buttonRect.left + buttonRect.width / 2)
    : 0
```

如果设置、历史页面只属于聊天区域，它们的 `position: fixed` 应改成相对 Chat Surface 的 `absolute inset-0`，且 Chat Surface 本身设置 `relative`。

### 6.5 响应式布局

建议断点：

```text
总宽度 >= 900px：左右双栏
总宽度 600–899px：可拖动双栏，隐藏非关键按钮文字
总宽度 < 600px：单栏，WorkspacePane 通过抽屉或 Tab 切换
聊天宽度 < 360px：不允许继续缩小
```

当前聊天原本就是为 Side Bar 窄宽度设计，因此消息、输入和按钮大多能适应。但仍需检查：

- 长模型名与 Provider 名；
- Plan/Act 切换；
- 文件/图片缩略图；
- Auto Approve 两列/一列切换；
- MCP、Mention 和 Slash Command 弹层；
- Mermaid、代码块、DiffEditRow 横向滚动；
- TaskHeader 成本、Token 和 Focus Chain；
- 中文、英文和长路径的截断。

## 10. 常见错误

### 10.1 只给 ChatView 加 `float: right`

Webview 的 `body` 只能控制 Webview 内部，不能改变 WebviewView 在 VS Code Workbench 中的位置。结果只是聊天内容在原来的左侧容器内部右对齐。

### 10.2 把 `activitybar` 改成 `panel`

这会把聊天放到底部 Panel，不是右侧 Secondary Side Bar。

### 10.3 修改 `workbench.sideBar.location` 后发现 Explorer 也去了右边

这是预期行为。该设置移动整个 Primary Side Bar。若只移动聊天，使用 Secondary Side Bar。

### 10.4 同时保留 Sidebar 和 Panel

当前单例 WebviewProvider/Controller 架构不支持直接创建两份。会导致状态、消息、Dispose 和焦点冲突。要么只保留一个 Surface，要么先完成单 Controller 多 Surface 的协议设计。

### 10.5 关闭 Panel 后命令报 Provider 未初始化

Panel `onDidDispose` 错误调用了 `super.dispose()`，清空了静态 Provider 和 Controller。关闭 Panel 只应释放 Panel 级资源；扩展停用时才做完整 Dispose。

### 10.6 Panel 打开后 Add to Chat 读取不到选区

显示 Panel 抢走焦点后才读取 `activeTextEditor`。应先快照编辑器上下文，或使用 `preserveFocus: true`。

### 10.7 双栏后输入框跑出屏幕

通常是 Flex/Grid 子节点缺少 `min-h-0`，或者 `ChatLayout` 的 `min-height: 100vh` 与嵌套容器冲突。

### 10.8 弹层出现在两栏中间或越界

弹层使用了 `document.documentElement.clientWidth`、`w-screen` 或相对整个页面的 Fixed Position。改为基于 ChatPane 容器测量和定位。

### 10.9 移到右边后配色不协调

Side Bar 与 Editor 使用不同 VS Code Theme Token。Secondary Side Bar 仍适合 `sideBar` Token；WebviewPanel 则应考虑 `editor` Background Token。

## 13. 最终建议

对于当前项目，优先采用 **Secondary Side Bar**：它无需改动聊天业务源码，就能得到“左侧项目工具、中间代码/Diff、右侧聊天”的布局，并保留现有 `WebviewView` 的状态、焦点和生命周期设计。

只有当产品明确要求聊天作为 Editor Tab、必须由插件代码创建右侧编辑器组时，才实施 WebviewPanel 重构。若所谓“原有右侧区域”是 VS Code 原生编辑器，则不要尝试在 `App.tsx` 中用 CSS 交换；React 双栏只适用于插件自己拥有的两个自定义区域。
