# Cline 聊天记录存储机制

> 本文基于当前仓库源码分析。项目中存在两套并行的会话实现：正式 VS Code 扩展位于 `apps/vscode`，新 SDK/CLI 位于 `sdk/packages/*` 与 `apps/cli`。二者的目录、消息模型、压缩方式和持久化时机都不同，不能把一套实现的结论直接套到另一套。

## 1. 结论先行

Cline 会保存足以恢复会话的主要消息，但现有存储不是“从输入字节到流式响应字节全部不丢失”的审计日志。

| 内容 | VS Code 扩展 | SDK/CLI | 结论 |
| --- | --- | --- | --- |
| 用户发送的文本 | 写入 UI 历史和 API 历史 | 写入 `messages[]` | 基本完整，但可能经过提示词包装、Mention 展开或规范化 |
| 用户图片 | UI 历史通常为 Data URL；API 历史为 Base64 图片块 | Base64 图片块 | 图片内容通常能恢复，体积可能很大 |
| 用户文件附件 | UI 历史主要保存路径；API 历史保存提取后的文本 | 保存路径和读取后的文本 | 不等于备份原文件，二进制、超限内容或后续被修改的文件不能原样恢复 |
| 模型最终文本 | 保存 | 保存 | 是 |
| 模型显式 reasoning/thinking | Provider 返回时保存 | Provider 返回时保存 | 条件完整；未返回的隐式思考无法保存 |
| 加密/删减推理块 | 可保存 `redacted_thinking`、签名等 | 可保存 `redacted_thinking` 和元数据 | 保存的是 Provider 给出的密文/标记，不是可读思考正文 |
| 工具名称和参数 | 保存为 Tool Use 或 UI 工具事件 | 保存为 `tool_use` | 是 |
| 工具调用结果 | 保存为 Tool Result 和 UI 事件 | 保存为 `tool_result` | 通常保存，但可能在进入历史前已被截断、转换或丢弃二进制内容 |
| 流式文本/reasoning delta | UI 中不断覆盖 partial，最终保存聚合值 | 运行时有 delta 事件，消息文件保存聚合消息 | 不保存逐 chunk 原始时间线 |
| 工具运行中的每次进度更新 | 只保存部分 UI 状态/命令输出 | 运行时有 `tool-updated`，消息文件不保证逐次保存 | 不是完整工具事件日志 |
| 原始 HTTP 请求/响应、SSE、Header | 不在聊天历史中 | 不在会话消息文件中 | 否，且 Header 可能包含密钥，本来也不应直接归档 |
| System Prompt | 不作为普通 API 历史消息保存，由运行时重建 | `system_prompt` 可选保存在消息文件顶层 | 两套不同 |
| Provider 内部 Chain of Thought | 无法获得 | 无法获得 | 任何客户端都无法记录 Provider 没有返回的内容 |

因此，“所有用户可见消息、模型可见消息和主要工具结果”大多有记录；“原始流事件、原始附件、工具底层全部 stdout/二进制、Provider 内部过程”没有完整记录。

## 2. VS Code 扩展的存储位置

每个任务以 `taskId` 建立独立目录：

```text
{HostProvider.globalStorageFsPath}/tasks/<taskId>/
├── api_conversation_history.json
├── ui_messages.json
├── context_history.json
└── task_metadata.json
```

`HostProvider.globalStorageFsPath` 是宿主提供的全局存储目录。在 VS Code 中它来自扩展的 `globalStorageUri.fsPath`；实际绝对路径由操作系统、VS Code 版本和扩展 ID 决定，不能假定为 `~/.cline/data`。迁移与路径接入可参考：

```text
apps/vscode/src/hosts/vscode/vscode-to-file-migration.ts
apps/vscode/src/core/storage/disk.ts
apps/vscode/src/hosts/host-provider.ts
```

四个文件的职责如下：

| 文件 | 主要职责 | 是否是聊天正文 |
| --- | --- | --- |
| `ui_messages.json` | 恢复 ChatView 所需的 `ClineMessage[]` | 是，偏 UI 展示语义 |
| `api_conversation_history.json` | 恢复可发送给模型的 `ClineStorageMessage[]` | 是，偏 Provider 消息语义 |
| `context_history.json` | 保存按消息索引、内容块索引和时间戳组织的上下文改写记录 | 否，是上下文截断/文件读取优化的补丁历史 |
| `task_metadata.json` | 保存文件上下文、环境等任务元数据 | 否，不是完整对话 |

### 2.1 为什么有两份聊天历史

UI 和模型 API 的消息结构不是一回事，因此项目有两条并行记录：

```text
用户输入 / 模型流 / 工具执行
             │
             ├── ClineMessage[]
             │     └── ui_messages.json
             │         用于 ChatView 展示、恢复按钮、Checkpoint、费用和状态
             │
             └── ClineStorageMessage[]
                   └── api_conversation_history.json
                       用于组织下一次模型请求和恢复 Provider 对话
```

只读取 `ui_messages.json` 无法精确重建 Provider 消息，只读取 `api_conversation_history.json` 又无法恢复全部界面状态。做聊天导出或迁移时必须先确定目标是“人类阅读记录”还是“可继续运行的模型上下文”。

## 3. `ui_messages.json` 保存了什么

权威类型为 `apps/vscode/src/shared/ExtensionMessage.ts` 中的 `ClineMessage`：

```ts
interface ClineMessage {
  ts: number
  type: "ask" | "say"
  ask?: ClineAsk
  say?: ClineSay
  text?: string
  reasoning?: string
  images?: string[]
  files?: string[]
  partial?: boolean
  conversationHistoryIndex?: number
  conversationHistoryDeletedRange?: [number, number]
  modelInfo?: ClineMessageModelInfo
  // 另有命令、Checkpoint、工作区外操作等状态字段
}
```

其中会出现的内容包括：

- 初始任务、用户反馈、追问回答、工具批准或拒绝后的补充内容；
- 模型文本和显式 reasoning；
- 图片 Data URL、用户选择的文件路径；
- Tool Use 的 UI 描述、Tool Result 摘要；
- 命令、命令输出、浏览器动作、MCP 调用状态；
- API 请求状态、Token、费用、模型信息和错误；
- Task/Tool Hook 的界面消息、取消与完成状态；
- Checkpoint Hash、回退点、上下文删除范围等控制信息。

`MessageStateHandler.addToClineMessages()`、`updateClineMessage()` 和 `deleteClineMessage()` 都会保存整个数组。`say(..., partial: true)` 不是不断追加新记录，而是持续更新最后一条 partial 消息，所以磁盘上通常只能看到某一时刻的聚合值，不能恢复每个流式 chunk 的到达时间。

## 4. `api_conversation_history.json` 保存了什么

权威类型为 `apps/vscode/src/shared/messages/content.ts` 中的 `ClineStorageMessage`。消息角色是 `user` 或 `assistant`，内容可以是字符串或以下内容块：

| 内容块 | 含义 |
| --- | --- |
| `text` | 用户或模型文本，可带 `reasoning_details`、`signature`、`call_id` |
| `image` | Base64 图片 |
| `document` | Provider 支持的文档内容块 |
| `tool_use` | 模型发起的工具名、ID 和参数 |
| `tool_result` | 对应 Tool Use ID 的工具结果和错误信息 |
| `thinking` | Provider 返回的显式推理，可带签名、摘要或调用 ID |
| `redacted_thinking` | Provider 返回的加密或删减推理数据 |

消息自身还可带：

- `id`、`ts`；
- 生成该消息时的 `modelInfo`；
- Token、缓存和费用等 `metrics`。

这些 Cline 扩展字段不会全部发送给每个 Provider。`convertClineStorageToAnthropicMessage()` 会根据 Provider 清理 `modelInfo`、无效 thinking、`reasoning_details`、`call_id`、`summary` 和非 thinking 签名。因此“磁盘中的规范化历史”和“某次真正发送到 Provider 的请求体”也不是完全相同的对象。

### 4.1 用户附件的保存边界

用户选择文件后，UI 历史的 `files` 主要记录文件路径；准备模型输入时，`apps/vscode/src/integrations/misc/extract-text.ts` 的 `processFilesIntoText()` 会读取文件，并包装为：

```text
Files attached by the user:

<file_content path="/absolute/path/file.ext">
提取后的文本
</file_content>
```

这意味着：

- 文本、PDF、DOCX、XLSX、IPYNB 等以“提取后的文本”进入 API 历史；
- 普通文件读取前有大小检查，提取结果还会按内容上限截断；
- Notebook 会清理输出，Excel 也有行数保护；
- 原始 PDF、Office 文件和其他二进制并未复制进任务目录；
- 如果源文件后来被修改或删除，UI 中的路径不能还原当时原文件；
- 图片一般内联 Base64，可以恢复图像字节，但不是所有文件都按图片处理。

所以，现有机制保存的是“当时给模型看的附件表示”，不是通用附件归档系统。

### 4.2 模型思考内容的保存边界

`StreamResponseHandler` 会把 Provider 返回的 reasoning/thinking 聚合到 UI `reasoning` 和 API thinking/文本扩展字段中。这里必须区分三类信息：

1. Provider 返回了可读 reasoning：可以保存并显示；
2. Provider 只返回签名、摘要、加密的 `redacted_thinking`：只能保存这些返回值；
3. Provider 在服务端内部完成但协议未返回的隐式思考：Cline 从未接收到，无法记录。

因此不能宣称聊天历史包含“大模型全部思考”。它只包含 API 明确返回的推理相关字段。即使新增转存代码，也无法从客户端补出未返回的 Chain of Thought。

### 4.3 工具调用结果是否完整

工具名、参数、Tool Use ID、结果和错误通常会进入 API 历史，同时生成 UI 消息。但“进入历史的结果”可能已经是处理后的值：

- `MAX_CONTENT_SIZE_BYTES` 为 400 KB，文件内容及部分响应会截断；
- Standalone Terminal 的完整输出缓冲上限为 1 MB，超限后保留后半段；
- 单次未取 Terminal 输出超过 500 行时只保留前 100 行和后 100 行；
- MCP/Browser 返回的图片可转为图片块，但不保证所有二进制资源都原样内联；
- Handler 可以主动摘要、格式化错误或只把适合模型阅读的字段放进 Tool Result；
- 用户拒绝工具后，历史保存的是拒绝及反馈，不存在从未执行的真实结果。

如果业务要求保存命令完整 stdout/stderr 或 MCP 原始二进制，必须在 Terminal/MCP 的数据源边界旁路归档，不能等到 Tool Result 生成后再导出。

## 5. VS Code 扩展如何写盘、覆盖和回退

`apps/vscode/src/core/storage/disk.ts` 的 `saveClineMessages()` 与 `saveApiConversationHistory()` 都写入完整 JSON 数组，使用：

```text
目标路径.tmp.<timestamp>.<random>.json
           ↓ fs.writeFile
           ↓ fs.rename
目标路径
```

这种临时文件加 rename 的方式可避免多数场景下读到半个 JSON 文件。API 历史还会调用 `syncWorker().enqueue(taskId, fileName, data)` 异步进入远程同步队列；UI 历史没有走这条 API 历史同步调用。

但它仍有以下性质：

- 每次保存覆盖整个数组，不是 append-only；
- 保存失败会记录日志，很多调用不会因此中止任务；
- `MessageStateHandler` 用 Mutex 避免同一任务并发修改数组；
- 删除消息、恢复任务、Checkpoint 回退、压缩/摘要流程可以调用 `overwriteApiConversationHistory()`；
- 一旦覆盖，旧文件本身没有保留所有历史版本；能否恢复取决于 Checkpoint、同步端或其他备份，而不是聊天 JSON 自身。

### 5.1 上下文压缩是否会删除磁盘历史

旧式 `ContextManager` 通常通过 `conversationHistoryDeletedRange` 和 `context_history.json` 记录“后续发送给模型时应删除或替换哪些块”。`getNewContextMessagesAndMetadata()` 在请求前应用这些规则，原始 `api_conversation_history.json` 数组一般仍保留被排除的消息。

不过以下操作会真实覆盖 API 历史：

- Condense/Summarize 完成后重建历史；
- 恢复任务时去掉临时恢复消息；
- 用户删除消息或 Checkpoint 回退；
- Hook 或其他流程明确传入新数组调用 `overwriteApiConversationHistory()`。

所以“上下文窗口里看不到”不一定等于“磁盘已删除”，但也不能把 API 历史视为永不改写的原始档案。

## 6. SDK/CLI 的存储位置

新 SDK/CLI 默认使用：

```text
~/.cline/data/
├── db/
│   └── sessions.db
└── sessions/
    └── <sessionId>/
        ├── <sessionId>.json
        └── <sessionId>.messages.json
```

路径可以由以下环境变量改变：

```text
CLINE_DIR
CLINE_DATA_DIR
CLINE_DB_DATA_DIR
CLINE_SESSION_DATA_DIR
```

路径解析和 CLI 环境装配主要位于：

```text
sdk/packages/shared/src/storage/
apps/cli/src/utils/helpers.ts
sdk/packages/core/src/services/session-artifacts.ts
```

### 6.1 SQLite、Manifest 和消息文件的分工

| 存储 | 内容 |
| --- | --- |
| `sessions.db` | 会话 ID、状态、开始/结束时间、Provider、Model、cwd、标题/metadata、父子 Agent 关系、消息路径等索引数据 |
| `<sessionId>.json` | 可移植的 Session Manifest，记录状态、运行参数和 `messages_path` |
| `<sessionId>.messages.json` | 正文、工具调用、reasoning、附件表示、模型及费用数据 |

SQLite 的 `sessions` 表虽然保留 `prompt` 和若干路径字段，但它不是消息正文数据库。完整读取会话时仍需打开 `messages_path` 指向的 JSON 文件。

Subagent 与 Team Task 也会创建自己的消息工件，文件名由 `SessionArtifacts.subagentArtifactPaths()` 和 Session Graph 的 ID 解析规则生成；做导出时不能只枚举根会话的一个消息文件。

## 7. SDK/CLI 的消息文件格式

顶层结构由 `buildMessagesFilePayload()` 生成：

```json
{
  "version": 1,
  "updated_at": "2026-07-14T00:00:00.000Z",
  "agent": "lead",
  "sessionId": "session-id",
  "messages": [],
  "system_prompt": "可选的系统提示词"
}
```

`agent` 还可以是 `subagent` 或 `teammate`，子任务可带 `taskType`。每条持久化消息为 `user` 或 `assistant`，带稳定 ID，并可带 `agent`、`sessionId`、`metadata`、`modelInfo`、`metrics` 和 `ts`。

当前共享消息模型 `sdk/packages/shared/src/llms/messages.ts` 支持：

| 内容块 | 保存内容 |
| --- | --- |
| `text` | 文本和可选 thought signature |
| `image` | MIME 与 Base64 数据 |
| `file` | 绝对路径、读取时文本内容、可选 source |
| `tool_use` | ID、Provider Call ID、工具名、参数、签名 |
| `tool_result` | Tool Use ID、工具名、文本/图片/文件结果、错误标记 |
| `thinking` | reasoning 正文、签名、Call ID、details/summary |
| `redacted_thinking` | 加密/删减数据及 Call ID |

仓库中的 `sdk/packages/core/docs/messages-contract-v1.md` 描述了下游消费的最小 v1 契约，实际共享类型允许更多附件和 Provider 扩展块。编写导出器时应按“容忍未知字段”的方式解析，不能只对四种最小内容块做穷举后丢弃其余块。

### 7.1 附件处理

SDK 的用户图片会变成带 MIME 的 Base64 `image`；用户文件通过宿主加载器读取后形成含 `path` 和 `content` 的 `file` 块。与 VS Code 扩展相同：

- 消息文件保存了模型当时使用的文件文本和路径；
- 原始二进制文件没有自动复制到 Session 目录；
- 源文件被修改后，路径指向的当前文件可能与当时内容不同；
- 工具输出在更早阶段被限制后，消息文件只能保存受限后的结果。

## 8. SDK/CLI 的持久化时机和覆盖语义

主要链路为：

```text
AgentRuntime
  ├── 生成 message-added / assistant-message / turn-finished 等事件
  └── 内存 messages[]
          ↓ LocalRuntimeHost / AgentEventBridge
UnifiedSessionPersistenceService.persistSessionMessages()
          ↓ SessionManifestStore.persistSessionMessages()
<sessionId>.messages.json
```

持久化发生在多个保护点：

- 创建会话时先建立空消息文件；
- Assistant Message 事件后异步触发一次保存；
- Turn 成功结束后写入带模型和用量元数据的消息；
- Turn 失败时也尝试保存当前内存消息；
- 初始消息、Subagent、Team Task 和状态收尾路径也会保存。

`SessionManifestStore.persistSessionMessages()` 使用 `writeFileSync(path, contents, "utf8")` 覆盖整个文件。它不是 JSONL，也没有 VS Code `atomicWriteFile()` 的临时文件加 rename 保护。当前代码可以把消息文件上传到可选的 `messagesArtifactUploader`，但本地文件仍是可变快照。

### 8.1 运行时事件不等于持久化事件日志

新 `AgentRuntimeEvent` 包含：

```text
run-started / run-finished / run-failed
turn-started / turn-finished
message-added / assistant-message
assistant-text-delta / assistant-reasoning-delta
tool-started / tool-updated / tool-finished
usage-updated / status-notice
```

这些事件适合实时 UI 和扩展 Hook，但默认没有被逐条追加到通用事件文件。尤其是 `RuntimeEventAdapter` 为兼容旧 `AgentEvent`，会故意丢弃 `run-started` 和 `message-added`，并把 delta 投影为旧式 `content_start`。Core Event Bus 负责广播，不自动提供可回放的 append-only 日志。

`hooks.jsonl` 保存 Hook/可观测性信息，官方契约也明确它不是完整会话回放所需的聊天文件，不能把它当成全量聊天记录。

## 9. SDK/CLI 的截断、压缩和恢复边界

这里有两个不同层次：

1. `MessageBuilder.buildForApi()` 可以对“即将发送给 Provider 的副本”执行 Tool Result 截断、过期文件内容改写等操作；这通常不会直接修改原始会话数组；
2. `prepareTurn` 的 Context Compaction 可以返回替换后的 messages，`AgentRuntime` 会把 `this.state.messages` 换成压缩结果，后续持久化会覆盖消息文件。

因此：

- 仅用于 API 的截断，不一定破坏当前持久化原文；
- Executor 在产生 Tool Result 前就截断的内容，永远不会出现在消息原文中；
- Context Compaction 替换运行时消息后，压缩前正文可能从 `*.messages.json` 永久消失；
- Checkpoint Restore 可以裁剪消息数组并写出新的会话/消息状态；
- 若要审计压缩前历史，必须在 `prepareTurn` 替换内存数组之前另行追加记录。

## 10. 对“是否全部记录”的逐项回答

### 10.1 用户发送的所有消息

正常进入 Task/Session 的用户文本会记录。排队、steer、批准反馈等输入最终被消费后也会形成消息；但客户端崩溃前仍停留在临时 UI 状态或队列、尚未进入消息状态的输入，不存在强一致性保证。

### 10.2 所有附件

不会保存所有附件原件。图片通常内联，普通文件通常是“路径 + 提取文本”。需要合规归档附件时，应复制原文件并计算 SHA-256，而不是只依赖聊天历史中的路径。

### 10.3 大模型思考和输出

最终文本和 Provider 显式返回的 thinking/reasoning 会保存；流式 delta 通常不逐条保存；Provider 未返回的内部思考绝对无法记录。产品文案应使用“显式推理输出”，不要使用“模型全部思维过程”。

### 10.4 工具调用和结果

模型可见的 Tool Use 与 Tool Result 通常会保存，并可通过 ID 配对；工具运行器内部日志、完整 stdout/stderr、每个进度更新、原始网络响应与二进制资源并不保证完整。审计级需求必须在各工具执行边界另设 Recorder。

### 10.5 未被记录的中间过程

至少包括：

- Provider 内部未返回的 Chain of Thought；
- 原始 HTTP/SSE chunk、Header、重试握手和 Provider 服务端日志；
- 未开启专门抓取时的每一个 text/reasoning delta 时间点；
- UI partial 消息的全部历史版本；
- 工具底层输出被截断前的部分；

## 12. 最终判断

现有存储适合“恢复会话、继续调用模型、展示聊天 UI 和统计用量”，不适合直接承担“全量、不可篡改、逐事件、包含原始附件与工具底层 I/O 的审计归档”。若改造目标是后者，应新增独立的 append-only Transcript Recorder，并在消息被聚合、截断、压缩和覆盖之前采集；具体改造方案见 `10-聊天记录转存.md`。
