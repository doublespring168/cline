# Cline 快速熟悉与改造指南

> 目标不是一次读完数千个文件，而是在不破坏分层、Hub、事件兼容和双实现边界的前提下，尽快建立可验证的改造闭环。

## 1. 开始前先建立正确认知

### 1.1 这是两个开发域

| 开发域 | 包管理/构建 | 主要目录 | 适合改什么 |
| --- | --- | --- | --- |
| 新 SDK 工作区 | Bun workspace | `sdk/packages`、`apps/cli`、`apps/cline-hub`、`apps/examples` | 跨宿主 Core、CLI、Hub、SDK |
| 正式 VS Code 扩展 | 独立 npm 工程 | `apps/vscode`、`apps/vscode/webview-ui` | Marketplace 扩展和历史 UI/Task 内核 |

不要因为两边都出现 `core`、Provider、MCP、Tool 就认为它们是同一实现：

- `sdk/packages/core` 是新共享运行时；
- `apps/vscode/src/core` 是正式扩展当前仍使用的历史业务内核；
- `apps/examples/vscode` 才是使用新 Core 的示例扩展。

### 1.2 先回答“目标宿主是谁”

任何需求开始前先写下：

1. 只改 SDK API？
2. 只改 CLI？
3. 只改 Hub Dashboard？
4. 只改正式 VS Code？
5. 还是要求所有宿主行为一致？

这个答案决定是否需要双改。未确认入口就开始编码，是本仓库最容易产生“代码改了但产品没变化”的原因。

## 2. 推荐阅读顺序

### 2.1 第一轮：30 分钟建立地图

按顺序阅读：

1. 根 `package.json`：工作区、构建和测试命令；
2. `sdk/AGENTS.md`：包边界和改动归属；
3. `sdk/ARCHITECTURE.md`：RuntimeHost、Hub 和设计缝；
4. 五个 SDK `package.json`：实际发布依赖；
5. `apps/cli/package.json`、`apps/cline-hub/package.json`；
6. 若目标为 VS Code，再读 `apps/vscode/package.json` 和 `CONTRIBUTING.md`。

第一轮只需要回答：入口在哪、谁依赖谁、如何验证。

### 2.2 第二轮：沿最小运行链读源码

新 SDK/CLI 主链：

## 3. 本地环境与最小验证

### 3.1 SDK/CLI/Hub

仓库要求 Bun `1.3.13`、Node.js `>=22`。按 `sdk/AGENTS.md`，SDK 相关命令从 `sdk/` 工作区上下文执行：

```bash
cd sdk
bun install --frozen-lockfile
bun run build:sdk
```

常用命令：

```bash
# 包级测试
bun -F @cline/shared test
bun -F @cline/llms test
bun -F @cline/agents test
bun -F @cline/core test:unit
bun -F @cline/cli test:unit

# 跨包检查
bun run types
bun run test
bun run check

# 交互 CLI
bun run cli
```

注意：根 workspace 配置位于仓库根 `package.json`；在 `sdk/` 运行时 Bun 会使用该上级 workspace。

### 3.2 正式 VS Code

```bash
cd apps/vscode
npm run install:all
npm run protos
npm run check-types
npm run test:unit
npm run dev
```

然后用仓库的 VS Code Launch 配置按 `F5` 启动 Extension Development Host。UI 改动还应运行 Webview 测试/Storybook；端到端行为用 Playwright 和 VS Code Test Electron。

### 3.3 不要一上来跑最重测试

建议顺序：

```text
相关单测
→ 相关包 typecheck
→ 相关包 build
→ 一个真实最小路径
→ 跨包 types/test
→ 高风险时才跑完整 E2E
```

这样能更快定位是业务错误、包产物过期，还是环境问题。

## 4. 第一个可运行闭环

### 4.1 新 Core 最小闭环

优先使用 `apps/examples/quickstart` 或 `apps/examples/cline-core-cli-agent`：

1. 构建 SDK；
2. 配置一个 Provider；
3. 启动 `ClineCore.create({ backendMode: "local" })`；
4. 开一个只读任务；
5. 订阅事件；
6. 确认文本、工具、usage、完成原因；
7. 再切换 `hub`/`auto` 验证传输一致性。

### 4.2 CLI 最小闭环

```bash
bun run cli -- --help
bun run cli -- --json "只读取 package.json 并总结，不修改文件"
```

再进入 TUI 检查相同任务。Headless 正常但 TUI 异常，多半是事件/UI 层；两者都异常，继续向 Core/Agent 追踪。

### 4.3 VS Code 最小闭环

1. Extension Host 激活；
2. Webview `ready`；
3. 创建 Task；
4. 使用 Mock/低风险 Provider；
5. 执行只读工具；
6. 检查 Proto 消息、Controller、Task、UI 四层。

## 5. 改造需求的放置决策

```mermaid
flowchart TD
    Start[新需求]
    SharedQ{是否是跨包契约/低层通用能力?}
    ModelQ{是否是模型/Provider 特有?}
    LoopQ{是否改变无状态 Agent 循环?}
    StateQ{是否涉及会话/存储/工具/扩展/Hub?}
    HostQ{是否仅宿主 UI/OS 能力?}

    Start --> SharedQ
    SharedQ -->|是| Shared[@cline/shared]
    SharedQ -->|否| ModelQ
    ModelQ -->|是| Llms[@cline/llms]
    ModelQ -->|否| LoopQ
    LoopQ -->|是| Agents[@cline/agents]
    LoopQ -->|否| StateQ
    StateQ -->|是| Core[@cline/core]
    StateQ -->|否| HostQ
    HostQ -->|CLI| CLI[apps/cli]
    HostQ -->|Hub Web| Hub[apps/cline-hub]
    HostQ -->|VS Code| VS[apps/vscode]
```

### 5.1 典型错误放置

- 在 `shared` 中启动网络/进程；
- 在 `agents` 中写 SQLite 或加载用户配置；
- 在 `core` 中写只适用于 VS Code 的 API；
- 在 CLI 中直接改 Core 设置文件；
- 在 `ClineCore` 顶层根据 Hub/Local 分支业务逻辑；
- 在多个 Provider 中复制相同路由判断；
- 为了一个 UI 字段修改不可序列化的 RuntimeHost 输入。

## 6. 常见改造路径

### 6.1 新增或修改 Provider

建议顺序：

1. 在 `@cline/shared` 确认是否需要新增通用 Provider/Model 类型；
2. 在 `llms/src/providers/builtins.ts` 增加/修改 Manifest、配置字段和 metadata；
3. 在 `llms/src/providers/vendors/` 或工厂注册实现；
4. 在 `routing/` 处理特定 wire format；
5. 在 `catalog/` 增加稳定模型事实或生成数据；
6. 在 `registry/gateway` 测试默认模型、禁用、自定义模型、未知模型；
7. 验证 Core Provider Settings；
8. 验证 CLI/Hub 模型选择；
9. 若正式 VS Code 也必须支持，再改 `apps/vscode/src/core/api/providers/` 和对应 Webview Provider 组件。

必测边界：无 Key、错误 Key、自定义 Base URL、模型不存在、推理参数、Prompt Cache、流中断、usage 和取消。

### 6.2 新增内置工具

完整改造清单：

1. 在 `extensions/tools/schemas.ts` 定义输入；
2. 在 `types.ts` 定义 Executor Port；
3. 在 `definitions.ts` 定义名称、描述、Schema、超时、重试和生命周期；
4. 在 `executors/` 提供默认实现；
5. 在 `runtime.ts`/工具列表中装配；
6. 在 `presets.ts` 和 `model-tool-routing.ts` 确认各模式可用性；
7. 在 Tool Policy/Approval 中定义默认风险；
8. 检查 Hub 模式是否需要客户端 Capability Executor；
9. 添加执行器、定义、审批、超时、Abort 和输出上限测试；
10. 添加 CLI/Hub UI Tool Event 展示；
11. 如需正式 VS Code 同步，增加对应 `ToolHandler` 和 Webview 渲染。

工具的名称和 Schema 是模型协议的一部分，修改已有工具要考虑会话恢复和兼容 Prompt。

### 6.3 新增 Plugin 能力

1. 在共享 Manifest/Contribution 类型中定义能力；
2. 更新 Loader 的校验与诊断；
3. 更新 Sandbox API 和 Bootstrap 序列化；
4. 在 RuntimeBuilder 合并贡献；
5. 更新 Plugin 安装/卸载和设置投影；
6. 添加恶意/无权限插件的负面测试；
7. 更新 `sdk/examples/plugins/` 示例。

不要让插件通过未声明能力访问敏感宿主对象。

### 6.4 新增 MCP 行为

重点检查 `config-loader → manager → client/transport → tools projection → policy/approval → shutdown` 全链路。MCP 连接可能是 stdio、SSE 或 Streamable HTTP，OAuth 和断线重连也属于功能的一部分。

### 6.5 修改会话或历史

1. 修改共享/核心 Session 类型；
2. 更新 SQLite Schema/Migration；
3. 更新 File Fallback；
4. 更新 Manifest/Artifact 序列化；
5. 更新 `LocalRuntimeHost`；
6. 更新 Hub `session.*` command/reply 和事件投影；
7. 更新 CLI History/Export；
8. 更新 Dashboard Session Summary；
9. 测旧数据升级、死会话 Reconcile、删除和恢复。

只改 Store 类型而不做迁移，会让已有用户数据库直接失败。

### 6.6 修改事件

必须沿三层检查：

```text
AgentRuntimeEvent
→ RuntimeEventAdapter
→ AgentEvent
→ CoreSessionEvent
→ Hub Frame / CLI JSON / TUI / Dashboard / Telemetry
```

还要检查 Tool duration、usage delta、文本/推理结束事件等状态型转换。事件顺序是 UI 协议，不只是内部实现。

### 6.7 修改 Hub

至少验证：

- `local`、`hub`、`remote`、`auto` 四模式；
- 无 Hub、旧版本 Hub、显式端点；
- 并发启动锁；
- Discovery 写入/清理；
- Auth Token；
- 重连和客户端 detach；
- 会话持续运行；
- client-owned capability；
- daemon 停止和进程清理。

不要为了方便绕过 owner-scoped discovery 或令牌校验。

### 6.8 修改自动化

完整链是：共享 Spec 类型、Parser、Reconciler、Store、Materializer/EventIngress、Runner、Report、Hub Command、CLI、Dashboard。重点测试：

- 时区和 Cron 边界；
- 文件删除/非法 Spec；
- Revision 更新；
- Dedupe/Cooldown；
- 并发和 Lease 过期；
- Runner 重启；
- 超时中止；
- 报告与 Session 关联。

### 6.9 修改多智能体

要区分临时 Sub-agent 和持久 Team。检查：

- 父/子 Session 图；
- Agent/Conversation/Team ID；
- 工具和 Skill 继承；
- TeamStore 恢复；
- Mailbox/Task Board/Mission Log；
- Lead Completion Guard；
- Teammate 事件投影；
- 根用量与 Aggregate 用量。

### 6.10 修改 CLI/TUI

业务逻辑尽量留在 Core，CLI 层只做：

- Commander 参数与校验；
- 配置归一化；
- Runtime 生命周期；
- OpenTUI 状态和展示；
- 宿主审批、终端、连接器。

修改启动路径时保留“先渲染首帧，再后台预热 Hub/历史”的性能约束。

### 6.11 修改正式 VS Code

先判断调用入口：

```text
Webview 操作
→ generated gRPC client / message
→ WebviewProvider 或 service handler
→ Controller
→ Task/Integration/StateManager
→ VS Code HostProvider
```

若改 `.proto`：

1. 修改 `apps/vscode/proto/`；
2. `npm run protos`；
3. 更新 Host Handler；
4. 更新 Webview Client；
5. 更新测试；
6. 禁止手工编辑生成文件代替改 Proto。

若改工具，还要检查 AutoApproval、Hook、Diff、Checkpoint、消息渲染和 Standalone Host Bridge。

## 7. 搜索和追踪代码的方法

### 7.1 从用户动作反查

常用命令：

```bash
# 查 CLI 命令
rg '\.command\(' apps/cli/src

# 查工具名
rg 'name: "工具名"|toolName === "工具名"' sdk apps

# 查事件生产者和消费者
rg 'type: "事件名"|case "事件名"' sdk apps

# 查 Hub 命令
rg 'session\.|settings\.|schedule\.' sdk/packages/core/src/hub apps

# 查 VS Code RPC
rg '^service |^  rpc ' apps/vscode/proto
```

### 7.2 从接口找所有适配器

优先找：

- `implements RuntimeHost`；
- `implements SessionStore`；
- `AgentTool` 创建点；
- `subscribe(` 和事件 `case`；
- Hub Command Handler 注册；
- Proto RPC Handler；
- `package.json` exports。

接口变更必须先列出所有实现，再动类型，否则很容易漏 Hub/Remote 或测试 Fake。

### 7.3 从测试理解边界

本项目测试与实现同目录，测试名常直接说明隐含约束。优先阅读：

- 目标文件的 `*.test.ts`；
- `runtime-parity.test.ts`；
- Hub `boundary/auth/reconnect` 测试；
- Store migration/恢复测试；
- Tool timeout/abort/policy 测试；
- VS Code `src/test/e2e`。

## 8. 调试建议

### 8.1 固定 Backend

诊断 Core 时显式设置 `backendMode: "local"` 或 `"hub"`，不要先用 `auto`。`auto` 的回退可能让问题看似消失。

### 8.2 打开开发构建

设置 `CLINE_BUILD_ENV=development` 可为 Hub、Hook Worker、Plugin Sandbox、Connector 子进程启用 Source Map/Inspector。可用 `CLINE_DEBUG_HOST`、`CLINE_DEBUG_PORT_BASE` 固定各角色端口。

### 8.3 同时观察三类输出

1. 宿主结构化日志；
2. Agent/Core 事件流；
3. SQLite/Artifact 最终状态。

只看 UI 容易把事件丢失误判为业务未执行，只看数据库又会漏流式和审批问题。

### 8.4 清楚进程拓扑

一次 CLI 操作可能涉及：

- CLI 主进程；
- Hub Daemon；
- Plugin Sandbox；
- Hook Worker；
- Connector Child；
- MCP Server 子进程。

确认日志属于哪个 PID/角色，并在测试结束时检查是否清理。

## 9. 验证矩阵

| 改动类型 | 最小测试 | 扩展验证 |
| --- | --- | --- |
| shared 类型/Schema | `@cline/shared` test + typecheck | 所有 SDK 包 types |
| Provider | `@cline/llms` unit/VCR | Core + CLI Headless；必要时 live |
| Agent 循环 | `@cline/agents` test | Core runtime parity、CLI |
| Core 会话/工具 | `@cline/core test:unit` | Core E2E、CLI Headless |
| Hub | Hub/Core 定向测试 | local/hub/remote 手工闭环 |
| Cron | Cron Store/Runner/Service 测试 | CLI schedule + Hub |
| CLI 命令/TUI | CLI unit | CLI E2E/TUI Test |

```bash
cd sdk
bun run check
```

## 10. 主要风险清单

### 10.1 SDK `dist` 过期

CLI 构建会打包已编译 `dist`，不是直接读取兄弟包 TypeScript。编辑 SDK 后若不先 `bun run build:sdk`，CLI 可能仍运行旧实现。

### 10.2 双实现漂移

Provider、工具、MCP、Prompt 和上下文在新 Core 与正式 VS Code 中都有实现。产品需求若要求一致，需要显式列出两边变更；否则应在说明中限定宿主。

### 10.3 事件兼容

旧 UI 消费 `AgentEvent`，新 Agent 产生 `AgentRuntimeEvent`。删除看似冗余的 Adapter 逻辑可能造成流式文本、Tool Finish 或费用显示回归。

### 10.4 不可序列化配置

Local 模式可以接受函数，但 Hub/Remote 必须跨进程序列化。宿主函数应放入 Capability/Executor 反向通道，不要塞进通用 Runtime Config。

### 10.5 SQLite 与恢复

数据库有多个域和迁移；测试新库成功不代表旧用户库可升级。必须验证已有 Schema、Busy/Lock、进程崩溃和死会话恢复。

### 10.6 文件 Watcher 竞态

Watcher 事件只应触发重新扫描，不能把事件流本身当作真相。处理临时文件、重命名、删除和短时间多次写入时要去抖。

### 10.7 守护进程和 Discovery

不同构建、不同工作区、并发 CLI 都可能启动 Hub。不要硬编码单一端口/全局进程，也不要破坏显式端点粘性。

### 10.8 安全边界

文件编辑、命令、网络、插件、MCP 都是高权限能力。新增功能必须考虑：

- Workspace 越界；
- Shell 注入；
- Secret 泄露；
- 审批绕过；
- 超时/Abort；
- 输出和内存上限；
- Dashboard 非本地暴露；
- 插件能力最小化。

## 11. 建议的首周上手计划

### 第 1 天：结构和运行

- 构建 SDK；
- 跑 `quickstart`；
- 跑 CLI 只读 Headless 和 TUI；
- 画出一次 Session 的事件流。

### 第 2 天：Agent 和 Tool

- 阅读 `agent-runtime.ts`；
- 跟踪 `read_files` 完整链；
- 增加一个只在示例中使用的低风险自定义 Tool；
- 写单测。

### 第 3 天：Session 和 Store

- 跟踪一次 start/send/end；
- 检查 `sessions.db` 与 Artifact；
- 恢复一次 Session；
- 比较 Local 与 Hub。

### 第 4 天：扩展面

- 创建一个示例 Plugin 或 Hook；
- 配一个 MCP Server；
- 修改一条 Rule/Skill，观察 Watcher 刷新。

### 第 5 天：目标宿主

- 如果改 CLI，跟踪 TUI Event Bridge；
- 如果改 Hub，跟踪 Browser → Dashboard → Hub；
- 如果改 VS Code，跟踪 Proto → Controller → Task → Webview；
- 为真实需求写一份影响矩阵和最小测试计划。

## 12. 推荐的首个改造任务

优先选择低风险且纵向完整的任务，例如：

- 给已有工具增加一个经过 Schema 校验的可选参数；
- 为某个 Core 事件增加不破坏兼容的 metadata；
- 在 CLI/Hub UI 增加一个只读 Session 字段；
- 增加一个 Plugin 示例和测试；
- 补一个 Provider 路由的负面用例。

不建议把“新增 Provider + 新工具 + 新 Hub 协议 + VS Code UI”作为第一个任务，这会同时触碰所有高耦合边界。

## 13. 改造完成定义

一个改造只有满足以下条件才算完成：

1. 功能放在正确层，没有制造向上依赖；
2. Local/Hub/Remote 的适用范围已明确；
3. 新输入经过 Schema/边界校验；
4. Tool/Plugin/网络能力有策略、审批和清理；
5. 事件消费者和兼容层已同步；
6. 持久化变更有迁移和恢复验证；
7. 相关单测、类型检查和真实最小路径通过；
8. SDK 已重建，未误用旧 `dist`；
9. 若需求跨宿主，新 Core 与正式 VS Code 的覆盖范围已明确；
10. 修改架构/公共 API 时同步维护相应开发文档。

## 14. 最短上手路线

```text
确定目标宿主
→ 沿入口追到 ClineCore/Controller
→ 判断改动应落 shared/llms/agents/core/app 哪层
→ 阅读相邻测试
→ 做最小改动
→ 跑定向测试与 typecheck
→ 构建 SDK
→ 走一个真实纵向闭环
→ 再做跨包/跨宿主验证
```

只要始终围绕“执行入口、依赖方向、事件链、存储状态、宿主边界”五个问题推进，就可以在不通读每一行 UI 代码的前提下快速、安全地改造该项目。
