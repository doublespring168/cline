# 模型连接、通信协议与授权存储

> 本文基于当前工作区源码，分析项目能连接的模型与 Provider、实际通信协议、跨协议适配方式，以及 API Key、OAuth Token 和云凭证的存储与注入机制。项目存在两套并行实现：正式 VS Code 扩展位于 `apps/vscode`；SDK/CLI 位于 `sdk/packages/*` 与 `apps/cli`。两套实现的 Provider 注册表、默认模型、协议适配器和凭证文件都不完全相同，不能把其中一套的结论直接套到另一套。

## 1. 先给出结论

1. **“支持哪些模型”不是一个封闭的模型 ID 清单。** 项目既有内置模型元数据，也支持从 OpenRouter、LiteLLM、Ollama、LM Studio、OCA、Vercel AI Gateway 等服务动态发现模型；OpenAI-compatible 和 SDK Gateway 还允许使用未登记的自定义模型 ID。
2. **VS Code 扩展当前注册 43 个 `ApiProvider`。** 权威类型是 `apps/vscode/src/shared/api.ts`，实现分发位于 `apps/vscode/src/core/api/index.ts`。
3. **SDK/CLI 当前注册 49 个规范 Provider ID。** 权威枚举是 `sdk/packages/llms/src/providers/ids.ts`；另外接受 `openai`、`togetherai`、`sap-ai-core` 三个别名。
4. **通信协议不是只有 OpenAI 一种。** 项目同时适配 Anthropic Messages、OpenAI Chat Completions、OpenAI Responses、Gemini、AWS Bedrock、Vertex AI、Mistral、Ollama、Dify、AskSage、SAP AI Core、本地 CLI 和 VS Code Language Model API 等接口。
5. **上层智能体不直接处理各家 SDK 的事件。** VS Code 将不同响应统一为 `ApiStream`；SDK 将不同响应统一为 `AgentModelEvent`，再交给各自的 Agent Loop。
6. **当前凭证落盘主要依赖文件权限，不是应用层加密。** VS Code 的 `secrets.json` 和 SDK/CLI 的 `providers.json` 都会尽力设置为 `0600`，但内容仍是明文 JSON；同一操作系统用户权限下的其他进程仍可能读取。

## 2. 两套模型连接实现的边界

| 维度 | VS Code 正式扩展 | SDK/CLI |
| --- | --- | --- |
| Provider 权威注册表 | `apps/vscode/src/shared/api.ts` | `sdk/packages/llms/src/providers/ids.ts`、`builtins.ts` |
| 当前规范 Provider 数 | 43 | 49 |
| 创建入口 | `buildApiHandler()` / `createHandlerForProvider()` | `DefaultGateway` / `GatewayRegistry` |
| Provider 接口 | `ApiHandler` | `GatewayProviderFactory` / `AgentModel` |
| 内部消息 | `ClineStorageMessage` | `AgentMessage` |
| 统一流事件 | `ApiStreamChunk` | `AgentModelEvent` |
| 模型目录 | `shared/api.ts` + 运行时刷新 | `models.dev` 生成目录 + 运行时配置 |
| 凭证文件 | `~/.cline/data/secrets.json` | `~/.cline/data/settings/providers.json` |
| 普通设置文件 | `~/.cline/data/globalState.json` | 同一个 `providers.json` 条目中的非敏感字段 |
| OAuth 自动管理 | Cline、OCA、OpenAI Codex 等各自实现 | 统一注册 Cline、ClinePass、OCA、OpenAI Codex |

SDK 的 standalone `Agent` 与 `ClineCore` 是两种不同 API 表面，但模型连接最终都以 `@cline/llms` Gateway/Registry 为中心。`ClineCore` 还负责从持久化设置解析 Provider、刷新 OAuth 和把旧 `ApiHandler` 适配为 `AgentModel`。

## 3. “支持哪些模型”的准确含义

### 3.1 Provider、协议和模型是三个不同概念

- **Provider**：账号、网关或推理服务，例如 Anthropic、OpenRouter、AWS Bedrock、Ollama。
- **协议**：请求和流式响应的形状，例如 Anthropic Messages、OpenAI Chat、OpenAI Responses。
- **模型**：最终发送给服务的模型 ID，例如 `claude-sonnet-5`、`gpt-5.5`、`glm-5.1`。

一个 Provider 可以承载多种模型和协议。例如：

- AWS Bedrock 可以承载 Claude、Amazon Nova、Qwen、DeepSeek 等模型；
- Vertex 可以按模型走 Claude/Anthropic 或 Gemini 协议；
- OCA 会根据模型元数据在 Anthropic Messages、OpenAI Chat、OpenAI Responses 之间切换；
- OpenRouter、Requesty、LiteLLM 等路由器背后可以连接很多厂商模型；
- Ollama 和 LM Studio 的模型取决于用户本机已经安装、加载或暴露的模型。

`apps/vscode/src/shared/api.ts` 保存默认模型、上下文窗口、最大输出、图片、推理、缓存、价格和 `apiFormat` 等元数据。当前源码中的部分默认值如下：

### 3.3 SDK/CLI 的模型目录

SDK 主要使用下面的生成链路：

```text

  → sdk/packages/llms/src/catalog/catalog-live.ts
  → sdk/packages/llms/scripts/generate-models.ts
  → sdk/packages/llms/src/catalog/catalog.generated.ts
  → builtins.ts 生成 Provider Manifest
```

SDK 的默认模型不保证和 VS Code 一致。例如当前源码中：

| Provider | VS Code | SDK/CLI |
| --- | --- | --- |
| Anthropic | `claude-sonnet-5` | `claude-sonnet-4-6` |

`GatewayRegistry.resolveModel()` 找不到已登记的模型 ID 时，会用 `createUnregisteredModel()` 建立临时模型定义并继续路由。因此模型目录用于默认值、能力和价格提示，并不是硬性白名单。

## 6. 通信协议分类

### 6.1 VS Code 的 `ApiFormat`

`apps/vscode/proto/cline/models.proto` 定义了模型级协议枚举：

```text
ANTHROPIC_CHAT
GEMINI_CHAT
OPENAI_CHAT
R1_CHAT
OPENAI_RESPONSES
OPENAI_RESPONSES_WEBSOCKET_MODE
```

`apiFormat` 属于模型元数据，而不只是 Provider 元数据。这允许同一个 Provider 针对不同模型选择不同请求转换和流解析方式。

### 6.2 SDK 的语义协议与客户端类型

`sdk/packages/llms/src/catalog/types.ts` 定义的 `ProviderProtocol` 为：

```text
anthropic
gemini
openai-chat
openai-responses
openai-r1
ai-sdk
```

客户端类型为：

```text
anthropic, ai-sdk, ai-sdk-community, openai, openai-compatible,
openai-r1, gemini, bedrock, custom, fetch, vertex
```

这里的 `protocol` 表示消息和能力的语义类型，不一定等于最底层网络传输。例如 SDK 把 Bedrock 归入 `anthropic` 语义协议，但实际网络请求仍由 AWS SDK、AWS 签名和 Bedrock 服务完成。

`builtins.ts` 的默认推断规则是：

- `openai` family/client → `openai-responses`；
- `anthropic`、`bedrock` → `anthropic`；
- `google`、`vertex` → `gemini`；
- 其他 Provider 默认 → `openai-chat`；
- LiteLLM、V0、Xiaomi、Kilo 显式覆盖为 `openai-responses`；
- MiniMax 作为 Anthropic-compatible Provider；
- SDK 中 Ollama 走 `http://localhost:11434/v1` 的 OpenAI-compatible 接口，而 VS Code 使用 Ollama 原生 Chat 客户端。

### 6.3 协议与实现对照

| 协议/接口 | 请求形态 | 流式响应 | 典型 Provider |
| --- | --- | --- | --- |
| Anthropic Messages | `system`、`messages`、content blocks、tools | SSE content block events | Anthropic、MiniMax、Vertex Claude |
| OpenAI Chat Completions | role messages、`tool_calls`、`stream: true` | SSE delta | OpenAI-compatible、OpenRouter、DeepSeek、Qwen 等 |
| OpenAI Responses | `instructions`、`input`、Response tools | HTTP SSE；部分支持 WebSocket | OpenAI Native、OpenAI Codex、部分 OCA/SDK Provider |
| Gemini Generate Content | `contents`、parts、function declarations | `generateContentStream` | Gemini、Vertex Gemini、部分 AIhubmix |
| AWS Bedrock | Converse 或模型专用 Invoke payload | `ConverseStream` / `InvokeModelWithResponseStream` | Bedrock |
| Mistral Chat | Mistral messages/tools | Mistral SDK stream | Mistral |
| Ollama Native | Ollama chat messages | Async chat chunks | VS Code Ollama |
| Dify | `/chat-messages` 自定义 JSON | Dify SSE event | Dify |
| AskSage | `/query` 自定义 JSON | 普通 REST 响应 | AskSage |
| SAP AI Core | Orchestration/Foundation Models | SDK/REST stream | SAP AI Core |
| 本地 CLI | stdin/stdout JSON | `stream-json` 或社区 Provider 事件 | Claude Code、Codex CLI、OpenCode |
| IDE 进程内 API | VS Code 对象与异步流 | `vscode.lm` stream | VS Code LM |

## 7. VS Code 怎样适配不同协议

### 7.1 统一 Provider 接口

`apps/vscode/src/core/api/index.ts` 定义：

```ts
interface ApiHandler {
  createMessage(
    systemPrompt: string,
    messages: ClineStorageMessage[],
    tools?: ClineTool[],
    useResponseApi?: boolean,
  ): ApiStream
  getModel(): ApiHandlerModel
  getApiStreamUsage?(): Promise<ApiStreamUsageChunk | undefined>
  abort?(): void
}
```

`createHandlerForProvider()` 根据 `apiProvider` 创建具体 Handler。Task 层只依赖 `ApiHandler`，不需要知道底层是 Anthropic SDK、OpenAI SDK、AWS SDK、HTTP fetch、WebSocket 还是本地进程。

### 7.2 统一内部消息

对话历史使用 `apps/vscode/src/shared/messages/content.ts` 中的 `ClineStorageMessage`。其内容块以 Anthropic 风格的结构化消息为基础，可以表达：

- 文本和图片；
- 推理/思考块及签名；
- `tool_use`；
- `tool_result`；
- Provider 响应关联信息。

各协议在发送前使用自己的转换器：

| 目标协议 | 主要转换器 |
| --- | --- |
| Anthropic | `transform/anthropic-format.ts` |
| OpenAI Chat | `transform/openai-format.ts` |
| OpenAI Responses | `transform/openai-response-format.ts` |
| Gemini | `transform/gemini-format.ts` |
| Mistral | `transform/mistral-format.ts` |
| Ollama | `transform/ollama-format.ts` |
| R1/Think 标签模型 | `transform/r1-format.ts` |
| VS Code LM | `transform/vscode-lm-format.ts` |

### 7.3 统一返回流

`apps/vscode/src/core/api/transform/stream.ts` 将返回值归一为四类：

```text
text       可展示文本增量
reasoning  可记录/展示的推理增量
tool_calls 原生工具调用增量或完整调用
usage      输入、输出、缓存、推理 Token 与费用
```

OpenAI 的工具参数可能跨多个 delta 到达，`transform/tool-call-processor.ts` 负责按调用 ID 拼接函数名和 JSON 参数。Anthropic Messages 和 OpenAI Responses 的流事件分别由 `utils/messages_api_support.ts`、`utils/responses_api_support.ts` 转成相同的 `ApiStreamChunk`。

### 7.4 完整主链

```text
ClineStorageMessage
  → buildApiHandler() 选择 Provider Handler
  → Provider-specific message/tool transform
  → SDK / HTTP SSE / WebSocket / CLI / IDE API
  → Provider-specific stream parser
  → ApiStream(text/reasoning/tool_calls/usage)
  → Task 记录、界面展示、工具执行和下一轮模型请求
```

## 8. SDK/CLI 怎样适配不同协议

### 8.1 Gateway 与 Registry

核心链路为：

```text
AgentMessage / GatewayStreamRequest
  → DefaultGateway.stream()
  → GatewayRegistry.resolveModel()
  → GatewayRegistry.createProvider()
  → builtins-runtime.ts 按 family 延迟加载工厂
  → AI SDK Provider / 社区 Provider
  → streamText().fullStream
  → AgentModelEvent
  → AgentRuntime / ClineCore / CLI
```

`GatewayRegistry` 负责：

- 注册内置或自定义 Provider Manifest；
- 合并默认配置与运行时覆盖；
- 合并内置模型和用户自定义模型；
- 解析默认模型；
- 为未登记模型生成临时定义；
- 延迟加载实际 Provider 工厂。

### 8.2 AI SDK Provider 层

`sdk/packages/llms/src/providers/builtins-runtime.ts` 按 family 选择工厂，主要依赖：

```text
@ai-sdk/anthropic
@ai-sdk/openai
@ai-sdk/openai-compatible
@ai-sdk/google
@ai-sdk/google-vertex
@ai-sdk/amazon-bedrock
@ai-sdk/mistral
```

社区 Provider 包括：

```text
ai-sdk-provider-claude-code
ai-sdk-provider-codex-cli
ai-sdk-provider-opencode-sdk
dify-ai-provider
@jerome-benoit/sap-ai-provider
```

### 8.3 消息、工具和流事件归一化

`sdk/packages/llms/src/providers/ai-sdk.ts` 与 `sdk/packages/shared/src/llms/ai-sdk-format.ts` 完成：

- Text、Reasoning、Image、File、Tool Call、Tool Result 到 AI SDK message 的转换；
- JSON Schema 工具到 AI SDK Tool 的转换；
- Anthropic thinking signature、redacted data 的保留；
- Gemini thought signature 等 Provider 元数据的保留；
- Provider usage 字段到统一 Token/费用结构的归一化；
- Tool Call delta 的统一输出。

`streamText().fullStream` 最终映射为：

```text
text-delta
reasoning-delta
tool-call-delta
usage
finish
```

如果 Host 提供的是 VS Code 风格旧 `ApiHandler`，`sdk/packages/core/src/services/llms/apihandler-agent-model-adapter.ts` 会把 `ApiStreamChunk` 再转换为 `AgentModelEvent`，使旧 Handler 也能接入新 Agent Runtime。

## 9. 跨协议最容易出错的能力

### 9.1 工具调用

Anthropic 使用 `tool_use/tool_result`，OpenAI Chat 使用 `tool_calls/tool_call_id`，Responses 使用独立 Response Item，Gemini 使用 function call/response part。适配层必须同时保证：

- 工具名称一致；
- 调用 ID 与结果 ID 一致；
- JSON 参数跨流分片后仍可解析；
- 多个并行工具调用不会互相串线；
- 工具结果中的图片在不支持多模态 tool message 的 Provider 上被拆分或降级。

### 9.2 推理内容

不同服务可能返回明文 reasoning、summary、`<think>` 标签、签名块或加密内容。代码会尽可能保留 Provider 要求回传的签名和 redacted data，但不能假设每个模型都公开完整内部推理。统一事件中的 `reasoning` 只表示 Provider 实际返回、且适配层能够识别的内容。

### 9.3 图片和文件

Anthropic、OpenAI、Gemini 对图片 URL、Base64、MIME 和工具结果图片的结构不同。VS Code 使用各 transform 文件转换；SDK 使用 AI SDK formatter 和 `split-tool-images` 中间件进行兼容。

### 9.4 Token 与费用

各家字段名可能是 `prompt_tokens`、`input_tokens`、cache read/write、reasoning tokens 或 Provider 自带 cost。适配层统一为输入、输出、缓存和总费用；订阅型 Provider 如 OpenAI Codex/Claude Code 不一定能给出真实按 Token 价格，代码可能隐藏费用或记为 0。

## 10. VS Code 的 API Key 和授权存储

### 10.1 文件位置

`apps/vscode/src/shared/storage/storage-context.ts` 当前建立：

```text
~/.cline/data/globalState.json
~/.cline/data/secrets.json
~/.cline/data/workspaces/<workspace-hash>/workspaceState.json
```

可以通过 `CLINE_DIR` 改变 `~/.cline` 根目录。

分工如下：

- `globalState.json`：Provider、Plan/Act 模型、Base URL、Region、Azure 选项、推理设置等普通配置；
- `secrets.json`：API Key、Access/Refresh Token、AWS Secret、SAP Client Secret 等；
- `workspaceState.json`：工作区级规则开关等，不是主要凭证存储。

### 10.2 Secret 内容

`apps/vscode/src/shared/storage/state-keys.ts` 的 `SECRETS_KEYS` 包含：

- Anthropic、OpenRouter、OpenAI、Gemini、DeepSeek、Qwen、Mistral 等 Provider Key；
- AWS Access Key、Secret Key、Session Token、Bedrock API Key；
- SAP AI Core Client ID/Client Secret；
- OCA Access Token 与 Refresh Token；
- Cline Account 授权数据；
- OpenAI Codex OAuth JSON；
- MCP OAuth Secret；
- 远程下发的 LiteLLM Key。

`apps/vscode/src/shared/storage/provider-keys.ts` 提供 Provider 到 Secret Key 的映射，用于设置界面判断和清理相关凭证。

### 10.3 写入机制和安全属性

`ClineFileStorage` 的行为是：

1. 内存中维护 JSON 对象；
2. 批量更新键；
3. 先写临时文件，再 `rename` 到目标文件；
4. `secrets.json` 创建时指定 `0600`；
5. `undefined` 或 StateManager 转换后的空字符串会删除该 Key。

`StateManager` 在内存中缓存全局状态、Secret 和工作区状态，并批量/防抖持久化。远程配置、会话覆盖、任务设置和全局设置有明确覆盖层级；Plan 与 Act 也可以保存不同 Provider 和模型。

必须注意：`0600` 只是“文件所有者可读写”的 POSIX 权限，`secrets.json` 本身仍是明文 JSON，没有调用系统 Keychain，也没有应用层加密。

### 10.4 从旧 VS Code SecretStorage 迁移

`apps/vscode/src/hosts/vscode/vscode-to-file-migration.ts` 会把旧 `ExtensionContext.globalState`、`workspaceState` 和 `ExtensionContext.secrets` 一次性导出到共享文件存储：

- 文件存储已有值优先，不覆盖新值；
- 全局和工作区分别使用迁移版本标记；
- 迁移后不删除旧 VS Code 数据，以支持降级到旧版扩展；
- 因而升级后的凭证可能同时存在于旧 VS Code 存储和新文件中。

## 11. VS Code 的特殊授权机制

### 11.1 Cline 与 ClinePass

当前 Cline Account 授权主要保存在 Secret `cline:clineAccountId` 中，是一个 JSON 字符串，内容包括：

```text
idToken/access token
refreshToken
userInfo
expiresAt
provider
startedAt
```

`ClineAuthProvider` 在过期前刷新并回写。请求时 `ClineHandler` 优先使用显式 `clineApiKey`，否则通过 `AuthService` 获取有效账号 Token，再调用 Cline `/api/v1` OpenAI-compatible 端点。`clineAccountId`、`clineApiKey` 还承担旧版兼容或手工配置用途；ClinePass 复用同一套账号授权。

### 11.2 OpenAI Codex OAuth

`apps/vscode/src/integrations/openai-codex/oauth.ts` 使用 Authorization Code + PKCE，凭证以 Secret `openai-codex-oauth-credentials` 的 JSON 字符串保存：

```json
{
  "type": "openai-codex",
  "access_token": "...",
  "refresh_token": "...",
  "expires": 0,
  "email": "...",
  "accountId": "..."
}
```

Token Manager 会在过期前刷新、合并新的 refresh token，并用单一 Promise 去重并发刷新。Handler 调用 `https://chatgpt.com/backend-api/codex` 的 Responses API；模型格式允许时，可连接 `wss://chatgpt.com/backend-api/codex/responses`，失败后回退 HTTP Responses。

### 11.3 OCA

OCA 使用 OIDC Authorization Code + PKCE，支持 Internal/External 两种环境。VS Code 将：

- Access Token 写入 `ocaApiKey`；
- Refresh Token 写入 `ocaRefreshToken`；
- 模式、Base URL 等普通配置写入全局设置。

请求前检查 Token，必要时刷新；模型元数据决定调用 Messages、Chat 还是 Responses API。

### 11.4 Qwen Code

Qwen Code 是一个重要例外：VS Code Handler 不使用 `StateManager` 的 Secret 作为主要 OAuth 存储，而是默认读取：

```text
~/.qwen/oauth_creds.json
```

也可通过 `qwenCodeOauthPath` 指定路径。文件包含 `access_token`、`refresh_token`、`expiry_date` 和可选 `resource_url`。Handler 会在过期前刷新，遇到 401 后再强制刷新并重试，然后调用 DashScope OpenAI-compatible Chat。

### 11.5 Claude Code

Claude Code Handler 启动本地 `claude` 子进程，并使用：

```text
--output-format stream-json
--max-turns 1
```

它让 Claude Code 自己解析本地登录/订阅凭证。代码还会从子进程环境中删除 `ANTHROPIC_API_KEY`，防止误用用户的 Anthropic API Key。因此 Cline 不保存 Claude Code 订阅凭证。

### 11.6 AWS Bedrock

Bedrock 支持多种来源：

- 手工 Access Key + Secret Key + Session Token；
- AWS Profile；
- AWS SDK 默认 Credential Chain/IAM Role；
- Bedrock Bearer API Key；
- 自定义 Region 和 Endpoint。

长期部署更适合使用 IAM Role、Profile 或短期凭证链，而不是把长期 AWS Secret 写进 `secrets.json`。

### 11.7 Azure、Google 与 SAP

- **Azure OpenAI**：可用 `openAiApiKey`，也可在 `azureIdentity` 开启时使用 `DefaultAzureCredential`；Base URL 与 API Version 属于普通配置。
- **Vertex AI**：主要依赖 Google Application Default Credentials、Service Account、Project ID 和 Region；Gemini 直连可使用 API Key。
- **SAP AI Core**：保存 Client ID/Client Secret、Token URL、Resource Group、Deployment ID 等，使用 OAuth2 Client Credentials 换取 Token，再调用 Orchestration 或 Foundation Models。
- **VS Code LM**：模型选择与授权由 `vscode.lm` 及提供模型的 VS Code 扩展管理，Cline 不直接保存其远端 Key。

## 12. SDK/CLI 的凭证存储

### 12.1 文件位置和覆盖

SDK 默认路径是：

```text
~/.cline/data/settings/providers.json
```

路径解析位于 `sdk/packages/shared/src/storage/paths.ts`：

- `CLINE_PROVIDER_SETTINGS_PATH` 可直接指定文件；
- 否则使用 `CLINE_DATA_DIR/settings/providers.json`；
- 再否则使用 `CLINE_DIR/data/settings/providers.json`；
- 最终默认根目录是 `~/.cline`。

### 12.2 数据结构

`ProviderSettingsManager` 保存的结构大致为：

```json
{
  "version": 1,
  "lastUsedProvider": "anthropic",
  "providers": {
    "anthropic": {
      "settings": {
        "provider": "anthropic",
        "model": "claude-sonnet-4-6",
        "apiKey": "..."
      },
      "updatedAt": "2026-01-01T00:00:00.000Z",
      "tokenSource": "manual"
    }
  }
}
```

`tokenSource` 取值为：

```text
manual | oauth | migration
```

单个 `settings` 可包含：

- `apiKey`；
- `auth.accessToken`、`refreshToken`、`expiresAt`、`accountId`；
- `model`、`protocol`、`client`、`baseUrl`、`headers`；
- reasoning、timeout、context/output limit；
- AWS Access/Secret/Session Token、Region、Profile；
- GCP Project/Region；
- Azure Identity/API Version；
- SAP Client ID/Client Secret/Token URL；
- OCA 模式和模型目录选项。

这意味着 `providers.json` 同时保存普通设置和敏感设置，不能因为文件名不是 `secrets.json` 就把它当成可提交配置。

### 12.3 写入和迁移

`ProviderSettingsManager`：

- 创建 settings 目录时使用 `0700`；
- 写入后尽力把 `providers.json` 设置为 `0600`；
- 启动时也会修正已有文件权限；
- 会从旧 `globalState.json` 和 `secrets.json` 迁移 Provider 设置；
- 写入使用 `writeFileSync`，当前没有像 `ClineFileStorage` 那样的临时文件 + rename 原子替换。

CLI 的 API Key 配置和 OAuth 登录最终会调用该 Manager。相反，调用方直接在 `ClineCore.start({ config: { apiKey } })` 或 Gateway 运行时配置中传入的 Key，不必然持久化；只有显式保存到 `ProviderSettingsManager` 的设置才落盘。

### 12.4 Key 注入优先级

`sdk/packages/llms/src/providers/http.ts` 的解析优先级是：

```text
显式 config.apiKey
  → apiKeyResolver()
  → Provider 注册表声明的环境变量
  → undefined
```

环境变量示例包括 `ANTHROPIC_API_KEY`、`OPENAI_API_KEY`、`GEMINI_API_KEY`、`AWS_*`、`OPENROUTER_API_KEY` 等；完整列表由 `builtins.ts` 的 `apiKeyEnv` 声明。环境变量适合 CI 和短期进程注入，但仍会存在于进程环境中，并不等同于硬件或系统密钥库。

## 13. SDK/CLI 的 OAuth 刷新

### 13.1 当前统一注册的 OAuth Provider

`sdk/packages/core/src/auth/provider-auth-registry.ts` 当前只注册：

```text
cline
cline-pass  （授权存储复用 cline）
oca
openai-codex
```

不要仅凭 Provider 描述或 `oauth` capability 就断言 Core 已实现自动 OAuth。尤其是 `qwen-code`：VS Code 有独立的 `~/.qwen/oauth_creds.json` 刷新实现，但当前 SDK Core OAuth Registry 没有 Qwen Code Handler。

### 13.2 运行时刷新链路

`RuntimeOAuthTokenManager` 的流程为：

```text
从 providers.json 读取 auth
  → 找到 ProviderAuthHandler
  → 解析 access/refresh token 与过期时间
  → 同一 storageProviderId 使用 Single Flight 去重并发刷新
  → 调用 Provider 专用 refresh
  → 发生变化时写回 providers.json，tokenSource=oauth
  → 返回本次请求使用的 apiKey/access token
```

刷新失败且无法继续时抛出 `OAuthReauthRequiredError`。`LocalRuntimeHost` 在认证错误分支可以强制刷新、恢复消息基线并重试模型请求，避免失败请求把不完整中间状态永久写入会话。

Cline Token 在发请求前会规范为：

```text
workos:<access-token>
```

## 14. 远程配置和企业凭证优先级

VS Code 的 `StateManager.constructApiConfigurationFromCache()` 对普通设置采用：

```text
远程配置
  → 会话覆盖
  → 任务设置
  → 全局设置
```

LiteLLM 还有一个特殊规则：如果企业远程配置设置了 `remoteLiteLlmApiKey`，它会覆盖本地 `liteLlmApiKey`。远程下发的 Key 最终仍进入内存 Secret 缓存，并可写入当前文件 Secret 存储；改造企业配置时需要同时审计远程下发、落盘和注销清理路径。

## 15. 安全边界与改造建议

### 15.1 当前安全边界

- `secrets.json` 与 `providers.json` 都是明文 JSON；
- `0600` 能阻止其他 OS 用户直接读取，但不能阻止同一用户权限下的恶意进程；
- Windows 上 POSIX `chmod` 只是 best effort，需要依赖 NTFS ACL 和用户目录权限；
- `providers.json.headers` 若保存 `Authorization` 或自定义 Token，这些值同样明文落盘；
- Qwen Code 的 `~/.qwen/oauth_creds.json` 由该集成直接读写，不受 Cline `secrets.json` 的权限封装；
- 从 VS Code SecretStorage 迁移后，旧存储不会删除，凭证可能有两份；
- 不应把 `secrets.json`、`providers.json`、Qwen OAuth 文件或包含 Token 的调试文件提交到 Git。

### 15.2 请求抓包风险

SDK 的 Provider Request Capture 默认关闭。开启 `CLINE_CAPTURE_PROVIDER_REQUEST=full` 或 Wire Capture 后，捕获文件可能包含完整 Prompt、消息、工具参数、工具结果或请求 Body。Wire Capture 明确不记录 Headers，因此正常不会把 Authorization Header 写入捕获文件，但 Body 中由业务显式携带的 Secret 仍需自行审计。

相关说明位于 `sdk/packages/llms/src/providers/README.md` 和 `provider-request-capture.ts`。

### 15.3 推荐改造方向

如果要用于企业或生产环境，建议：

1. 用 macOS Keychain、Windows Credential Manager、Linux Secret Service 或企业 Vault 替换明文 Secret 字段；
2. 在文件中只保存 Key 引用、Credential ID 或 Secret Manager 路径；
3. 优先使用 AWS IAM Role、Google ADC、Azure Managed Identity 等短期云凭证链；
4. 对 OAuth Refresh Token 单独加密，并建立撤销、轮换和登出清理机制；
5. 给 `providers.json` 增加原子写入和备份恢复，避免进程中断导致文件损坏；
6. 禁止把 Token 放入自定义 `headers` 的普通配置导出；
7. 对日志、Telemetry、错误对象和 Provider Request Capture 做统一脱敏；
8. 将 VS Code 与 SDK 的默认模型目录和协议元数据抽成单一来源，减少两套实现漂移。

## 18. 最终判断

当前项目的模型连接层本质上是“**多 Provider 注册表 + 多协议转换器 + 统一流事件 + 分层凭证解析**”：

```text
模型目录/用户模型 ID
  → Provider 注册与配置
  → 协议/客户端选择
  → 消息、工具和推理格式转换
  → HTTP/SSE/WS/Cloud SDK/CLI/IDE API
  → 统一流事件
  → Agent Loop
```

VS Code 实现成熟且 Provider 专用 Handler 较多；SDK/CLI 正在把同类能力收敛到 Gateway、AI SDK 和统一 OAuth Registry。后续改造时，最重要的不是再增加一个 Provider 名称，而是明确它的模型目录来源、协议语义、工具/推理兼容性、凭证生命周期和安全落盘边界。
