# 模型接入实现：官方 SDK、自研适配层与直接协议

> 本文基于当前工作区源码分析模型接入的真实实现。项目同时存在两套模型运行时：VS Code 扩展使用 `apps/vscode/src/core/api` 下的 `ApiHandler`；SDK/CLI 使用 `sdk/packages/llms` 下的 Gateway。两套实现支持的 Provider 和具体客户端不完全一致，不能只查看某一个 `package.json` 后概括整个项目。

## 1. 结论：这是混合接入架构，不是三选一

当前项目并不是只采用“模型官方 SDK”“自研一套模型 SDK”或“直接 API + 通信协议”中的一种，而是分层混合使用：

| 层次 | 实现归属 | 实际做法 |
| --- | --- | --- |
| 智能体与会话层 | Cline 自研 | 管理系统提示词、历史消息、工具、上下文、重试和智能体循环 |
| 统一模型接口层 | Cline 自研 | VS Code 使用 `ApiHandler`；SDK/CLI 使用 `AgentModel`、`DefaultGateway` 和 `GatewayRegistry` |
| 消息与流适配层 | Cline 自研 | 把内部消息转换为 Anthropic、OpenAI、Gemini、Mistral、Ollama、VS Code LM 等格式，再把响应统一为内部流事件 |
| Provider 客户端层 | 混合 | 按 Provider 使用官方 SDK、Vercel AI SDK Provider、兼容协议客户端、社区 Provider、手写 Fetch/SSE/WebSocket 或本地 CLI |
| HTTP/TLS 与云鉴权底层 | 复用现有实现 | 由 Node.js、Undici、Axios、官方云 SDK和宿主 API 完成，项目没有从零实现完整网络协议栈 |

所以最准确的回答是：

1. **项目自研了“统一模型接入框架和适配层”。** 它负责 Provider 注册、模型配置、消息转换、工具调用转换、流事件归一化、用量与费用归一化等。
2. **项目没有为所有厂商重新实现一套底层模型 SDK。** Anthropic、OpenAI、AWS、Google、Mistral 等大量复用现有 SDK。
3. **部分 Provider 确实由项目直接调用 REST/SSE/WebSocket API。** Dify、AskSage 以及 OpenAI Responses 的部分路径是典型例子。
4. **还有两类不属于普通远程 API：** Claude Code 通过本地子进程接入；VS Code LM 通过进程内 `vscode.lm` 宿主接口接入。

“是否自研 SDK”需要区分两个含义：

- 如果“SDK”指 Cline 对外提供的 `@cline/sdk`、`@cline/llms`，答案是**有自研 SDK/Gateway**；
- 如果“SDK”指替代 Anthropic、OpenAI、AWS 等厂商客户端的通用网络 SDK，答案是**没有完全替代，底层仍大量复用官方或第三方实现**。

## 2. 项目为什么需要自己的适配层

不同模型接口的请求和响应并不统一。例如：

- Anthropic Messages 使用 content block、`tool_use`、`tool_result` 和 thinking block；
- OpenAI Chat Completions 使用 role message、`tool_calls` 和 delta；
- OpenAI Responses 使用 `instructions`、`input`、Response item，既可走 HTTP SSE，也可走 WebSocket；
- Gemini 使用 `contents`、part、function declaration 和 thought signature；
- Bedrock 使用 AWS 签名、Converse 或模型专用 Invoke 请求；
- Dify 使用自己的 `/chat-messages` 事件；
- VS Code LM 返回 `LanguageModelTextPart`、`LanguageModelToolCallPart` 等宿主对象。

如果智能体主循环直接依赖这些形状，上层代码会出现大量 Provider 分支。项目因此把差异隔离在 Provider 和 transform 层：

```text
智能体内部消息、系统提示词、工具
                │
                ▼
        Cline 统一模型接口
                │
                ▼
      Provider 请求格式转换
                │
                ▼
官方 SDK / AI SDK / Fetch / CLI / VS Code API
                │
                ▼
      Provider 原始流式响应
                │
                ▼
        Cline 统一流事件
                │
                ▼
     智能体循环、工具执行与界面
```

这里真正由项目自研的核心不是某一种 HTTP 客户端，而是上下两次“统一”：请求前统一内部语义，响应后统一流事件。

## 3. VS Code 扩展的模型接入实现

### 3.1 统一接口与 Provider 分发

入口位于 `apps/vscode/src/core/api/index.ts`。所有 Provider Handler 都实现：

```ts
interface ApiHandler {
  createMessage(
    systemPrompt: string,
    messages: ClineStorageMessage[],
    tools?: ClineTool[],
    useResponseApi?: boolean,
  ): ApiStream
  getModel(): ApiHandlerModel
  getApiStreamUsage?(): Promise<ApiStreamUsageChunk | undefined>
  abort?(): void
}
```

`buildApiHandler()` 根据 plan/act 模式选择 Provider，`createHandlerForProvider()` 再通过 `switch` 创建具体 Handler。当前 `apps/vscode/src/shared/api.ts` 的 `ApiProvider` 联合类型注册了 43 个 Provider。

这套实现不是一个第三方 SDK 提供的统一接口，而是 Cline 自己定义的反腐层。新增一个正式 VS Code Provider，通常必须增加 Handler、配置类型、分发分支、界面设置以及测试。

### 3.2 内部消息与统一输出

VS Code 主链路使用 `apps/vscode/src/shared/messages/content.ts` 中的 `ClineStorageMessage`。它历史上以 Anthropic `MessageParam` 为基础扩展，加入了：

- reasoning details；
- tool use/tool result；
- Gemini thought signature；
- Response ID；
- 模型信息、指标和时间戳。

以 Anthropic 类型作为存储基础，不表示所有模型都通过 Anthropic API 接入。发送前会根据目标 Provider 转换，主要转换文件包括：

```text
apps/vscode/src/core/api/transform/anthropic-format.ts
apps/vscode/src/core/api/transform/openai-format.ts
apps/vscode/src/core/api/transform/openai-response-format.ts
apps/vscode/src/core/api/transform/gemini-format.ts
apps/vscode/src/core/api/transform/mistral-format.ts
apps/vscode/src/core/api/transform/ollama-format.ts
apps/vscode/src/core/api/transform/vscode-lm-format.ts
apps/vscode/src/core/api/transform/tool-call-processor.ts
```

所有 Handler 最终返回 `apps/vscode/src/core/api/transform/stream.ts` 定义的 `ApiStream`，流块被归一为：

```text
text        文本增量
reasoning   推理/思考增量及签名、摘要等元数据
tool_calls  工具调用 ID、名称和参数
usage       输入、输出、缓存、思考 Token 和费用
```

因此，上层 `Task` 只需要调用 `this.api.createMessage(...)` 并消费统一流，不需要知道底层使用的是 Anthropic SDK、OpenAI SDK、SSE 还是 VS Code API。主调用位置可见 `apps/vscode/src/core/task/index.ts`。

## 4. VS Code 中直接使用官方或厂商 SDK 的实现

`apps/vscode/package.json` 明确依赖多种模型或云厂商客户端。典型实现如下：

| Provider | 主要依赖 | 关键调用 | 接入性质 |
| --- | --- | --- | --- |
| Anthropic | `@anthropic-ai/sdk` | `new Anthropic()`、`client.messages.create()` | Anthropic 官方 SDK |
| AWS Bedrock | `@aws-sdk/client-bedrock-runtime`、`@aws-sdk/credential-providers` | `BedrockRuntimeClient`、`ConverseStreamCommand`、`InvokeModelWithResponseStreamCommand` | AWS 官方 SDK |
| Gemini | `@google/genai` | `new GoogleGenAI()`、`models.generateContentStream()` | Google 官方 SDK |
| Vertex Claude | `@anthropic-ai/vertex-sdk` | `new AnthropicVertex()`、`beta.messages.create()` | Anthropic Vertex SDK |
| Vertex Gemini | `@google/genai` | 复用 `GeminiHandler` 的 Vertex 模式 | Google 官方 SDK |
| OpenAI/Azure OpenAI | `openai`、`@azure/identity` | `new OpenAI()`、`new AzureOpenAI()`、Chat Completions | OpenAI SDK + Azure 身份库 |
| OpenAI Native | `openai` | Chat Completions 或 Responses | OpenAI 官方 SDK，WebSocket 路径另行实现 |
| OpenAI Codex | `openai` | OAuth 后调用 Responses | OpenAI SDK为主，另有 Fetch/SSE 和 WebSocket 回退/增强路径 |
| Mistral | `@mistralai/mistralai` | `new Mistral()`、`client.chat.stream()` | Mistral 官方 SDK |
| Cerebras | `@cerebras/cerebras_cloud_sdk` | `new Cerebras()`、`chat.completions.create()` | Cerebras 厂商 SDK |
| Ollama | `ollama` | `new Ollama()`、`client.chat({ stream: true })` | Ollama JavaScript 客户端，使用原生 Chat 接口 |
| SAP AI Core | `@sap-ai-sdk/orchestration` 等 | `OrchestrationClient`，并配合部署发现和 REST 调用 | 官方 SDK 与自定义 REST 混合 |

这些 Handler 仍包含大量 Cline 自己的代码，例如：

- 把 `ClineStorageMessage` 转为厂商消息；
- 决定是否开启 thinking、prompt cache、tools；
- 解析流事件并恢复工具调用参数；
- 统一 Token 和费用；
- 接入项目的重试、代理 Header、取消信号和错误处理。

所以“用了官方 SDK”只说明客户端和部分协议序列化由官方包完成，并不意味着整个 Provider Handler 是官方提供的。

## 5. 使用官方 SDK 连接兼容接口

### 5.1 OpenAI SDK 不等于请求一定发给 OpenAI

VS Code 中大量 Provider 复用 `openai` npm 包，只替换 `baseURL`、API Key、Headers 和模型 ID，然后调用：

```ts
client.chat.completions.create({
  model,
  messages,
  stream: true,
  ...
})
```

`apps/vscode/src/shared/net.ts` 还封装了 `createOpenAIClient()`，为这些客户端统一注入平台代理 Fetch 和外部 Header。

主要采用这种方式的 Provider 包括：

```text
OpenRouter、Requesty、Together、Fireworks、Groq、DeepSeek、Baseten、
Hugging Face、LM Studio、Qwen、Qwen Code、Doubao、Moonshot、Nebius、
SambaNova、xAI、Z.AI、W&B、Vercel AI Gateway、Huawei Cloud MaaS、
HiCap、Nous Research、Cline/ClinePass
```

这里可以同时说两句话，而且都正确：

- 客户端代码使用了 OpenAI 官方 SDK；
- 实际模型接入本质是 OpenAI-compatible API + SSE 通信协议，对端不一定是 OpenAI。

因此不能依据 `import OpenAI from "openai"` 就把这些 Provider 归类为“模型厂商官方 SDK 接入”。

### 5.2 其他兼容协议复用

项目还会用一个厂商 SDK访问其他服务暴露的兼容接口：

| Provider | 复用方式 | 说明 |
| --- | --- | --- |
| MiniMax | `@anthropic-ai/sdk` + MiniMax Anthropic-compatible Base URL | 请求形状是 Anthropic Messages，但服务端是 MiniMax |
| AIhubmix | Anthropic、OpenAI、Google GenAI 三套客户端 | 根据模型格式在三种协议之间选择 |
| LiteLLM | Anthropic 或 OpenAI 客户端 | 根据模型/配置选择兼容协议 |
| OCA | Anthropic 与 OpenAI 客户端 | 根据模型元数据选择 Messages、Chat 或 Responses |
| 自定义 `openai` Provider | OpenAI/AzureOpenAI 客户端 + 用户 Base URL | 可连接 OpenAI、Azure 或其他兼容端点 |

这种复用方式减少了重复的请求序列化和 SSE 解析代码，但兼容服务与原协议存在细节偏差时，项目仍需要在 Handler 和 transform 中修正。

## 6. 直接使用 API + 通信协议的实现

部分接口没有合适的统一 SDK，或者项目需要 SDK 尚未覆盖的能力，于是直接使用 Fetch、Axios、Undici WebSocket 并自行解析响应。

### 6.1 Dify：手写 REST 与 SSE

`apps/vscode/src/core/api/providers/dify.ts` 直接调用：

```text
POST /chat-messages
POST /files/upload
POST /chat-messages/{taskId}/stop
GET  /conversations/{conversationId}/messages
GET/DELETE/POST 其他会话与反馈接口
```

`createMessage()` 设置 `response_mode: "streaming"`，随后直接读取 `response.body.getReader()`，按 Dify 事件解析 SSE。文件上传、停止生成、会话历史和反馈也由该 Handler 自己实现。这是最典型的“API + 自定义通信协议适配”。

### 6.2 AskSage：手写 REST JSON

`apps/vscode/src/core/api/providers/asksage.ts` 使用项目封装的 Fetch 调用：

```text
POST /query
POST /count-monthly-tokens
```

它自行把聊天历史转换成 AskSage 的 `message: [{ user, message }]` 结构，再把 JSON 响应映射为 `ApiStream`。该实现没有依赖 AskSage 专用 SDK。

### 6.3 OpenAI Responses：SDK 与手写协议并存

`openai-native.ts` 和 `openai-codex.ts` 不是单一接入方式：

- 普通 HTTP Responses 优先使用 `openai` SDK；
- `openai-codex.ts` 在 SDK 路径失败时会用 Fetch 直接请求 `/responses` 并手动解析 SSE；
- WebSocket 模式使用 Undici `WebSocket`，自行建立连接、发送请求、关联事件和处理重连；
- OpenAI Native 也实现了 Responses WebSocket。

这说明同一个 Provider 内也可能是混合实现，不能简单按文件归为“只用 SDK”或“只用 API”。

### 6.4 SAP AI Core：官方 SDK与辅助 REST 混合

`sapaicore.ts` 使用 `OrchestrationClient` 处理编排调用，同时使用 Axios 完成 OAuth Token、部署发现及部分 Foundation Model 请求。这里官方 SDK承担一部分高层能力，项目补齐其余控制面和协议差异。

## 7. 不经过普通模型 HTTP Endpoint 的两种接入

### 7.1 Claude Code：本地 CLI 子进程

VS Code 的 `claude-code.ts` 会调用 `apps/vscode/src/integrations/claude-code/run.ts`：

1. 使用 `execa` 启动本地 `claude` 可执行文件；
2. 传入 `--output-format stream-json` 等参数；
3. 按行读取标准输出；
4. 解析 assistant、result、usage、thinking 和 tool use；
5. 转换为 `ApiStream`。

模型授权和实际远程通信由 Claude Code CLI 自己管理，Cline 连接的是本地进程接口。

### 7.2 VS Code LM：宿主进程内 API

`apps/vscode/src/core/api/providers/vscode-lm.ts` 使用：

```ts
vscode.lm.selectChatModels(selector)
client.sendRequest(messages, options, cancellationToken)
```

模型由 VS Code 或提供 Language Model API 的扩展暴露，授权、模型发现和底层网络均由宿主管理。Cline 只把内部消息转换成 VS Code 的 `LanguageModelChatMessage`，并把响应 part 转回 `ApiStream`。

## 8. SDK/CLI 的 `@cline/llms` Gateway

### 8.1 这是 Cline 自研的模型 Gateway

SDK/CLI 主链路位于：

```text
sdk/packages/llms/src/providers/gateway.ts
sdk/packages/llms/src/providers/registry.ts
sdk/packages/llms/src/providers/builtins.ts
sdk/packages/llms/src/providers/builtins-runtime.ts
sdk/packages/llms/src/providers/ai-sdk.ts
sdk/packages/llms/src/providers/vendors/
```

`@cline/sdk` 当前入口是面向使用者的 Cline SDK 包，它转出 `@cline/core`；`@cline/core` 又暴露 `Llms` 命名空间及 Cline 的会话、Agent 和共享能力。`@cline/llms` 是其中负责模型路由的项目包，不是 Anthropic、OpenAI 等模型厂商发布的 SDK。

它定义并实现：

- `GatewayProviderManifest`：Provider、模型和能力清单；
- `GatewayProviderConfig`：API Key、Base URL、Header、Fetch 和 Provider Options；
- `GatewayProviderFactory`：Provider 创建工厂；
- `GatewayRegistry`：注册、配置、解析 Provider/模型；
- `DefaultGateway`：统一创建 `AgentModel` 并发起流式请求；
- `AgentModelEvent`：统一文本、推理、工具调用、用量和结束事件。

当前 `sdk/packages/llms/src/providers/ids.ts` 注册 49 个规范 Provider ID，并把 `openai`、`togetherai`、`sap-ai-core` 等别名规范化到内部 ID。

### 8.2 底层主要使用 Vercel AI SDK Provider

`sdk/packages/llms/package.json` 的核心依赖为：

| 类型 | 依赖 |
| --- | --- |
| 统一生成/流 API | `ai` |
| 官方维护或协议专用 Provider | `@ai-sdk/openai`、`@ai-sdk/openai-compatible`、`@ai-sdk/anthropic`、`@ai-sdk/google`、`@ai-sdk/google-vertex`、`@ai-sdk/amazon-bedrock`、`@ai-sdk/mistral` |
| CLI/社区 Provider | `ai-sdk-provider-claude-code`、`ai-sdk-provider-codex-cli`、`ai-sdk-provider-opencode-sdk` |
| 其他社区 Provider | `dify-ai-provider`、`@jerome-benoit/sap-ai-provider` |

`builtins.ts` 为每个 Provider 声明 `family`、`protocol`、默认 URL 和模型；`builtins-runtime.ts` 按 family 延迟加载对应工厂。最终 `ai-sdk.ts` 统一调用：

```ts
streamText({
  model,
  messages,
  system,
  tools,
  temperature,
  maxOutputTokens,
  providerOptions,
  abortSignal,
})
```

随后 `emitAiSdkEvents()` 把 AI SDK 的 `fullStream` 转为 Cline 的：

```text
text-delta
reasoning-delta
tool-call-delta
usage
finish
```

因此 SDK/CLI 比 VS Code 的逐 Provider Handler 更集中：多数协议差异先由 Vercel AI SDK Provider 处理，Cline 再负责统一配置、消息增强、Provider Options、工具图片兼容、推理路由、用量和错误归一化。

### 8.3 SDK/CLI 的实际分类

| 运行时 family/路径 | 典型 Provider | 底层实现 |
| --- | --- | --- |
| `openai` | OpenAI Native、OpenAI Codex，以及声明 `openai-responses` 的 LiteLLM、V0、Xiaomi、Kilo | `@ai-sdk/openai` Responses |
| `openai-compatible` | OpenRouter、DeepSeek、Together、Fireworks、Groq、Cerebras、Ollama、LM Studio、Qwen 等 | `@ai-sdk/openai-compatible` |
| `anthropic` | Anthropic、MiniMax | `@ai-sdk/anthropic`；MiniMax 使用 Anthropic-compatible Endpoint |
| `google` | Gemini | `@ai-sdk/google` |
| `vertex` | Vertex Gemini、Vertex Claude | `@ai-sdk/google-vertex`，按模型选择 Google 或 Anthropic Vertex Provider |
| `bedrock` | AWS Bedrock | `@ai-sdk/amazon-bedrock` + AWS 凭证链 |
| `mistral` | Mistral | `@ai-sdk/mistral` |
| 社区/CLI | Claude Code、Codex CLI、OpenCode、Dify、SAP AI Core | 对应社区 AI SDK Provider |

这里的 Vercel AI SDK Provider 也是第三方协议适配器，不是 Cline 自己从零实现的厂商 SDK。Cline 自研的是包在它外面的 Gateway、注册表、消息/流适配和 Agent 接口。

## 9. 两套运行时的一次完整请求链路

### 9.1 VS Code 主链路

```text
Task 准备系统提示词、工具和截断后的会话历史
  → buildApiHandler() 根据 plan/act 配置选择 Provider
  → createHandlerForProvider() 创建具体 ApiHandler
  → Handler 将 ClineStorageMessage 转成目标协议
  → 官方 SDK / OpenAI-compatible SDK / Fetch / CLI / VS Code LM 发起请求
  → Handler 读取厂商流、SSE、WebSocket、子进程输出或宿主流
  → 转成 ApiStreamChunk(text/reasoning/tool_calls/usage)
  → Task 消费流并驱动界面、消息存储和工具执行
```

源码入口：

- `apps/vscode/src/core/task/index.ts`
- `apps/vscode/src/core/api/index.ts`
- `apps/vscode/src/core/api/providers/`
- `apps/vscode/src/core/api/transform/`

### 9.2 SDK/CLI 主链路

```text
Agent/ClineCore 构造 AgentModelRequest
  → AgentRuntime 根据 providerId/modelId 创建 Gateway AgentModel
  → DefaultGateway.resolveModel() 解析 Provider 与模型元数据
  → GatewayRegistry.createProvider() 加载 Provider Factory 与配置
  → family factory 创建具体 Vercel AI SDK Provider
  → Cline 将 AgentMessage、工具和 Provider Options 转成 AI SDK 输入
  → streamText() 调用底层 Provider
  → emitAiSdkEvents() 归一化完整流
  → AgentModelEvent 返回 Agent Loop，继续工具执行或结束本轮
```

源码入口：

- `sdk/packages/agents/src/agent-runtime.ts`
- `sdk/packages/llms/src/providers/gateway.ts`
- `sdk/packages/llms/src/providers/registry.ts`
- `sdk/packages/llms/src/providers/ai-sdk.ts`
- `sdk/packages/llms/src/providers/vendors/`

## 10. Cline 自研了什么，没有自研什么

### 10.1 明确属于项目自研的部分

1. **Provider 抽象和路由**
   - VS Code：`ApiHandler`、`buildApiHandler()`、43 个 Provider 分发；
   - SDK/CLI：`DefaultGateway`、`GatewayRegistry`、Provider Manifest/Factory、49 个内置 Provider。
2. **统一消息模型**
   - VS Code：`ClineStorageMessage`；
   - SDK/CLI：`AgentMessage`、`AgentModelRequest`。
3. **跨协议转换**
   - Anthropic/OpenAI/Gemini/Mistral/Ollama/VS Code LM 格式转换；
   - thinking、tool call、tool result、图片和签名兼容。
4. **流事件归一化**
   - VS Code 的 `ApiStreamChunk`；
   - SDK/CLI 的 `AgentModelEvent`。
5. **Provider 增强能力**
   - 重试、错误映射、取消、代理 Fetch、外部 Header；
   - 模型能力和价格元数据；
   - Token/缓存/费用归一化；
   - prompt cache、reasoning、sticky session、工具图片中间件。
6. **旧接口与新 Gateway 的兼容桥**
   - `sdk/packages/llms/src/providers/compat.ts` 可在旧 `ApiHandler` 与新 Gateway 请求/事件之间转换。

### 10.2 明确不是项目从零自研的部分

- Anthropic、OpenAI、Gemini、AWS Bedrock、Mistral 等公开协议本身；
- HTTP、HTTPS、TLS、SSE、WebSocket 的底层网络实现；
- AWS SigV4、Google Cloud、Azure Identity 等完整云鉴权协议栈；
- Vercel AI SDK 的 `streamText()` 和各 `@ai-sdk/*` Provider；
- Claude Code、Codex CLI、OpenCode 等本地工具本身。

## 11. 新增模型或 Provider 时应该选择哪种方式

### 11.1 只有新模型 ID，没有新协议

优先复用已有 Provider：

- 增加模型元数据、上下文窗口、最大输出、图片/工具/推理能力；
- 如果接口是 OpenAI-compatible，只需配置 Base URL、API Key 和模型 ID；
- SDK/CLI 可在 Provider Manifest 或运行时配置中增加模型，不必新建网络客户端。

这是改动最小、维护成本最低的路径。

### 11.2 新 Provider 兼容已有协议

VS Code 可参考现有 OpenAI-compatible 或 Anthropic-compatible Handler；SDK/CLI 通常只需在 `builtins.ts` 增加 `BuiltinSpec`，选择正确的 `family`、`protocol`、默认 URL、凭证环境变量和模型来源。

不要因为服务商名称不同就复制整套协议实现。先验证：

- 消息字段是否完全兼容；
- tool call 与 tool result 是否兼容；
- 流式 usage 是否存在；
- reasoning 字段和 finish reason 是否有扩展；
- 图片和缓存控制是否支持。

### 11.3 新协议或特殊鉴权

如果现有 SDK/AI SDK Provider 无法覆盖，应新增独立适配器：

- VS Code：实现 `ApiHandler`、请求转换、流解析、`getModel()`、取消和重试，并在 `createHandlerForProvider()` 注册；
- SDK/CLI：实现新的 `GatewayProviderFactory` 或 vendor module，必要时增加 family 与 lazy loader；
- 同时补齐配置 Schema、秘密字段、模型能力、错误映射和测试。

### 11.4 依赖宿主或本地进程

SDK 提供两种扩展方式：

- `gateway.registerProvider()`：注册遵循 Gateway 接口的新 Provider；
- `registerHandler()` / `registerAsyncHandler()`：注册需要宿主依赖的旧式 Handler，再由 Core 将其适配为 `AgentModel`。

`sdk/packages/core/src/services/llms/handler-factory.ts` 明确优先检查宿主注册 Handler。VS Code LM 就适合这种路径，因为通用 `@cline/llms` 包不应硬依赖 `vscode`。

需要注意：VS Code 正式扩展的 `apps/vscode/src/core/api/index.ts` 当前仍是静态 `switch`，SDK 的动态注册机制不能自动替代这个分发文件。

## 12. 这种架构的收益与维护风险

### 12.1 收益

- Agent Loop 与具体模型厂商解耦；
- OpenAI-compatible Provider 可以大量共享实现；
- 特殊 Provider 仍能使用手写协议或宿主能力；
- 同一个上层工具系统可复用到 Anthropic、OpenAI、Gemini、Bedrock 等模型；
- SDK/CLI 可通过 Gateway 动态注册 Provider，便于二次开发。

### 12.2 风险

- VS Code 与 SDK/CLI 是两套实现，Provider 数量、默认模型和协议路径可能漂移；
- “兼容 OpenAI/Anthropic”不代表所有高级能力完全兼容；
- 官方 SDK升级可能改变事件、错误或 usage 结构；
- 手写 SSE/WebSocket 必须自行处理半包、重连、取消和错误事件；
- 同一 Provider 可能在两套运行时使用不同客户端。例如 VS Code Ollama 使用原生 `ollama` 客户端，而 SDK/CLI 将 Ollama 路由到 `/v1` 的 OpenAI-compatible Provider；
- 只修改 VS Code Handler 或只修改 `@cline/llms`，通常不能保证另一套运行时同步获得能力。

## 13. 最终判定表

| 问题 | 判定 |
| --- | --- |
| 是否直接使用模型官方 SDK？ | **是。** Anthropic、OpenAI、Google、AWS Bedrock、Mistral、Cerebras、Ollama、SAP 等均有直接使用 |
| 是否自研了一套 SDK？ | **是，但要限定含义。** 自研的是 Cline Agent SDK、`@cline/llms` Gateway、Provider 抽象和适配层，不是替代所有厂商的底层网络 SDK |
| 是否仅通过 API + 通信协议接入？ | **部分是，但不是全部。** Dify、AskSage、部分 Responses SSE/WebSocket 等为手写 API；许多其他 API 调用由 SDK封装 |
| 是否大量使用兼容协议？ | **是。** OpenAI-compatible 是覆盖 Provider 最多的共享路径，MiniMax 等还使用 Anthropic-compatible |
| 是否存在非 API 接入？ | **是。** Claude Code 使用本地 CLI，VS Code LM 使用宿主进程内 API |
| 整体应如何概括？ | **Cline 自研统一接入层，底层按 Provider 混用官方 SDK、AI SDK、兼容协议、手写通信和宿主/CLI 接口** |
