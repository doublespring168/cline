# 将 Cline 转换为可独立安装的 VS Code 插件

> 本文以把当前仓库改造成名为 **Acme Agent** 的独立插件为例。目标不是只修改界面上的名称，而是让新插件拥有独立的 Extension ID、命令、视图、回调 URI 和数据目录，能够与原版 Cline 同时安装、同时运行，并最终生成可在本地侧载的 `.vsix` 文件。

## 1. 先确定本次改造的源码边界

当前仓库包含新 SDK、CLI、Hub、示例应用和正式 VS Code 扩展等多个开发域。要生成当前产品形态的 VSIX，应改造：

```text
apps/vscode/
├── package.json                 # VS Code 扩展清单、贡献点、构建脚本
├── src/extension.ts             # Extension Host 激活入口
├── src/registry.ts              # 扩展 ID、命令 ID、视图 ID 注册表
├── src/core/                    # 当前正式扩展的任务和业务内核
├── src/hosts/vscode/            # VS Code 宿主适配
├── webview-ui/                  # React Webview 前端
├── assets/                      # 图标、字体等品牌资源
├── walkthrough/                 # VS Code 欢迎教程
├── esbuild.mjs                  # Extension Host 打包
└── .vscodeignore                # VSIX 文件包含/排除规则
```

打包链路为：

```text
apps/vscode/src/extension.ts
        │
        ├── esbuild.mjs ───────────────→ apps/vscode/dist/extension.js
        │
        ├── webview-ui 的 Vite 构建 ──→ apps/vscode/webview-ui/build/
        │
        └── @vscode/vsce + .vscodeignore ─→ acme-agent-0.1.0.vsix
```

以下内容不要混淆：

- `apps/examples/vscode` 是新 SDK 的示例扩展，不是当前正式 Cline VSIX 的源码；
- `npm run compile-standalone` 服务于 Standalone/其他宿主打包，不是生成 VSIX 的必要替代步骤；
- `sdk/packages/core` 是新共享运行时，而 `apps/vscode/src/core` 仍是正式 VS Code 扩展使用的业务内核。

如果只要求改造 VS Code 插件，先把修改限制在 `apps/vscode` 及根目录的调试/发布配置。只有在还要发布自己的 CLI、Hub 或 SDK 时，才继续改造其他工作区。

## 2. “独立插件”有三个层级

| 层级 | 修改内容 | 能否与原版共存 | 是否仍依赖 Cline 服务 |
| --- | --- | --- | --- |
| 仅换品牌 | `displayName`、描述、图标、文案 | 不一定 | 是 |
| 独立 VS Code 插件 | Extension ID、命令、视图、Context Key、URI、存储全部隔离 | 是 | 可以仍依赖 |
| 完全独立产品 | 再替换账户、API、遥测、Marketplace、文档、CLI 和发布体系 | 是 | 否 |

本地安装自己的插件，至少应完成第二层。否则可能出现以下问题：

- 与原版共用命令 ID，命令被覆盖或执行了错误扩展的处理器；
- 与原版共用 `~/.cline`，API Key、任务历史、MCP 配置互相污染；
- 登录或 OAuth 返回到 `saoudrizwan.claude-dev`，无法回到新插件；
- Activity Bar 看似已经改名，但菜单、评论操作或 Git 提交按钮失效；
- 插件仍把账号、遥测或错误上报发送给 Cline 官方服务。

## 3. 先冻结一套不可随意变化的命名

本文使用以下示例。实施时一次性替换为自己的值，并保存一份产品标识表：

| 含义 | 当前值 | 示例新值 |
| --- | --- | --- |
| 显示名称 | `Cline` | `Acme Agent` |
| 扩展包名 `name` | `claude-dev` | `acme-agent` |
| 发布者 `publisher` | `saoudrizwan` | `acme` |
| Extension ID | `saoudrizwan.claude-dev` | `acme.acme-agent` |
| 命令前缀 | `cline.*` | `acme-agent.*` |
| Activity Bar ID | `claude-dev-ActivityBar` | `acme-agent-ActivityBar` |
| Sidebar ID | `claude-dev.SidebarProvider` | `acme-agent.SidebarProvider` |
| Walkthrough ID | `ClineWalkthrough` | `AcmeAgentWalkthrough` |
| 图标贡献 ID | `cline-icon` | `acme-agent-icon` |
| 评论控制器 ID | `cline-ai-review` | `acme-agent-review` |
| Context Key 前缀 | `cline.*` | `acme-agent.*` |
| 用户数据目录 | `~/.cline` | `~/.acme-agent` |
| 数据目录环境变量 | `CLINE_DIR` | `ACME_AGENT_DIR` |
| 项目配置目录 | `.cline/`、`.clinerules/` | 兼容保留或迁移到 `.acme-agent/` |

命名时注意：

- `name` 和 `publisher` 是机器标识，不使用空格；推荐小写字母、数字和连字符；
- VS Code 最终用 `publisher.name` 识别扩展，而不是 `displayName`；
- 一旦用户开始安装，不要随意改变 `publisher` 或 `name`，否则 VS Code 会把它当成另一个扩展；
- 本地安装 VSIX 时，`publisher` 不要求已经在 Marketplace 注册；将来公开发布时才需要创建相同名称的 Publisher。

## 4. 建立安全的改造分支

先保留可持续同步上游的 Git 历史：

```bash
git switch -c product/acme-agent
git remote rename origin upstream
git remote add origin <你的仓库地址>
```

如果当前仓库已经有自己的 `origin`，只需要创建分支，不要机械执行远程重命名。建议让 Cline 上游保持为 `upstream`，以后用独立提交分层维护：

```text
上游同步提交
→ 产品身份/品牌提交
→ 存储与服务隔离提交
→ 自己的业务功能提交
```

仓库使用 Apache-2.0 许可证。改名和二次开发时应保留原 `LICENSE`、原版权声明和适用的归属信息；同时替换 Cline Logo、头像和可能造成“官方版本”误解的商标素材。是否需要额外 `NOTICE` 应根据实际分发内容和法务要求确认。

## 5. 修改扩展的基础身份

编辑 `apps/vscode/package.json`。至少修改这些字段：

```json
{
  "name": "acme-agent",
  "displayName": "Acme Agent",
  "description": "你的插件描述",
  "version": "0.1.0",
  "icon": "assets/icons/icon.png",
  "author": {
    "name": "你的个人或公司名称"
  },
  "license": "Apache-2.0",
  "publisher": "acme",
  "repository": {
    "type": "git",
    "url": "https://github.com/acme/acme-agent"
  },
  "homepage": "https://example.com/acme-agent",
  "main": "./dist/extension.js"
}
```

其中 `main` 和 `engines.vscode` 不应因改名而删除。当前运行入口就是 `./dist/extension.js`。

还要同步处理：

- `keywords` 中的旧品牌词；
- `contributes.configuration.title`；
- 命令的 `title`、`category`；
- Activity Bar 的 `title`；
- Walkthrough 的标题、描述和步骤正文；
- `apps/vscode/README.md`、`README.marketplace.md`（若存在）、ChangeLog、隐私说明；
- `apps/vscode/package-lock.json` 根包的名称和版本。不要只手改 Lockfile，修改清单后运行 `npm install` 让 npm 同步它。

`apps/vscode/webview-ui/package.json` 的 `name: webview-ui` 是私有内部包名，不决定 VS Code Extension ID，可以保留；如果组织规范要求完整去品牌，再单独修改。

## 6. 同步所有 VS Code 贡献点

### 6.1 为什么不能只改 `name`

`apps/vscode/src/registry.ts` 当前包含：

```ts
const prefix = name === "claude-dev" ? "cline" : name
```

把 `package.json.name` 改为 `acme-agent` 后，运行时注册表会自动生成：

```text
acme-agent.plusButtonClicked
acme-agent.addToChat
acme-agent.generateGitCommitMessage
acme-agent.SidebarProvider
```

但 `apps/vscode/package.json` 中的 `contributes.commands`、菜单和快捷键仍写着 `cline.*`。若不联动修改，就会发生“清单贡献的是旧命令，源码注册的是新命令”。

### 6.2 修改清单中的静态 ID

在 `apps/vscode/package.json` 中进行有边界的替换：

| 位置 | 原值 | 新值示例 |
| --- | --- | --- |
| `contributes.icons` 键 | `cline-icon` | `acme-agent-icon` |
| `walkthroughs[].id` | `ClineWalkthrough` | `AcmeAgentWalkthrough` |
| Activity Bar ID | `claude-dev-ActivityBar` | `acme-agent-ActivityBar` |
| `views` 的容器键 | `claude-dev-ActivityBar` | `acme-agent-ActivityBar` |
| Sidebar ID | `claude-dev.SidebarProvider` | `acme-agent.SidebarProvider` |
| 所有命令 ID | `cline.<command>` | `acme-agent.<command>` |
| `view == ...` 条件 | `claude-dev.SidebarProvider` | `acme-agent.SidebarProvider` |
| Context Key | `cline.isDevMode` | `acme-agent.isDevMode` |
| Context Key | `cline.isGeneratingCommit` | `acme-agent.isGeneratingCommit` |
| Comment Controller | `cline-ai-review` | `acme-agent-review` |
| 图标引用 | `$(cline-icon)` | `$(acme-agent-icon)` |

必须检查贡献点中的所有消费者，而不只是定义处：

```text
contributes.commands
contributes.keybindings
contributes.menus.view/title
contributes.menus.editor/context
contributes.menus.scm/title
contributes.menus.comments/commentThread/context
contributes.menus.comments/commentThread/title
when / enablement 条件表达式
```

同一个命令在 `commands` 中声明后，还会在菜单、快捷键和按钮中被多次引用；这些引用必须完全一致。

### 6.3 同步运行时代码

下列源码包含不会随 `package.json.name` 自动变化的硬编码：

| 文件 | 要处理的内容 |
| --- | --- |
| `apps/vscode/src/extension.ts` | `cline.isDevMode`、Walkthrough ID |
| `apps/vscode/src/dev/commands/tasks.ts` | 两个 `cline.dev.*` 开发命令 |
| `apps/vscode/src/hosts/vscode/commit-message-generator.ts` | `cline.isGeneratingCommit` |
| `apps/vscode/src/services/test/TestMode.ts` | `cline.isTestMode` |
| `apps/vscode/src/hosts/vscode/review/VscodeCommentReviewController.ts` | 评论控制器、两个评论命令、显示名称、头像 |
| `apps/vscode/src/hosts/vscode/terminal/VscodeTerminalRegistry.ts` | `cline-icon` |
| `apps/vscode/src/hosts/vscode/hostbridge/workspace/executeCommandInTerminal.ts` | `cline-icon` |
| `apps/vscode/src/hosts/vscode/VscodeWebviewProvider.ts` | `cline.mcpMarketplace.enabled` 配置监听 |
| `apps/vscode/src/core/storage/state-migrations.ts` | `getConfiguration("cline")` 旧设置迁移 |
| `apps/vscode/src/test/extension.test.ts` | 测试调用的旧命令 ID |

评论功能尤其独立于 `ExtensionRegistryInfo.commands`。应把源码和清单同时改为：

```ts
vscode.comments.createCommentController("acme-agent-review", "Acme Agent Review")
vscode.commands.registerCommand("acme-agent.reviewComment.reply", /* ... */)
vscode.commands.registerCommand("acme-agent.reviewComment.addToChat", /* ... */)
```

更稳妥的长期方案是在 `registry.ts` 中集中导出产品 ID、命令 ID、Context Key、图标 ID 和 Walkthrough ID，清单则通过构建脚本生成或校验。这样以后同步上游时，不会再次散落品牌常量。

## 7. 修复 Walkthrough 和 URI 回调

### 7.1 Walkthrough

`apps/vscode/src/extension.ts` 的首次打开逻辑已经使用动态 Extension ID：

```ts
`${context.extension.id}#ClineWalkthrough`
```

改造后应把后半段也改成新的 Walkthrough ID：

```ts
`${context.extension.id}#AcmeAgentWalkthrough`
```

`apps/vscode/src/core/controller/ui/openWalkthrough.ts` 目前仍硬编码发布者：

```ts
`saoudrizwan.${ExtensionRegistryInfo.name}#ClineWalkthrough`
```

应改为：

```ts
`${ExtensionRegistryInfo.id}#AcmeAgentWalkthrough`
```

并同步重写 `apps/vscode/walkthrough/step1.md` 至 `step5.md` 中的名称、链接和截图。

### 7.2 桌面版 URI Handler

`apps/vscode/src/extension.ts` 注册了 URI Handler，并用当前安装扩展的真实 ID 生成回调：

```ts
const callbackUri = vscode.Uri.parse(`${scheme}://${context.extension.id}${path}`)
```

因此修改 `publisher/name` 后，主回调会自然变成：

```text
vscode://acme.acme-agent/auth
vscode://acme.acme-agent/openrouter
vscode://acme.acme-agent/mcp-auth/callback/<hash>
```

但是 `apps/vscode/src/hosts/vscode/hostbridge/env/getIdeRedirectUri.ts` 仍返回：

```text
vscode://saoudrizwan.claude-dev
```

桌面环境应改为基于注册表生成：

```ts
import { ExtensionRegistryInfo } from "@/registry"

return { value: `${uriScheme}://${ExtensionRegistryInfo.id}` }
```

然后更新 URI、Auth 和 MCP OAuth 相关测试中的旧示例 ID。

### 7.3 服务端回调白名单

客户端改完并不代表 OAuth 一定可用。自己的 Auth/OpenRouter/MCP 服务必须允许新 URI。至少验证：

- 登录页是否接收 `vscode://acme.acme-agent/auth`；
- OpenRouter 授权是否能返回 `/openrouter`；
- MCP OAuth 是否允许动态的 `/mcp-auth/callback/<hash>`；
- VS Code Web/Codespaces 下的 `asExternalUri` HTTP(S) 回调是否仍被服务端接受。

如果继续调用 Cline 官方账户服务，不能假设官方后端会允许第三方 Extension ID。完全独立产品应使用自己的 Auth/API，或者删除账户登录和 Cline Pass 相关功能，仅保留用户自带 API Key 的 Provider。

## 8. 隔离用户数据，避免与原版互相污染

### 8.1 改 Extension ID 仍不够

正式扩展在 `apps/vscode/src/extension.ts` 中调用：

```ts
createStorageContext({ workspacePath })
```

`apps/vscode/src/shared/storage/storage-context.ts` 的默认根目录却是：

```ts
opts.clineDir || process.env.CLINE_DIR || path.join(os.homedir(), ".cline")
```

当前主要数据布局为：

```text
~/.cline/data/globalState.json
~/.cline/data/secrets.json
~/.cline/data/workspaces/<hash>/workspaceState.json
```

这套文件存储已经替代了主要的 VS Code `globalStorage` 使用方式。因此，即使 Extension ID 改成 `acme.acme-agent`，不修改该目录仍会和原版共享设置、密钥、任务历史引用和工作区状态。

### 8.2 最小隔离修改

在 `storage-context.ts` 中把默认目录和环境变量改为自己的标识：

```ts
const productDir =
  opts.clineDir ||
  process.env.ACME_AGENT_DIR ||
  path.join(os.homedir(), ".acme-agent")

const dataDir = path.join(productDir, SETTINGS_SUBFOLDER)
```

为了减少一次改造的风险，可以暂时保留 `clineDir` 这个内部参数名；它不会影响外部品牌。后续再把类型、类名和变量名重构为中性名称。

还应同步：

- `apps/vscode/src/standalone/vscode-context.ts` 中的 `CLINE_DIR` 和 `~/.cline`，保证未来 Standalone 构建一致；
- E2E 测试传入的数据目录环境变量；
- `apps/vscode/src/config.ts` 中的 `~/.cline/endpoints.json`；
- 安装、迁移、清理和故障排查文档；
- 日志中向用户展示的真实数据路径。

`secrets.json` 当前以 `0600` 权限创建，只允许文件所有者读写。改造存储代码时必须保留该权限。

### 8.3 项目配置采用兼容策略

用户级私有数据 `~/.cline` 应默认隔离；工作区内的 `.cline/`、`.clinerules/`、`.clineignore` 则属于公开配置协议，不能未经设计就全局替换。它们涉及 Rules、Skills、Workflows、Hooks、MCP、Ignore、Checkpoint 和远程配置。

可以选择：

| 策略 | 读取 | 写入 | 适合场景 |
| --- | --- | --- | --- |
| 完全兼容 | `.cline*` | `.cline*` | 希望直接复用已有项目配置 |
| 读旧写新 | `.cline*` 和 `.acme-agent*` | `.acme-agent*` | 平滑迁移，最推荐 |
| 完全隔离 | `.acme-agent*` | `.acme-agent*` | 新协议，不要求兼容 Cline |

若采用“读旧写新”，还要定义优先级，例如新目录优先、旧目录仅在新目录不存在时作为回退，并在 UI 中明确显示配置来源。不要静默把用户的旧配置移动或删除。

## 9. 替换品牌资源与用户可见文本

至少审查以下资源：

```text
apps/vscode/assets/icons/
apps/vscode/walkthrough/
apps/vscode/README.md
apps/vscode/README.marketplace.md
apps/vscode/webview-ui/src/
apps/vscode/src/core/prompts/
apps/vscode/src/shared/slashCommands.ts
apps/vscode/src/hosts/vscode/review/VscodeCommentReviewController.ts
```

重点包括：

- Activity Bar、Marketplace 和命令使用的 PNG/SVG/字体图标；
- 评论头像 `CLINE_AVATAR_URL`；
- Onboarding、设置、About、What's New、错误提示和空状态；
- “Add to Cline”“Cline AI Review”“Cline CLI”等命令和文案；
- 系统提示词中要求模型访问 Cline 文档的内容；
- Terms of Service、Privacy Policy、Docs、Issue、Discussion、社区链接；
- OpenRouter 等请求中的 `HTTP-Referer`；
- HTTP `User-Agent: Cline/...` 和 Provider 特定客户端标识。

品牌改造不应只做大小写替换。先区分用户可见品牌、协议兼容标识、内部类型名和第三方 Provider 名，再决定是否修改。

## 10. 决定是否继续使用 Cline 官方网络服务

当前源码仍直接连接或引用 Cline 服务，主要入口包括：

| 功能 | 主要源码 |
| --- | --- |
| App/API/MCP 基础地址 | `apps/vscode/src/config.ts` |
| Cline 账户与 Token | `apps/vscode/src/services/account/`、`services/auth/` |
| Cline Provider/Cline Pass | `apps/vscode/src/core/api/providers/cline.ts` 及模型刷新逻辑 |
| PostHog | `apps/vscode/src/shared/services/config/posthog-config.ts`、`src/services/telemetry/` |
| OpenTelemetry | `apps/vscode/src/services/telemetry/providers/opentelemetry/` |
| MCP Marketplace | `apps/vscode/src/services/mcp/`、Webview Marketplace 页面 |
| Webview 网络白名单 | `apps/vscode/src/core/webview/WebviewProvider.ts` |
| 账户、订阅、条款、隐私 | `apps/vscode/webview-ui/src/components/account/`、`onboarding/`、`settings/` |
| Cline CLI 检测与安装 | `apps/vscode/src/utils/cli-detector.ts`、`src/core/controller/state/installClineCli.ts` |
| Issue 上报 | `apps/vscode/scripts/report-issue.js`、Webview 反馈按钮 |

### 10.1 本地原型阶段

为了先跑通 VSIX，可以：

- 保留 Anthropic、OpenAI、OpenRouter、Ollama 等用户自带 Key 的 Provider；
- 暂时关闭账户、订阅、官方 Marketplace 和公告入口；
- 默认关闭遥测，直到自己的隐私政策和接收端准备完成；
- 在 UI 中明确这是独立分支，不是官方 Cline。

### 10.2 完全独立阶段

应逐项完成：

1. 把 `app.cline.bot`、`api.cline.bot` 和 MCP API 改为自己的服务，或移除相应功能；
2. 自建登录和 Token 生命周期，更新所有回调白名单；
3. 使用自己的 PostHog/OpenTelemetry 项目和密钥，或彻底禁用；
4. 更新 Webview CSP 的 `connect-src`，只允许实际需要的域名；
5. 替换 Marketplace、Banner、Feature Flags、Remote Config 来源；
6. 替换服务条款、隐私政策、帮助文档和问题反馈地址；
7. 替换 `User-Agent`、`HTTP-Referer`、客户端类型和版本头；
8. 删除“安装 Cline CLI”，或改成检测、安装自己的 CLI；
9. 更新缓存、状态迁移和测试快照中的服务假设；
10. 实际抓包确认启动、登录、聊天和退出时不再访问未授权的 Cline 域名。

服务地址最好集中到一个产品配置模块，并允许通过构建环境或企业配置注入。不要让生产地址继续散落在 React 组件和 Provider 中。

## 11. 不要盲目全局替换 `cline`

全局搜索是审计手段，不是自动替换方案。以下内容通常需要分别判断：

| 类型 | 示例 | 建议 |
| --- | --- | --- |
| 外部身份 | Extension ID、命令、URI、存储目录 | 必须替换或隔离 |
| 用户可见品牌 | 标题、Logo、链接、提示词 | 应替换 |
| 官方服务 | API、Auth、遥测、Marketplace | 替换、禁用或取得授权 |
| 项目配置协议 | `.clinerules`、`.clineignore` | 先设计兼容策略 |
| Proto 包名 | `proto.cline.*`、生成代码路径 | 默认保留，除非做协议级迁移 |
| 内部类型名 | `ClineCore`、`ClineMessage` | 可渐进重构，不影响 Extension ID |
| Provider ID | `cline` Provider、配置枚举 | 删除前先做数据迁移 |
| 历史状态键/遥测事件 | 已持久化键、指标名 | 修改前评估兼容和迁移 |
| 测试 Fixture/快照 | 固定字符串 | 行为改变后同步更新 |

先运行审计：

```bash
cd apps/vscode

rg -n --hidden \
  -g '!node_modules/**' \
  -g '!dist/**' \
  -g '!webview-ui/build/**' \
  'saoudrizwan|claude-dev|Cline|cline\.|cline-|\.cline|CLINE_DIR|cline\.bot' \
  package.json src webview-ui walkthrough assets scripts
```

将结果分为“身份、品牌、存储、服务、协议、内部实现、测试”七类后逐类处理。完成后重复搜索；剩余项必须能说明保留原因。

## 17. 常见失败及定位方法

### 17.1 新图标出现，但按钮全部无效

原因通常是运行时命令已变成 `acme-agent.*`，而 `package.json` 仍贡献 `cline.*`。对比 `src/registry.ts` 与 `package.json` 中每个命令 ID。

### 17.2 Activity Bar 有容器，但侧边栏为空

检查三处是否一致：

```text
viewsContainers.activitybar[].id = acme-agent-ActivityBar
views["acme-agent-ActivityBar"][].id = acme-agent.SidebarProvider
ExtensionRegistryInfo.views.Sidebar = acme-agent.SidebarProvider
```

### 17.3 Git 按钮一直显示“生成中”

`package.json` 的 `when` 条件与 `commit-message-generator.ts` 的 `setContext` 使用了不同 Context Key。统一为 `acme-agent.isGeneratingCommit`。

### 17.4 Walkthrough 报不存在

Extension ID 或 Walkthrough ID 仍有旧值。统一使用：

```text
acme.acme-agent#AcmeAgentWalkthrough
```

### 17.5 登录成功后没有回到插件

依次检查：

1. `publisher.name` 是否为 `acme.acme-agent`；
2. `extension.ts` 生成的 URI；
3. `getIdeRedirectUri.ts` 是否移除了旧硬编码；
4. 服务端 redirect allowlist；
5. VS Code Web/Codespaces 是否走了 HTTP(S) 外部 URI。

### 17.6 原版账户或历史出现在新插件中

说明新插件仍读取 `CLINE_DIR` 或 `~/.cline`。检查 `storage-context.ts`、Standalone 上下文、测试环境变量和所有直接拼接路径的代码。

### 17.7 VSIX 很小、Webview 白屏或图标丢失

检查：

```bash
npm run package
npx @vscode/vsce ls
```

确认 `dist/extension.js`、`webview-ui/build`、`assets/icons` 和必要的 `node_modules` 文件被包含，并检查 `.vscodeignore` 的否定规则。

### 17.8 本地运行正常，安装 VSIX 后异常

常见原因是代码依赖了未打包的源码文件、开发环境 `.env`、绝对路径或只存在于工作区的资源。必须在一个干净 VS Code Profile 中安装 VSIX 复测，而不是只依赖 F5。

## 18. 建议的分阶段实施顺序

### 阶段一：最小可安装

1. 修改 `name/displayName/publisher/version`；
2. 替换图标和明显品牌文案；

5. 把存储改到 `~/.acme-agent`；
6. 完成类型检查、单测、生产构建和 VSIX 安装。

### 阶段二：可与原版可靠共存

1. 同时启用两个插件做全入口验收；
2. 增加存储、命令、URI 和评论控制器自动化测试；

## 19. 完成定义

只有同时满足以下条件，才能认为“已转换成独立插件”：

- `code --list-extensions --show-versions` 显示自己的 Extension ID；
- VSIX 能在干净 VS Code Profile 中安装、激活、升级和卸载；
- 所有清单命令都有同 ID 的运行时处理器；
- Activity Bar、Sidebar、菜单、Context Key、评论和 Walkthrough 不与原版冲突；
- URI/Auth/MCP OAuth 全部回到自己的 Extension ID；
- 用户数据、Secret 和工作区状态不再写入原版数据目录；
- 原版与新插件同时启用时，双方主要功能都可用；
- 用户界面、图标、文档和链接不会让人误认为官方 Cline；
- 网络请求只访问已披露且获得授权的服务；
- Apache-2.0 许可证、版权归属、隐私政策和第三方依赖义务得到保留或履行；
- `npm run check-types`、相关测试、`npm run package` 和 VSIX 实机验收全部通过。

完成这些步骤后，`apps/vscode/dist/acme-agent-<version>.vsix` 才是一个真正具有独立身份、可本地安装，并具备继续产品化基础的 VS Code 插件。
