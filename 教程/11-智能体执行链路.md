# 用户消息后的智能体执行链路

> 本文基于当前工作区源码，分析“用户发送一条消息后，系统怎样把它变成模型请求、怎样执行工具、怎样继续下一轮以及怎样结束”。项目目前存在两套并行实现：正式 VS Code 扩展位于 `apps/vscode`；新 SDK/CLI 运行时位于 `sdk/packages/*` 与 `apps/cli`。两者目标相同，但入口、事件模型、持久化和工具循环并不是同一套代码，改造时不能混用。

## 1. 先给出结论

一条用户消息不会简单地对应一次模型 API 调用。更准确的层次是：

- **会话/任务**：VS Code 中是一个 `Task`，SDK 中是一个 `Session`；
- **用户 Turn**：用户提交一次新指令，或者回答一次追问；
- **模型迭代**：模型调用一次，可能输出文本，也可能提出一个或多个工具调用；
- **工具回合**：工具执行结果作为 `tool_result` 或用户侧内容写回历史，再触发下一次模型迭代；
- **结束边界**：模型明确完成、终止工具成功、用户确认、达到错误/迭代上限，或者用户取消。

正式 VS Code 扩展的核心闭环是：

```text
Webview 输入
  → gRPC TaskService
  → Controller.initTask / Task.handleWebviewAskResponse
  → Task.startTask / 被挂起的 Task.ask 恢复
  → Task.initiateTaskLoop
  → Task.recursivelyMakeClineRequests
  → Task.attemptApiRequest
  → Provider 流式响应
  ├─ 文本/推理 → 增量展示
  ├─ 工具调用 → ToolExecutor → Tool Result → 下一次模型请求
  └─ 完成/追问 → 等待用户、继续或结束 Task
```

SDK/CLI 的核心闭环是：

```text
CLI / SDK 调用方
  → ClineCore.start / ClineCore.send
  → RuntimeHost.startSession / runTurn
  → LocalRuntimeHost.executeTurn
  → SessionRuntime.run / continue
  → AgentRuntime.execute
  → model.stream
  ├─ Delta → AgentRuntimeEvent
  ├─ Tool Call → Hook/Policy/Approval/execute → Tool Result → 下一迭代
  └─ 无工具、终止工具、取消或上限 → AgentRunResult
  → 保存 Session 消息、用量和 Manifest
  → CoreSessionEvent 返回 CLI/TUI/SDK 调用方
```

## 2. 两套实现的职责边界

| 维度 | VS Code 正式实现 | SDK/CLI 新实现 |
| --- | --- | --- |
| 用户入口 | React Webview | CLI、TUI、ACP 或 SDK 调用方 |
| 会话核心 | `Task` | `ClineCore` + `RuntimeHost` + `SessionRuntime` |
| Agent 循环 | `Task.recursivelyMakeClineRequests()` | `AgentRuntime.execute()` |
| 模型流 | `ApiHandler.createMessage()` 返回 `ApiStream` | `AgentModel.stream()` 返回原生运行时事件流 |
| 工具表示 | XML Tool Block 与 Native Tool Call 并存 | 统一为 `AgentToolCallPart` |
| 工具调度 | `ToolExecutor`、Coordinator、各 Handler | `AgentRuntime.prepareToolExecution()` / `executePreparedTool()` |
| 用户批准 | `Task.ask()` 与 Webview `askResponse` | `requestToolApproval` 回调、Session 状态 `pending` |
| 事件 | `ClineMessage`、Webview 状态和 Task History | `AgentRuntimeEvent` → 旧 `AgentEvent` → `CoreSessionEvent` |
| 持久化 | Task 目录下 UI/API History、Checkpoint | Session Manifest 与 `*.messages.json` |

本文先完整展开 VS Code 链路，再展开 SDK/CLI 链路，最后给出分支和改造定位对照。

## 3. VS Code：消息怎样进入扩展后端

### 3.1 Webview 输入分流

入口位于：

```text
apps/vscode/webview-ui/src/components/chat/chat-view/hooks/useMessageHandlers.ts
```

`handleSendMessage()` 会根据当前聊天状态选择不同协议动作，而不是所有内容都调用“新任务”：

| 当前状态 | 发出的调用/响应 | 作用 |
| --- | --- | --- |
| 没有现存聊天任务 | `TaskServiceClient.newTask()` | 创建新的 `Task`，首条文本、图片和文件成为任务输入 |
| 后端正在 `ask()` 等待答案 | `TaskServiceClient.askResponse()` | 回答工具追问、审批、完成确认或错误恢复问题 |
| 恢复历史任务 | `yesButtonClicked` 等 Ask Response | 唤醒恢复流程，使旧历史继续运行 |
| Tool/Followup 的文字或附件反馈 | `messageResponse` | 将用户反馈包装成当前工具的结果，继续同一任务 |
| 批准或拒绝工具 | `yesButtonClicked` / `noButtonClicked` | 决定工具是否真正执行 |

对应的 gRPC 定义和服务实现位于：

```text
apps/vscode/proto/cline/task.proto
apps/vscode/src/core/controller/task/newTask.ts
apps/vscode/src/core/controller/task/askResponse.ts
```

这里有一个容易误判的细节：Webview 代码允许在若干 UI 状态下提交消息，但后端 `Task.handleWebviewAskResponse()` 的直接行为只是写入 `TaskState.askResponse*`。从当前可验证的主链路看，这些数据是在 `Task.ask()` 的等待边界被消费；不能仅凭 UI 注释就断言任意流式时刻都会立即形成一个独立用户 Turn。

### 3.2 新任务入口

新任务的调用关系为：

```text
TaskServiceClient.newTask
  → newTask(controller, request)
  → Controller.initTask(text, images, files, settings)
  → 清理旧 Task 并解析任务级设置
  → 建立 WorkspaceManager、任务锁和 Task 实例
  → Task.startTask(task, images, files)
```

`newTask.ts` 还会把前端传入的 Plan/Act 模式、Provider、浏览器配置、自动批准配置和 Reasoning Effort 转换为后端 `Settings`。因此，消息内容相同但任务级设置不同，后续 System Prompt、可用工具和审批策略都可能不同。

### 3.3 已有 Ask 的响应入口

已有任务正在等待用户时，调用关系为：

```text
TaskServiceClient.askResponse
  → askResponse(controller, request)
  → Task.handleWebviewAskResponse(response, text, images, files)
  → 写入 taskState.askResponse / Text / Images / Files
  → 正在轮询等待的 Task.ask() 取得结果
  → Tool Handler、Followup、Resume 或 Completion 分支继续
```

`Task.ask()` 在返回前还会核对 `lastMessageTs`，防止连续 Ask 时旧响应错误地唤醒新问题。响应被读取后，`askResponse*` 字段会被清空，避免重复消费。

## 4. VS Code：新任务初始化链路

核心实现在：

```text
apps/vscode/src/core/task/index.ts
```

`Task.startTask()` 的步骤及作用如下。

1. **初始化 `.clineignore`**

   建立路径访问过滤规则。后续附件解析、文件工具和目录工具都要服从这一边界。

2. **清空本次 Task 的 UI/API 历史**

   新任务不能继承旧任务的模型上下文；界面消息和 Provider 消息分别初始化。

3. **调用 `say("task")`**

   把首条任务保存为可展示的 `ClineMessage`，同步给 Webview，并成为任务历史标题/摘要的数据来源之一。

4. **构造 `<task>...</task>` 用户内容**

   首条纯文本不是裸字符串进入模型，而是被标明为任务正文，使 System Prompt 能区分初始目标与后续环境信息。

5. **转换图片**

   图片被转换为 Provider 能识别的 Image Block；模型不支持图片时，后续 Provider/消息构建层还可能降级处理。

6. **处理文件附件**

   `processFilesIntoText()` 读取允许访问的附件，将路径和文本内容加入用户上下文。界面上的“附件”与最终送入模型的文本表示因此不是同一个对象。

7. **执行 `TaskStart` Hook**

   Hook 可以取消任务，也可以返回 `contextModification`。取消时会保存状态并调用 `cancelTask()`；上下文修改会以带来源标记的 Hook Context 注入首轮用户内容。

8. **执行 `UserPromptSubmit` Hook**

   它处理用户真正提交的提示，也可以取消或追加上下文。初始任务中它位于 `TaskStart` 之后，以保证 Hook 的 UI 和语义顺序。

9. **记录环境与任务元数据**

   包括模式、模型、工作区和 Telemetry 所需信息，为后续请求和诊断提供上下文。

10. **进入 `initiateTaskLoop(userContent)`**

    从这里开始，用户消息变成可递归执行的 Agent Loop，而不再只是一次 UI 事件。

## 5. VS Code：外层 Agent Loop

### 5.1 `initiateTaskLoop()`

主调用是：

```text
Task.initiateTaskLoop(userContent)
  → Task.recursivelyMakeClineRequests(userContent, includeFileDetails)
```

`recursivelyMakeClineRequests()` 返回“是否应结束循环”。如果模型本轮既没有结束任务也没有使用工具，外层会构造 `formatResponse.noToolsUsed()`，增加 `consecutiveMistakeCount`，再要求模型继续。这是为什么有时用户只发一条消息，却能观察到多次模型请求。

### 5.2 每次模型迭代前的准备

`recursivelyMakeClineRequests()` 每轮依次处理：

1. **Abort 检查**：任务已取消则立即停止，不再访问 Provider 或工具。
2. **等待远程工作区检测**：保证远程/本地工作区能力已经确定。
3. **更新请求计数与 Focus Chain 计数**：用于迭代控制、界面状态和连续工作目标。
4. **固定本轮 Provider/Model 信息**：后续流式统计和历史消息能准确关联实际模型。
5. **检查连续错误上限**：
   - YOLO/非交互策略可直接失败；
   - 交互模式通过 `ask()` 询问用户是否继续。
6. **首轮初始化 Checkpoint**：异步创建初始 Git/工作区快照，为回滚和 Diff 提供基线。
7. **判断是否需要 Context Compaction**：上下文过长时进入摘要/截断分支。
8. **普通上下文加载**：`loadContext()` 解析 Mentions、Slash Commands、MCP Prompt、环境详情和 Focus Chain 指令。
9. **压缩上下文加载**：用 `summarizeTask()` 等结果替代被压缩的旧对话，同时保留继续任务所需状态。
10. **写入 `api_req_started` UI 消息**：界面开始显示请求状态、Token 和费用。
11. **把本轮用户内容写入 API History**：注意这是 Provider 对话历史，不等同于 UI History。
12. **调用 `attemptApiRequest()`**：正式构建 System Prompt 并连接模型。

## 6. VS Code：System Prompt 与 Provider 请求

### 6.1 请求前动态发现

`Task.attemptApiRequest()` 不使用固定的 System Prompt 文件直接发送，而是实时收集：

- 当前 Provider、Model、API Format 和模型能力；
- VS Code/IDE 类型、首选语言和浏览器能力；
- 全局与工作区 `.clinerules`；
- Cursor、Windsurf、`AGENTS.md` 等兼容规则；
- `.clineignore` 内容；
- MCP Server/Prompt/Tool；
- 可用 Skills；
- 多根工作区信息；
- 打开和可见的编辑器标签；
- Plan/Act、YOLO、Subagent、Web Tools、Native/Parallel Tool Call 等开关。

主要实现位于：

```text
apps/vscode/src/core/prompts/system-prompt/index.ts
apps/vscode/src/core/prompts/system-prompt/types.ts
apps/vscode/src/core/context/context-management/ContextManager.ts
apps/vscode/src/core/task/index.ts
```

随后形成：

```text
SystemPromptContext
  → getSystemPrompt(promptContext)
  → { systemPrompt, tools }
  → ContextManager.getNewContextMessagesAndMetadata(...)
  → api.createMessage(systemPrompt, truncatedConversationHistory, tools)
```

`getSystemPrompt()` 同时决定文字版工具协议和 Native Tool Definitions。`ContextManager` 再应用历史删除范围、截断、自动 Condense 和消息重写，最终的 `truncatedConversationHistory` 才是 Provider 真正看到的对话。

### 6.2 首个 Chunk 错误分支

`attemptApiRequest()` 会先主动读取 Stream 的第一个 Chunk：

- 成功：把第一个 Chunk 交还主循环，继续流式消费；
- Context Window Exceeded：在未自动重试过时进入上下文缩减/重试；
- Rate Limit、认证、网络或 Provider 错误：转换为统一错误，按配置重试、询问用户或结束；
- 用户在等待首 Chunk 时取消：终止请求并更新 Task 状态。

这一设计把“建立连接就失败”和“已经产生部分输出后失败”区分开，避免把失败请求误记为完整 Assistant 回答。

## 7. VS Code：流式响应处理

主循环由 `StreamChunkCoordinator` 协调，相关实现包括：

```text
apps/vscode/src/core/task/StreamChunkCoordinator.ts
apps/vscode/src/core/task/StreamResponseHandler.ts
apps/vscode/src/core/task/index.ts
```

### 7.1 Reasoning Chunk

```text
reasoning chunk
  → ReasonsHandler.processReasoningDelta()
  → 累积 reasoning / redacted reasoning
  → say("reasoning", partial=true)
  → Webview 增量展示
```

只有 Provider 实际返回的 Reasoning/Thinking 才能进入这条链路；Provider 内部未返回的隐式思考不在客户端执行链路中。

### 7.2 Text Chunk 与 XML Tool

```text
text chunk
  → 累加 assistantMessage
  → parseAssistantMessageV2(assistantMessage)
  → 得到 Text Block / ToolUse Block
  → presentAssistantMessage()
```

XML Tool Call 可能跨多个 Chunk，因此解析器会产生 Partial Block。Partial 阶段只更新展示和工具预览；直到 Block 完整，才允许真实执行工具。

### 7.3 Native Tool Call

```text
tool_calls chunk
  → ToolUseHandler.processToolUseDelta()
  → Provider Call ID 映射到内部 Tool Use ID
  → 组装名称与 JSON 参数
  → processNativeToolCalls()
  → 与 XML Tool 进入统一 ToolExecutor
```

Native Tool 与 XML Tool 的解析入口不同，但执行阶段最终都落到 `ToolExecutor.executeTool()`，因此审批、Hook、`.clineignore` 和结果回填规则应在统一执行层修改。

### 7.4 Usage Chunk

Usage 会累加 Input、Output、Cache Read/Write Token 和 Cost，更新 `api_req_started`、任务历史与 Telemetry。部分 Provider 不在 Stream 中给出最终 Usage，因此流结束后还会补取 Provider Usage。

### 7.5 流中断条件

常见中断包括：

- 用户取消 Task；
- 工具被用户拒绝；
- 未开启并行工具时，本轮已经执行了一个工具，后续输出不再继续执行；
- Provider Stream 抛错；
- Hook 请求取消；
- Task 已被新任务替换。

### 7.6 流结束后的归档与递归

一次模型 Stream 结束后，主循环会：

1. 补齐 Provider Usage；
2. 完成 `api_req_started` UI 消息；
3. 保存 UI History；
4. 组装 Reasoning、Redacted Reasoning、Text 和 `tool_use` 内容；
5. 把完整 Assistant Message 写入 API History；
6. 完成仍处于 Partial 的工具展示块；
7. 等待 UI 展示与工具任务完成；
8. 保存 Checkpoint；
9. 将工具结果或纠错内容作为下一轮用户内容，再次调用 `recursivelyMakeClineRequests()`。

所以一次“模型回答”在内部既有增量 UI 状态，也有最终 Assistant API Message；两者保存时机和用途不同。

## 8. VS Code：工具执行链路

核心源码为：

```text
apps/vscode/src/core/task/ToolExecutor.ts
apps/vscode/src/core/task/tools/ToolExecutorCoordinator.ts
apps/vscode/src/core/task/tools/ToolValidator.ts
apps/vscode/src/core/task/tools/autoApprove.ts
apps/vscode/src/core/task/tools/utils/ToolResultUtils.ts
apps/vscode/src/core/task/tools/utils/ToolHookUtils.ts
apps/vscode/src/core/task/tools/handlers/
```

完整调用关系为：

```text
presentAssistantMessage()
  → ToolExecutor.executeTool(block)
  → Coordinator 查找 Tool Handler
  → Validator / Handler 校验参数和路径
  → Auto Approve 或 Task.ask() 等待用户
  → PreToolUse Hook
  → Handler.execute() 执行真实副作用
  → ToolExecutor.runPostToolUseHook()
  → ToolResultUtils.pushToolResult()
  → taskState.userMessageContent
  → 下一次 recursivelyMakeClineRequests()
```

### 8.1 执行前分支

| 判断 | 结果 | 目的 |
| --- | --- | --- |
| Tool 未注册 | 生成 Unknown/Invalid Tool 结果 | 让模型下一轮修正工具名 |
| 前一个 Tool 已被拒绝 | 跳过同一批次后续 Tool | 防止拒绝后仍产生副作用 |
| 非并行模式已执行 Tool | 返回 `toolAlreadyUsed` | 维持一轮一个工具的旧协议约束 |
| Strict Plan Mode 请求写操作 | 拒绝 | 保证 Plan 模式只分析不修改 |
| Block 尚未完整 | 只更新 Partial UI | 避免参数未完整就运行工具 |
| 参数、工作区路径或 `.clineignore` 不合法 | 返回 Tool Error | 阻断越界访问并让模型自修复 |

### 8.2 审批与 Hook 的真实顺序

对于需要批准的工具，顺序是：

```text
参数/安全校验
  → 自动批准判断
  → 若不能自动批准，Task.ask() 等用户决定
  → 用户批准
  → PreToolUse Hook
  → 真实工具操作
  → PostToolUse Hook
  → Tool Result 回填
```

特别需要注意：当前源码把 `PreToolUse` 放在各具体 Handler 内，发生在用户批准之后、真实操作之前。`PostToolUse` 用于观察和结果处理，成功与失败路径都会尝试执行。改造安全策略时不能假设 `PreToolUse` 早于用户批准。

### 8.3 Tool Result 为什么会触发下一次模型请求

工具不直接“替模型回答”。Handler 返回后，`pushToolResult()` 把结构化结果写入 `taskState.userMessageContent`。本轮 Assistant History 已经包含对应 Tool Use；下一轮模型请求同时看到 Tool Use 与 Tool Result，模型据此决定：

- 使用另一个工具；
- 修复错误参数后重试；
- 向用户追问；
- 输出最终答案并调用完成工具。

工具异常通常被转换为 `tool_result` 错误，而不是立即杀死整个 Task。这使模型有机会自行修复。只有 Abort、不可恢复 Hook 错误、连续错误上限等才直接终止外层循环。

### 8.4 重复工具调用

系统会记录工具名和参数签名。连续重复达到软阈值时，向模型加入恢复提示；达到硬阈值时按错误上限策略询问用户或停止，避免 Agent 无限执行同一个无效动作。

## 9. VS Code：追问、完成与恢复分支

### 9.1 `ask_followup_question`

实现位于：

```text
apps/vscode/src/core/task/tools/handlers/AskFollowupQuestionToolHandler.ts
```

交互模式下：

```text
模型调用 ask_followup_question
  → Handler 展示问题和建议答案
  → Task.ask("followup") 挂起
  → 用户提交文字/图片/文件
  → 包装为 <answer> Tool Result
  → 下一轮模型请求
```

YOLO 模式不能等待人工输入时，Handler 会返回提示，要求模型自行通过工具获取信息或采用合理假设，而不是永久挂起。

### 9.2 `attempt_completion`

实现位于：

```text
apps/vscode/src/core/task/tools/handlers/AttemptCompletionHandler.ts
```

主要分支如下：

1. 缺少 `result`：记为 Mistake，让模型补齐完成说明；
2. 开启 Double Check Completion：第一次完成请求被拦截，要求模型重新验证任务；
3. 存在完成命令：执行命令并把输出纳入完成判断；
4. 展示 `completion_result` 并保存 Checkpoint；
5. 执行只观察的 `TaskComplete` Hook；
6. 等待用户决定：
   - 用户确认或开始新任务：结束当前循环；
   - 用户给出反馈：反馈成为 Completion Tool Result，Agent 继续工作。

因此“模型说完成了”不总等于 Task 立即销毁；是否结束还取决于完成策略和用户反馈。

### 9.3 历史任务恢复

恢复时会读取 UI/API History、任务元数据和 Checkpoint，重建 `Task`，然后通过 Ask Response 确认继续。新的反馈经过 `UserPromptSubmit` Hook 后进入 `initiateTaskLoop()`。恢复不是把旧对话拼成一段纯文本，而是尽量恢复原始结构化消息和任务状态。

## 10. VS Code 分支链路总表

| 分支 | 触发条件 | 后续链路 | 最终效果 |
| --- | --- | --- | --- |
| 新任务 | 无当前 Task | `newTask → initTask → startTask` | 新建历史、Checkpoint 和 Agent Loop |
| 回答 Ask | Tool/Followup/Completion 正在等待 | `askResponse → Task.ask()` 恢复 | 继续当前工具或当前任务 |
| 普通文本输出 | Stream 只有 Text/Reasoning | 保存 Assistant；若未完成且无工具则纠错 | 可能再次请求模型 |
| XML Tool | 文本中解析出完整 Tool Block | `presentAssistantMessage → ToolExecutor` | 执行后递归下一轮 |
| Native Tool | Provider 返回 Tool Call Delta | `processNativeToolCalls → ToolExecutor` | 与 XML Tool 统一执行 |
| 自动批准 | Tool 和设置允许 | 跳过用户 Ask | 直接执行 Tool |
| 用户拒绝 | Ask 返回 No | 写拒绝 Tool Result，跳过后续 Tool | 模型收到拒绝原因 |
| Plan 写操作 | Strict Plan Mode | Validator/Handler 拒绝 | 模型只能规划或切换模式 |
| Followup | 模型缺少信息 | `Task.ask("followup")` | 用户答案进入下一轮 |
| Completion | 模型调用完成工具 | 校验、Hook、用户确认 | 结束或根据反馈继续 |
| 上下文过长 | Token/Provider 报错 | Compaction/Condense 后重试 | 使用压缩历史继续 |
| 连续错误 | 达到 Mistake 上限 | Ask 用户或 YOLO 失败 | 防止无限循环 |
| Provider 首包失败 | 首 Chunk 抛错 | 自动重试、Ask 或终止 | 不把失败流当完整回答 |
| 用户取消 | Abort/Cancel | 停流、停工具、保存状态 | Task 以取消状态结束 |

## 11. SDK/CLI：入口与会话层

CLI 并没有复制一套 Agent Loop。`apps/cli` 创建 `ClineCore`，再通过 Session Manager 调用 `start()` 和 `send()`：

```text
apps/cli/src/session/session.ts
apps/cli/src/runtime/run-agent.ts
apps/cli/src/runtime/interactive/session-runtime.ts
sdk/packages/core/src/ClineCore.ts
```

### 11.1 新会话

```text
ClineCore.start(input)
  → 可选 prepare/bootstrap
  → normalizeClineCoreStartInput()
  → RuntimeHost.startSession()
```

`RuntimeHost` 可以是 Local、Hub 或 Remote。传输位置不同，但本地权威执行实现是：

```text
sdk/packages/core/src/runtime/host/local-runtime-host.ts
```

`LocalRuntimeHost.startSession()` 的主要步骤是：

1. 解析或创建 `sessionId`；
2. 为 OAuth Provider 注入当前 Credential；
3. 确定 Session 目录、Manifest 路径和 `*.messages.json` 路径；
4. 建立初始 Manifest，记录 Provider、Model、CWD、Workspace、工具和 Team 开关；
5. 通过 `prepareLocalRuntimeBootstrap()` 合并插件、Hook、工具策略和能力；
6. 通过 `RuntimeBuilder` 构建工具、扩展、Completion Policy、Team Runtime 等；
7. 创建 `SessionRuntime`/Agent facade，并注册事件订阅；
8. 创建 `ActiveSession`，写入 Session Map；
9. 持久化初始消息和 Manifest；
10. 如果 `start` 带 Prompt，立即调用 `executeTurn()`；否则只建立可继续的会话。

### 11.2 已有会话的新消息

```text
ClineCore.send(...)
  → RuntimeHost.runTurn(input)
  → LocalRuntimeHost.runTurn(input)
```

`runTurn()` 先检查 Agent 是否可开始新 Run，再决定立即执行还是进入待处理队列。

## 12. SDK/CLI：`queue` 与 `steer` 分支

这是 SDK 相比 VS Code `Task.ask()` 更明确的一套“运行中消息”语义，实现在：

```text
sdk/packages/core/src/runtime/turn-queue/pending-prompt-service.ts
sdk/packages/core/src/runtime/host/local-runtime-host.ts
```

### 12.1 `queue`

```text
当前 Agent 正在运行
  → runTurn(delivery="queue")
  → PendingPromptsController.enqueue()
  → 当前 Run 正常结束
  → drain() 取出队首
  → 再次调用 send/runTurn
  → 形成一个新的独立用户 Turn
```

`queue` 保留图片和文件附件，适合“做完当前事情后再做下一件事”。发送失败时，条目会重新放回队首，避免悄悄丢失。

### 12.2 `steer`

```text
当前 Agent 正在运行
  → runTurn(delivery="steer")
  → Steer 条目插到 Pending 队列前部
  → AgentRuntime 下一次 iteration 构造模型请求
  → consumePendingUserMessage()
  → 把 Steer 文本作为 user message 注入当前 Run
```

`steer` 用于调整当前任务方向，不必等整个 Run 完成。不过当前 `AgentRuntime.consumePendingUserMessage()` 返回的是文本；由 `LocalRuntimeHost` 连接的消费回调只格式化 `entry.prompt` 和模式。排队条目中的图片/文件适用于后续独立 `queue` Turn，不能据此假设 Steer 附件也会在当前 Run 中被完整注入。

### 12.3 默认行为

交互 Session 正在忙且调用方未指定 `delivery` 时，`runTurn()` 默认采用 `queue`。空闲时则立即进入 `executeTurn()`。

## 13. SDK/CLI：LocalRuntimeHost 的 Turn 主链

### 13.1 输入准备

`executeTurn()` 首先调用 `prepareTurnInput()`：

1. `normalizeUserInput()` 规范化文本；
2. `enrichPromptWithMentions()` 解析工作区 Mention；
3. `formatModePrompt()` 加入 Plan/Act 等模式语义；
4. 把显式文件路径相对 CWD 转成绝对路径；
5. 把 Mention 命中的文件相对 Workspace 转成绝对路径；
6. 去重并保留图片、文件附件。

接着：

```text
prepareTurnInput
  → ensureSessionPersisted
  → syncOAuthCredentials
  → markTurnRunning
  → executeAgentTurn
```

### 13.2 首次 Run 与后续 Continue

`executeAgentTurn()` 根据会话是否已有消息选择：

```text
新会话：session.agent.run(prompt, images, files)
已有会话：session.agent.continue(prompt, images, files)
```

调用前保存 `baselineMessages` 和 Usage Baseline；调用后：

- 把最新 Assistant Turn 的 Model、Usage 等元数据合并到消息；
- 分别计算主 Agent 与 Team/Subagent 聚合用量；
- 更新 Session Metadata；
- 保存完整消息到 `*.messages.json`；
- 检查是否成功调用 `submit_and_exit`；
- 交互 Session 回到 `idle`，非交互 Session 进入最终状态。

失败路径也会先保存 `session.agent.getMessages()`，再把异常向上抛出，尽量保留已经产生的部分轨迹。

### 13.3 OAuth 自动恢复

`runWithAuthRetry()` 的分支是：

```text
Agent Run 抛错
  ├─ 非 OAuth/非认证错误 → 原样抛出
  └─ 疑似 OAuth 认证错误
       → 强制刷新 Token
       → session.agent.restore(baselineMessages)
       → 用刷新后的连接重试同一个 Run
```

先 `restore()` 到基线可以避免第一次失败产生的部分消息在重试时重复进入历史。

### 13.4 Team 自动继续

Lead Agent 一轮结束时，如果仍有 Team Run 在后台执行：

```text
shouldAutoContinueTeamRuns(...)
  → waitForTeamRunUpdates()
  → buildTeamRunContinuationPrompt()
  → executeAgentTurn(continuationPrompt)
```

因此 Team 场景中，用户只提交一次消息，也可能出现 Lead 等待 Teammate、收到更新、自动继续总结的多个 Run。

## 14. SDK：SessionRuntime 适配层

核心实现：

```text
sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts
sdk/packages/core/src/runtime/orchestration/runtime-event-adapter.ts
```

`SessionRuntime` 的作用不是再实现一遍模型循环，而是把 Core 世界适配到底层 `AgentRuntime`：

1. 把当前用户文字、图片和文件构造成 User Message；
2. 把完整 Session Conversation 作为 `initialMessages`；
3. 合并配置声明工具与 Extension 注册工具；
4. 组合 System Prompt 和 Rules；
5. 把 Core Hook、Tool Policy、Approval、Compaction `prepareTurn` 转成 `AgentRuntimeConfig`；
6. 创建新的 `AgentRuntime` 执行本 Turn；
7. 订阅原生 `AgentRuntimeEvent`；
8. Run 结束后用 `runResult.messages` 替换 Session Conversation。

为避免同一条用户消息写两次，`SessionRuntime` 会先把用户消息加入 Conversation，再用完整 Conversation 初始化 `AgentRuntime`，最后调用 `runtime.run("")` 或 `runtime.continue(undefined)`，不再把输入重复传给底层。

## 15. SDK：AgentRuntime 核心循环

核心源码：

```text
sdk/packages/agents/src/agent-runtime.ts
```

`run()` 与 `continue()` 最终都进入私有 `execute()`。详细流程如下。

### 15.1 Run 初始化

1. 初始化插件提供的 Tool 和 Hook；
2. 拒绝同一个 Runtime 上并发的第二个 Run；
3. 创建 `AbortController` 和新的 `runId`；
4. 清空本 Run 的 Iteration、Pending Tool Calls、Usage 和 Last Error；
5. 调用 `beforeRun` Hook；
6. 发出 `run-started`；
7. 加入本次 User Message，并发出 `message-added`；
8. 如果 Completion Policy 强制终止工具，加入“必须调用终止工具”的 Reminder。

### 15.2 每次 Iteration

```text
while 未超过 maxIterations
  → throwIfAborted()
  → iteration += 1
  → emit(turn-started)
  → generateAssistantMessage()
  → 保存 Assistant Message
  → emit(message-added / assistant-message)
  ├─ 没有 Tool Call → Completion Guard 或结束
  └─ 有 Tool Call → executeToolCalls()
                      → 保存 Tool Messages
                      → emit(turn-finished)
                      ├─ 成功的终止 Tool → 结束
                      └─ 普通 Tool → 下一 Iteration
```

超过 `maxIterations` 会产生失败结果，而不是无限运行。

### 15.3 模型请求生成

`generateAssistantMessage()` 依次执行：

1. 用当前 System Prompt、完整内存消息、工具定义和 Abort Signal 创建 `AgentModelRequest`；
2. 第二次及以后 Iteration 尝试消费 Steer 消息；
3. 调用 `prepareTurn()`，这里可执行 Context Compaction 并替换消息/System Prompt；
4. 调用 `beforeModel` Hook，Hook 可改消息、工具、模型选项或停止 Run；
5. 调用 `config.model.stream(request)`；
6. 消费 Stream Event；
7. 组装最终 Assistant Message；
8. 调用 `afterModel` Hook。

### 15.4 Stream Event 分支

| 原生事件 | Runtime 行为 | 发出的事件 |
| --- | --- | --- |
| `text-delta` | 合并相邻 Text Part | `assistant-text-delta` |
| `reasoning-delta` | 合并 Reasoning、Redacted 和 Metadata | `assistant-reasoning-delta` |
| `tool-call-delta` | 按 Call ID/Index 拼接名称、JSON 和 Metadata | 最终形成 `tool-call` Part |
| `usage` | 累加 Token、Cache 和 Cost | `usage-updated` |
| `finish` | 保存 Stop/Error/Aborted 原因 | 影响本 Iteration/Run 结束方式 |

缺少工具名或无法解析参数时，不会凭空执行；错误信息写入 Invalid Tool Metadata，后续工具准备阶段生成错误 Tool Result，让模型有机会修正。

## 16. SDK：工具、策略与审批链路

### 16.1 工具准备

每个 Tool Call 先经过 `prepareToolExecution()`：

```text
查找 Tool
  → 检查参数解析错误
  → 检查 Provider-only Tool 是否禁止客户端执行
  → beforeTool Hook（可改 Input/Policy、Skip 或 Stop）
  → 合并 Tool Policy
  → enabled 检查
  → autoApprove 检查
  → 必要时 requestToolApproval()
  → 形成 PreparedToolExecution
```

与 VS Code 正式实现不同，SDK 原生 `beforeTool` Hook 位于审批判断之前，并且可以覆盖 Policy。文档和扩展开发中不要把它与 VS Code Handler 内“批准后执行的 `PreToolUse`”视为完全相同的时序。

### 16.2 审批

当 `policy.autoApprove === false`：

- 配置了 `requestToolApproval`：调用外部审批 UI/逻辑；
- 未配置回调：默认拒绝；
- 回调抛错：转为拒绝并记录原因；
- LocalRuntimeHost 在等待审批时把 Session 标为 `pending`，结束后恢复 `running`。

拒绝不会让整个 Runtime 直接抛错，而是生成 `isError: true` 的 Tool Result，供模型下一轮理解。

### 16.3 顺序或并行执行

`toolExecution` 默认为 `sequential`：按模型给出的顺序执行。配置为 `parallel` 时，所有已经完成准备和审批的调用通过 `Promise.all()` 执行。

并行只改变执行时间，不改变结果顺序：结果数组仍对应原 Tool Call 数组。设计有副作用的自定义工具时，应显式判断它们能否安全并行。

### 16.4 真实执行与结果

`executePreparedTool()` 会：

1. 发出 `tool-started`；
2. 对 Skip、Unknown Tool 直接构造错误结果；
3. 调用 `tool.execute(input, context)`；
4. 工具可用 `emitUpdate()` 发出长任务进度；
5. 捕获异常并转为错误输出；
6. 调用 `afterTool` Hook，Hook 可替换结果或停止 Run；
7. 构造 Role 为 `tool` 的 `tool-result` Message；
8. 发出 `tool-finished`；
9. 把 Tool Message 写入历史，进入下一 Iteration。

### 16.5 终止工具与 Completion Guard

工具声明 `lifecycle.completesRun === true` 且执行成功时，Runtime 直接以该 Tool Result 的文本作为最终输出。Cline 默认的典型终止工具是 `submit_and_exit`。

若 Completion Policy 要求终止工具，而模型只输出普通文本：

```text
无 Tool Call
  → getCompletionReminderMessages()
  → 加入系统式 User Reminder
  → 继续下一 Iteration
```

可选 `completionGuard()` 还能检查业务完成条件，并返回新的 Reminder。只有不存在 Reminder，或者终止工具成功，Run 才会正常完成。

## 17. SDK：Context Compaction、错误和取消分支

### 17.1 Context Compaction

LocalRuntimeHost 把 `createContextCompactionPrepareTurn()` 作为 `prepareTurn` 传入 Session/Agent Runtime。每次模型调用前，它可以：

- 估算当前上下文；
- 发出 Auto Compaction 状态通知；
- 采用 Basic、Agentic 或自定义压缩策略；
- 保护最新 Turn 和成对 Tool Call/Result；
- 用摘要消息替换较老消息；
- 把替换后的消息写回 Runtime State。

相关源码：

```text
sdk/packages/core/src/extensions/context/compaction.ts
sdk/packages/core/src/extensions/context/basic-compaction.ts
sdk/packages/core/src/extensions/context/agentic-compaction.ts
sdk/packages/core/src/extensions/context/compaction-shared.ts
```

### 17.2 Abort 与 Hook Stop

- `AgentRuntime.abort()` 触发 Abort Signal，模型流和工具都能读取该 Signal；
- `beforeRun`、`beforeModel`、`beforeTool`、`afterTool` 返回 `stop` 时抛出受控停止；
- 受控停止或 Abort 得到 `status: "aborted"`；
- 其他异常得到 `status: "failed"` 和 `run-failed`；
- `afterRun` 在成功、失败和取消路径都会执行。

### 17.3 空响应和模型错误

- 模型返回空 Content：失败；
- Stream Finish 为 Error 且没有 Tool Call：失败；
- Error Finish 但已形成 Tool Call：工具仍可形成结构化错误/执行链路，再由结果决定后续；
- 工具自己的异常：默认转 Tool Result，不等同于 Runtime 失败。

### 17.4 Mistake 与 Loop Detection

`SessionRuntime` 观察 `tool-started`、`tool-finished` 和 `turn-finished`：

- 同一工具签名连续重复：进入 Loop Tracker；
- 一轮所有工具都失败且没有成功工具：记录 Mistake；
- 出现成功工具：重置暂时错误累计；
- 软限制加入恢复提示；硬限制 Abort。

## 18. SDK 事件怎样到达 CLI/TUI/调用方

这一部分最容易混淆。实际有三层事件：

```text
AgentRuntimeEvent（底层原生事件）
  → RuntimeEventAdapter
AgentEvent（兼容旧 Agent facade 的事件）
  → AgentEventBridge / handleAgentEvent
CoreSessionEvent（ClineCore 对外 Session 事件）
  → CLI、TUI、Hub、SDK subscribe()
```

### 18.1 原生事件

Standalone `AgentRuntime` 的订阅者看到 `assistant-text-delta`、`assistant-reasoning-delta`、`tool-started`、`tool-updated`、`tool-finished`、`usage-updated` 等 `AgentRuntimeEvent`。

### 18.2 兼容事件适配

`RuntimeEventAdapter` 会：

- 抑制 `run-started` 和 `message-added`；
- 把每个 `assistant-text-delta` 投影为旧 `content_start(text)`；
- 把每个 Reasoning Delta 投影为 `content_start(reasoning)`；
- 在完整 Assistant Message 时发 `content_end`；
- 把工具开始/更新/结束投影为旧 Tool Content 事件；
- 根据累计 Usage 计算旧事件需要的增量 Usage；
- 把完成、失败、取消映射为旧 `done`/`error` 语义。

因此，使用 Standalone Agent 时应监听原生 Delta 事件；使用 `ClineCore.subscribe()` 时应处理 `CoreSessionEvent` 中包裹的旧 `AgentEvent`，不能在同一消费者里假设两种事件名同时出现。

### 18.3 Core Session 事件

对外类型位于：

```text
sdk/packages/core/src/types/events.ts
sdk/packages/core/src/runtime/host/local/agent-event-bridge.ts
sdk/packages/core/src/services/agent-events.ts
```

除 `agent_event` 外，Core 还会发出 `status`、`pending_prompts`、`pending_prompt_submitted`、`team_progress`、`hook`、`session_snapshot` 和 `ended`。CLI/TUI 应以 `sessionId` 和 Agent/Team 身份聚合事件，不能只按到达时间把所有输出混成一个 Agent。

## 19. 两套执行链路的关键差异

| 问题 | VS Code Task | SDK/ClineCore |
| --- | --- | --- |
| 运行中追加用户消息 | 可靠消费点主要是 `Task.ask()` 边界 | 明确定义 `queue` 与 `steer` |
| 循环单位 | `recursivelyMakeClineRequests()` 递归 | `AgentRuntime.execute()` 的 `while` |
| XML 工具 | 支持，且是历史主协议 | AgentRuntime 内部统一结构化 Tool Call |
| Native 工具 | 解析后汇入 `ToolExecutor` | Provider Adapter 直接产生 Tool Call Delta |
| Hook 时序 | Handler 内 `PreToolUse` 在批准后 | `beforeTool` 在策略与批准前 |
| 完成 | `attempt_completion` + 用户确认 | Terminal Tool/`submit_and_exit` + Completion Guard |
| 压缩 | Task ContextManager/Summary | `prepareTurn` Compaction |
| 历史 | UI History 与 API History 分离 | Runtime Messages 回写 Session Conversation |
| 事件 | Webview `ClineMessage` | Runtime → Legacy → Core 三层投影 |
| 多 Agent | VS Code Subagent Handler/Runner | Spawn Tool、Team Runtime、聚合 Usage/Events |

## 20. 一条消息的完整时序示例

以“修改文件并运行测试”为例，VS Code 可能执行：

```text
用户发送任务
  → startTask 解析文本与附件
  → Hook 注入规则
  → 第 1 次模型请求
  → 模型调用 read_file
  → 用户/自动批准
  → 读取结果回填
  → 第 2 次模型请求
  → 模型调用 replace_in_file
  → 用户批准 → PreToolUse → 修改 → PostToolUse
  → 保存 Checkpoint 和 Tool Result
  → 第 3 次模型请求
  → 模型调用 execute_command 运行测试
  → 命令输出回填
  → 第 4 次模型请求
  → 模型调用 attempt_completion
  → Double Check/TaskComplete Hook/用户确认
  → Task 结束
```

SDK/CLI 对应时序可能是：

```text
ClineCore.start(prompt)
  → Session/Manifest 创建
  → AgentRuntime iteration 1：read_file
  → beforeTool → Policy → Approval → tool.execute
  → iteration 2：apply_patch
  → Tool Result
  → iteration 3：execute_command
  → Tool Result
  → iteration 4：submit_and_exit
  → Terminal Tool 成功
  → AgentRunResult
  → 保存 messages/usage/manifest
  → CoreSessionEvent done/ended
```

如果用户在 SDK 第 2 次 Iteration 时发送“不要改测试文件”：

- `delivery="steer"`：在下一次模型请求前注入当前 Run；
- `delivery="queue"`：当前 Run 结束后作为一个新 Turn 执行。

## 23. 阅读和调试建议

若要用断点快速验证一条消息，建议按以下顺序：

1. VS Code：`handleSendMessage()` → `newTask()` → `Task.startTask()`；
2. 在 `recursivelyMakeClineRequests()` 观察本轮 User Content；
3. 在 `attemptApiRequest()` 检查最终 System Prompt、History 和 Tool Definitions；
4. 在 Stream 分支观察 Text、Reasoning、XML/Native Tool 的组装；
5. 在 `ToolExecutor.executeTool()` 和具体 Handler 观察批准、Hook、实际副作用；
6. 在 `pushToolResult()` 观察进入下一轮的结果；
7. 在 Completion Handler 判断为何结束或继续。

SDK/CLI 则按：

1. `ClineCore.start()/send()`；
2. `LocalRuntimeHost.runTurn()/executeTurn()`；
3. `SessionRuntime.executeRunInternal()`；
4. `AgentRuntime.execute()`；
5. `generateAssistantMessage()`；
6. `prepareToolExecution()/executePreparedTool()`；
7. `RuntimeEventAdapter` 与 `AgentEventBridge`；
8. `persistSessionMessages()`。

抓取日志时至少同时记录 `sessionId/taskId`、`agentId`、`runId`、`iteration`、`toolCallId` 和 Provider/Model。只有 `sessionId` 无法区分 Team/Subagent，只有时间戳也无法可靠还原并行工具的因果关系。

## 24. 总结

这个项目的智能体执行本质是“消息驱动的模型—工具闭环”：用户消息先经过规则、附件、模式和上下文处理；模型流被拆成文本、推理、工具和用量；工具经过校验、策略、批准与 Hook 后执行；结果再写回历史触发下一次模型迭代；直到完成策略通过、用户确认、终止工具成功或发生取消/错误。

改造时最重要的边界是：

- 不把一个用户消息等同于一次模型请求；
- 不把 UI History 等同于 Provider History；
- 不把 XML Tool 解析层等同于统一工具执行层；
- 不把 VS Code 的 `PreToolUse` 时序套用到 SDK 的 `beforeTool`；
- 不把 Standalone `AgentRuntimeEvent` 与 ClineCore 的兼容 `AgentEvent/CoreSessionEvent` 混用；
- 不把 `queue` 与 `steer` 当成同一种运行中消息。

掌握这些边界后，无论是修改 UI 交互、接入新模型、增加工具、调整审批和 Hook、扩展聊天记录，还是引入 Subagent/Team，都能找到正确的主链路落点，而不会在错误层级重复实现。
