# Cline 提供给大模型的工具与扩展脚手架

> 本文盘点的是“可以改变模型上下文、给模型增加能力或介入 Agent 生命周期”的脚手架。项目中存在两套并行实现：正式 VS Code 扩展位于 `apps/vscode`，新 SDK/CLI 位于 `sdk/packages/*` 与 `apps/cli`。两套实现名称相似，但工具注册、配置目录和运行时接口并不相同，改造时不能交叉套用。

## 1. 总体结论

项目给大模型提供的能力不只是若干文件工具，而是一套分层扩展体系：

```text
模型可见层
├── 内置工具：读写文件、搜索、命令、网页、提问、完成任务
├── 动态工具：MCP Tool、自定义 Agent、Subagent、Team Tool
├── Skill：按需加载的专业操作说明
├── Rule / AGENTS.md：每轮注入的长期约束
└── Workflow / Command：用户显式触发的任务模板

运行控制层
├── Prompt Variant / Tool Preset：决定本轮暴露哪些工具
├── Tool Policy / Auto Approve：决定是否启用、是否需要批准
├── .clineignore / 工作区边界：限制文件访问
├── Hook：在任务、提示、工具和压缩阶段观察、修改或阻断
└── Context Compaction：在上下文过大时截断或总结

扩展接入层
├── MCP：把外部 Server 的工具动态转换为模型原生工具
├── Plugin / ContributionRegistry：注册工具、规则、命令、Provider 等
├── Configured Agent / Subagent / Team：把专用智能体变成工具
└── SDK createTool()：通过 JSON Schema/Zod 创建任意模型工具
```

正式 VS Code 扩展偏向“内置工具 + MCP + 文件约定”；新 SDK/CLI 则进一步把 Tool、Plugin、Hook、Agent Team 都抽象成公共 API。

## 2. 正式 VS Code 扩展的工具体系

### 2.1 工具从哪里注册和执行

主链路如下：

```text
apps/vscode/src/shared/tools.ts
  ClineDefaultTool：稳定工具 ID
        ↓
apps/vscode/src/core/prompts/system-prompt/tools/
  工具描述、参数和提示词定义
        ↓
apps/vscode/src/core/prompts/system-prompt/registry/ClineToolSet.ts
  按 Prompt Variant、模型和运行上下文筛选工具
        ↓
apps/vscode/src/core/task/ToolExecutor.ts
  权限、批准、Hook、并行调用、Checkpoint
        ↓
apps/vscode/src/core/task/tools/ToolExecutorCoordinator.ts
  工具名到 Handler 的路由
        ↓
apps/vscode/src/core/task/tools/handlers/*
  实际文件、终端、浏览器、MCP 等操作
```

`ClineToolSet.getEnabledTools()` 说明“枚举中存在”不等于“每次都暴露给模型”。最终集合还受到以下条件控制：

- Prompt Variant 的 `tools` 列表；
- 模型族及对应工具规格；
- Plan/Act 模式；
- Native Tool Calling 开关；
- Web Tool、Subagent、MCP 等功能开关；
- 当前是否已经处于 Subagent 运行中；
- Provider 对工具格式和名字长度的限制。

### 2.2 全部默认工具

`apps/vscode/src/shared/tools.ts` 中的 `ClineDefaultTool` 是当前权威清单。

| 工具 ID | 主要能力 | 主要实现 |
| --- | --- | --- |
| `ask_followup_question` | 向用户追问并取得文本、图片或文件反馈 | `AskFollowupQuestionToolHandler.ts` |
| `attempt_completion` | 宣告任务完成，展示结果，可选执行结束命令 | `AttemptCompletionHandler.ts` |
| `execute_command` | 在终端执行命令并收集输出 | `ExecuteCommandToolHandler.ts`、`integrations/terminal/` |
| `replace_in_file` | 用 SEARCH/REPLACE 形式编辑已有文件 | `WriteToFileToolHandler.ts` |
| `read_file` | 读取文本或图片，支持行范围和大小限制 | `ReadFileToolHandler.ts` |
| `write_to_file` | 创建或整体写入文件 | `WriteToFileToolHandler.ts` |
| `search_files` | 在工作区正则搜索 | `SearchFilesToolHandler.ts` |
| `list_files` | 列出目录，可递归 | `ListFilesToolHandler.ts` |
| `list_code_definition_names` | 提取源文件中的定义名 | `ListCodeDefinitionNamesToolHandler.ts` |
| `browser_action` | 启动浏览器、点击、输入、滚动、关闭 | `BrowserToolHandler.ts`、`services/browser/` |
| `use_mcp_tool` | 调用指定 MCP Server 的 Tool | `UseMcpToolHandler.ts` |
| `access_mcp_resource` | 读取 MCP Resource | `AccessMcpResourceHandler.ts` |
| `load_mcp_documentation` | 加载 MCP 使用/构建说明 | `LoadMcpDocumentationHandler.ts` |
| `new_task` | 从当前上下文创建新任务 | `NewTaskHandler.ts` |
| `plan_mode_respond` | 在 Plan 模式向用户给出计划并交互 | `PlanModeRespondHandler.ts` |
| `act_mode_respond` | 从计划阶段进入执行交互 | `ActModeRespondHandler.ts` |
| `focus_chain` | 更新任务清单/Focus Chain | 由 Task 的 Focus Chain 流程处理，不走普通 Handler |
| `web_fetch` | 获取 URL 内容 | `WebFetchToolHandler.ts` |
| `web_search` | 执行 Web 搜索 | `WebSearchToolHandler.ts` |
| `condense` | 让模型给出对话摘要并收缩后续上下文 | `CondenseHandler.ts` |
| `summarize_task` | 在上下文接近上限时生成续接摘要 | `SummarizeTaskHandler.ts` |
| `report_bug` | 整理并提交/打开 Bug 报告 | `ReportBugHandler.ts` |
| `new_rule` | 创建 Cline Rule 文件 | 复用 `WriteToFileToolHandler.ts` |
| `apply_patch` | 应用 Patch 格式的多文件修改 | `ApplyPatchHandler.ts` |
| `generate_explanation` | 针对代码范围生成解释 | `GenerateExplanationToolHandler.ts` |
| `use_skill` | 按需读取并注入 Skill 完整正文 | `UseSkillToolHandler.ts` |
| `use_subagents` | 调用配置化 Subagent | `SubagentToolHandler.ts` |

需要注意三个实现细节：

1. `replace_in_file`、`write_to_file` 和 `new_rule` 复用同一写文件 Handler，但注册名和提示语义不同；
2. Native GPT 变体可使用 `apply_patch`，并不保证同时暴露旧式写文件工具；
3. `focus_chain` 在 `ToolExecutorCoordinator` 的普通 Handler 表中返回 `undefined`，它是 Task 级特殊能力，不能照搬普通 Handler 的添加方式。

### 2.3 ToolExecutor 提供的运行保障

`apps/vscode/src/core/task/ToolExecutor.ts` 不只负责调用函数，还统一处理：

- Plan 模式写操作限制；
- Auto Approve 和人工审批；
- `.clineignore` 与工作区外路径提示；
- `PreToolUse`、`PostToolUse` Hook；
- 工具失败结果回填；
- Tool Use ID 与 Tool Result 配对；
- Checkpoint 保存；
- 单工具/并行工具调用策略；
- MCP 动态名字归一化；
- 用户拒绝、补充文本、图片和文件反馈；
- 将工具结果注入下一轮 `user` 内容。

因此新增工具时，仅在 System Prompt 中写一个 XML 标签是不够的；必须同时打通规格、启用条件、Coordinator、Handler、批准策略和结果回填。

## 3. 新 SDK/CLI 的默认工具体系

### 3.1 默认工具

新运行时的权威名称位于 `sdk/packages/core/src/extensions/tools/constants.ts`：

| 工具 | 功能 | 工厂函数 |
| --- | --- | --- |
| `read_files` | 批量读取文本或图片，支持行范围 | `createReadFilesTool()` |
| `search_codebase` | 批量正则搜索代码库 | `createSearchTool()` |
| `run_commands` | 执行一个或多个 Shell/PowerShell 命令 | `createBashTool()` / `createWindowsShellTool()` |
| `fetch_web_content` | 获取网页内容 | `createWebFetchTool()` |
| `apply_patch` | 应用标准 Patch | `createApplyPatchTool()` |
| `editor` | 结构化编辑文件 | `createEditorTool()` |
| `skills` | 按名称加载 Skill 指令 | `createSkillsTool()` |
| `ask_question` | 请求宿主向用户提问 | `createAskQuestionTool()` |
| `submit_and_exit` | 提交最终结果并结束自动化运行 | `createSubmitAndExitTool()` |

定义、Schema 和执行器分别位于：

```text
sdk/packages/core/src/extensions/tools/definitions.ts
sdk/packages/core/src/extensions/tools/schemas.ts
sdk/packages/core/src/extensions/tools/executors/
sdk/packages/core/src/extensions/tools/runtime.ts
```

### 3.2 Tool Preset

`sdk/packages/core/src/extensions/tools/presets.ts` 提供五套组合：

| Preset | 面向场景 | 关键差异 |
| --- | --- | --- |
| `act` | 完整编码与任务执行 | 文件、搜索、命令、网页、编辑、Skill、提问、Spawn、Team |
| `plan` | 规划和分析 | 禁用编辑器，但当前源码仍启用 `run_commands` |
| `search` | 代码检索 | 只保留读取、搜索，并允许 Spawn/Team |
| `minimal` | 极简命令任务 | 主要保留命令和 Spawn |
| `yolo` | 可信环境自动化 | 命令、编辑、提交退出，并自动批准工具 |

源码注释称 Plan 是“read-only, no shell access”，但配置实际为 `enableBash: true`。以当前代码为准，不能把 Plan 当作绝对无命令权限；若产品需要严格只读，必须修正配置并增加 Tool Policy 测试。

### 3.3 用 `createTool()` 创建自定义工具

公共工厂位于 `sdk/packages/shared/src/tools/create.ts`，支持：

- Zod 或 JSON Schema 输入；
- 运行前类型校验；
- 超时；
- 可重试标记和最大重试次数；
- `AgentToolContext`，包含 session、agent、run、iteration、AbortSignal；
- Tool Policy、审批和生命周期回调；
- 任意结构化输出。

最小示例：

```ts
import { createTool, zodToJsonSchema } from "@cline/shared"
import { z } from "zod"

const Input = z.object({ city: z.string().min(1) })

export const weatherTool = createTool({
  name: "get_weather",
  description: "查询指定城市天气",
  inputSchema: zodToJsonSchema(Input),
  timeoutMs: 10_000,
  retryable: true,
  maxRetries: 1,
  execute: async (input, context) => {
    const { city } = Input.parse(input)
    return { city, weather: "sunny", sessionId: context.sessionId }
  },
})
```

若只使用 `createTool()`，还需要把返回的 `AgentTool` 放进 `AgentConfig.tools`，或通过 Plugin 的 `api.registerTool()` 注册。

## 4. Skill 脚手架

### 4.1 Skill 的作用

Skill 是“可发现、按需加载的专业说明”，适合放入较长的操作步骤、领域约束和模板。它与 Tool 的区别是：

- Tool 提供可执行函数；
- Skill 提供模型如何完成某类任务的指令；
- Rule 默认影响每轮；
- Skill 通常只在模型调用 `use_skill`/`skills` 时加载正文。

这种懒加载设计可以只把 Skill 的名称和描述放入初始上下文，避免把所有说明一次性塞给模型。

### 4.2 VS Code 扩展的 Skill 目录与格式

扫描逻辑位于：

```text
apps/vscode/src/core/context/instructions/user-instructions/skills.ts
apps/vscode/src/core/storage/disk.ts
apps/vscode/src/core/task/tools/handlers/UseSkillToolHandler.ts
```

支持的来源包括：

```text
~/.cline/skills
~/.agents/skills
<workspace>/.clinerules/skills
<workspace>/.cline/skills
<workspace>/.claude/skills
<workspace>/.agents/skills
企业远程配置 remoteGlobalSkills
```

每个 Skill 是一个目录，入口必须为 `SKILL.md`：

```markdown
---
name: release-audit
description: 检查发布版本、变更日志和 Git 标签
---

# 发布审计

1. 读取 package.json。
2. 对比 CHANGELOG。
3. 检查标签和未提交变更。
```

正式扩展要求目录名与 `frontmatter.name` 一致。源码合并顺序体现的覆盖优先级是：远程企业 Skill 高于磁盘全局 Skill，全局 Skill 高于项目 Skill；同时存在全局、项目和远程开关，远程项还可 `alwaysEnabled`。

### 4.3 SDK/CLI 的 Skill

新实现由 `user-instruction-config-loader.ts`、`user-instruction-plugin.ts` 和统一文件 Watcher 管理。默认搜索：

```text
<workspace>/.clinerules/skills
<workspace>/.cline/skills
<workspace>/.agents/skills
~/.cline/skills
~/.agents/skills
插件包自己的 skills/
```

SDK 接受 `SKILL.md` 中的 `name`、`description`、`disabled`/`enabled` 和正文，并支持热更新。Skill 既可以注册为 `skills` 工具，也可以转成 Slash Command；同名或只写短名产生歧义时，执行器会要求使用完整 ID。

## 5. Rule、AGENTS.md 与 Workflow

### 5.1 Rule

Rule 是稳定注入模型上下文的约束，适合编码规范、目录边界、安全规则和团队约定。

正式扩展支持：

```text
.clinerules
.clinerules/*
.cursor/rules/*.mdc
.cursorrules
.windsurfrules
AGENTS.md
远程企业 Rules
```

主要源码：

```text
apps/vscode/src/core/context/instructions/user-instructions/cline-rules.ts
apps/vscode/src/core/context/instructions/user-instructions/external-rules.ts
apps/vscode/src/core/context/instructions/user-instructions/RuleContextBuilder.ts
```

SDK/CLI 通过 `resolveRulesConfigSearchPaths()` 扫描工作区 `AGENTS.md`、`.clinerules`、`.cline/rules`、全局 `~/.agents/AGENTS.md`、`~/.cline/rules` 和 Documents/Cline/Rules，并允许 Plugin 用 `registerRule()` 动态贡献内容。

### 5.2 Workflow 与 Slash Command

Workflow 是用户主动选择的任务模板，不应当无条件注入每一轮。正式扩展读取 `.clinerules/workflows/` 和全局 Workflows；SDK/CLI 还读取 `.cline/workflows/`，通过 `runtime-commands.ts` 暴露为 Slash Command。

适用例子：

- `/release`：执行版本发布检查；
- `/review`：按固定清单进行代码审查；
- `/migration`：生成迁移计划；
- `/incident`：收集故障证据并生成报告。

## 6. Hook 脚手架

### 6.1 VS Code 扩展 Hook

正式扩展的有效 Hook 名称来自 `apps/vscode/src/core/hooks/hook-factory.ts`：

| Hook | 时机与用途 |
| --- | --- |
| `TaskStart` | 新任务开始，可注入上下文或取消 |
| `TaskResume` | 恢复历史任务 |
| `TaskCancel` | 任务取消后的清理/记录 |
| `TaskComplete` | 任务完成后的通知或审计 |
| `PreToolUse` | 工具批准后、真正执行前，可检查输入、注入上下文或取消 |
| `PostToolUse` | 工具执行后记录结果或补充上下文 |
| `UserPromptSubmit` | 用户提示进入任务前检查或扩展 |
| `Notification` | 用户注意力通知 |
| `PreCompact` | 上下文压缩前读取历史、修改上下文或取消 |

Hook 搜索目录为运行时 `--hooks-dir`、全局 `Documents/Cline/Hooks` 和各工作区 `.clinerules/hooks`。Unix 使用无扩展名可执行文件，Windows 使用 `.ps1`。不同目录中的 Hook 可并发执行，源码明确不保证目录间顺序。

### 6.2 SDK/CLI Hook

SDK 文件 Hook 名称还包括 `TaskError` 和 `SessionShutdown`，映射定义位于 `sdk/packages/core/src/hooks/hook-file-config.ts`：

```text
TaskStart, TaskResume, TaskCancel, TaskComplete, TaskError,
PreToolUse, PostToolUse, UserPromptSubmit, PreCompact, SessionShutdown
```

支持无扩展名、Shell、JavaScript/TypeScript、Python、PowerShell 等文件。示例位于 `sdk/examples/hooks/`。

SDK 还有进程内 `AgentRuntimeHooks`：

```text
beforeRun, afterRun,
beforeModel, afterModel,
beforeTool, afterTool,
onEvent
```

进程内 Hook 能替换模型请求消息、修改工具输入/结果、停止运行并观察完整 `AgentRuntimeEvent`，比外部脚本更适合低延迟的产品逻辑；外部脚本更适合审计、通知和语言无关集成。

## 7. MCP 脚手架

### 7.1 VS Code 扩展 MCP

正式扩展的 MCP 实现在 `apps/vscode/src/services/mcp/`，提供：

- stdio、SSE、Streamable HTTP Transport；
- Tool、Resource、Prompt；
- OAuth；
- Marketplace；
- Server 开关、连接状态和超时；
- Tool Auto Approve；
- 远程企业允许列表和远程 Server。

在 Native Tool Calling 下，`ClineToolSet.mcpToolToClineToolSpec()` 会把每个 MCP Tool 转成独立的模型工具。工具名由 Server UID、内部分隔符和 MCP Tool Name 组合；超过 Provider 常见的 64 字符限制时会跳过注册。执行阶段再由 Coordinator 归一化为 `use_mcp_tool` Handler。

### 7.2 SDK/CLI MCP

新实现位于 `sdk/packages/core/src/extensions/mcp/`：

```text
config-loader.ts       读取 Server 配置
client.ts              Transport 客户端
manager.ts             注册、连接、缓存 tools/list、串行化 Server 操作
tools.ts               MCP Tool → AgentTool
oauth.ts               OAuth 状态
policies.ts            MCP Tool Policy
plugin-server-registration.ts  接收插件贡献的 MCP Server
```

`createMcpTools()` 最终仍返回普通 `AgentTool[]`，因此 MCP 工具自然复用超时、重试、审批、事件和持久化链路。

## 8. Plugin / Extension 脚手架

通用 TypeScript Plugin 是新 SDK 的能力，正式 `apps/vscode` 目前仍以自身内置模块、MCP 和文件配置为主，不应假定它直接加载同一套 SDK Plugin。

### 8.1 Plugin 能贡献什么

`sdk/packages/shared/src/extensions/contribution-registry.ts` 定义的能力包括：

| Manifest capability | 注册 API | 作用 |
| --- | --- | --- |
| `tools` | `registerTool()` | 增加模型可调用工具 |
| `commands` | `registerCommand()` | 增加 Slash Command |
| `rules` | `registerRule()` | 增加 System Prompt Rule |
| `messageBuilders` | `registerMessageBuilder()` | 在发给 Provider 前重写消息 |
| `providers` | `registerProvider()` | 增加 Provider 元数据/实现接入 |
| `automationEvents` | `registerAutomationEventType()` | 声明并发送自动化事件 |
| `mcp` | `registerMcpServer()` | 注册 MCP Server |
| `hooks` | `extension.hooks` | 介入 AgentRuntime 生命周期 |
| `skills` | Manifest 声明 + 包内 `skills/` | 随插件分发 Skill |

Plugin 搜索路径为：

```text
<workspace>/.cline/plugins
~/.cline/plugins
~/Documents/Cline/Plugins
显式配置的模块路径
```

Loader 支持单文件、目录入口和 package.json 声明，按 `name` 去重，后加载的同名插件覆盖前者并产生诊断 Warning。Manifest 还能用 `providerIds`、`modelIds` 限定生效范围。运行模式支持进程内和 Sandbox；需要访问路径时应使用 `PluginSetupContext.workspaceInfo`，而不是假设 `process.cwd()` 就是会话工作区。

### 8.2 最小 Plugin

```ts
import type { AgentPlugin } from "@cline/core"
import { createTool } from "@cline/shared"

export const plugin: AgentPlugin = {
  name: "company-tools",
  manifest: { capabilities: ["tools", "rules", "hooks"] },
  setup(api, ctx) {
    api.registerRule({
      id: "company-tools:no-secret-output",
      content: "不要在回答或工具参数中输出密钥。",
      source: "company-tools",
    })
    api.registerTool(createTool({
      name: "lookup_service_owner",
      description: "查询服务负责人",
      inputSchema: {
        type: "object",
        properties: { service: { type: "string" } },
        required: ["service"],
        additionalProperties: false,
      },
      execute: async (input) => ({ input, workspace: ctx.workspaceInfo?.rootPath }),
    }))
  },
  hooks: {
    beforeTool(context) {
      if (context.tool.name === "run_commands") {
        // 可在这里审查或阻断危险输入
      }
    },
  },
}
```

完整示例位于 `sdk/examples/plugins/`，涵盖天气工具、后台命令、Gitignore 文件保护、自定义压缩、环境变量阻断、自动化事件、Web 搜索、OpenRouter Provider、TypeScript LSP 和 Agents Squad。

## 9. Subagent、Configured Agent 与 Team

### 9.1 正式 VS Code Subagent

`apps/vscode/src/core/task/tools/subagent/AgentConfigLoader.ts` 从 `~/Documents/Cline/Agents/*.yaml` 读取：

```yaml
---
name: security-reviewer
description: 审查代码安全问题
modelId: optional-model
tools: [read_file, search_files, list_files]
skills: [secure-coding]
---

你是安全审查智能体，只分析证据，不修改文件。
```

配置会被热监听，并生成 `use_subagent_<name>` 动态工具；名字超过 64 字符时会截断并加哈希。父任务通过 `UseSubagentsToolHandler` 运行专用系统提示、工具集合、Skill 和可选模型。Subagent 内不会再次暴露动态 Subagent 工具，以避免无界递归。

### 9.2 SDK Configured Agent 与 `spawn_agent`

SDK 从以下目录读取 YAML：

```text
<workspace>/.cline/agents
~/.cline/agents
```

Schema 支持 `name`、`description`、`tools`、`skills`、`providerId`、`modelId`、`maxIterations` 和正文 System Prompt。`createConfiguredAgentTools()` 可把每个配置生成专用工具，`createSpawnAgentTool()` 则提供通用 `spawn_agent`，允许传入任务和专用系统提示。

### 9.3 Agent Team

Team 是比单次 Subagent 更完整的多智能体协作层。`sdk/packages/core/src/extensions/tools/team/team-tools.ts` 当前定义：

```text
team_spawn_teammate       team_shutdown_teammate
team_status               team_task
team_run_task             team_cancel_run
team_list_runs            team_await_runs
team_send_message         team_broadcast
team_read_mailbox         team_mission_log
team_cleanup              team_create_outcome
team_attach_outcome_fragment
team_review_outcome_fragment
team_finalize_outcome     team_list_outcomes
```

这些工具覆盖成员生命周期、任务队列、异步 Run、邮箱、广播、任务日志和最终产物合并。Team 会话和子会话还有独立持久化关系，不能只把它理解为并行调用几个函数。

## 10. 如何选择脚手架

| 需求 | 推荐扩展点 |
| --- | --- |
| 给模型增加一个真实可执行能力 | SDK `createTool()`；正式扩展新增 Tool Handler |
| 接入已有外部服务且希望跨客户端复用 | MCP Server |
| 给模型一套较长的专业步骤 | Skill |
| 对所有任务持续施加规范 | Rule / `AGENTS.md` |
| 让用户主动启动固定流程 | Workflow / Slash Command |
| 工具执行前做合规拦截 | `PreToolUse` / `beforeTool` |
| 记录任务完成或发送通知 | `TaskComplete` / `afterRun` |
| 改写 Provider 上下文或自定义压缩 | Plugin Message Builder / `beforeModel` / Compaction |
| 把复杂工作交给独立角色 | Configured Agent / `spawn_agent` |
| 多角色长期协作、通信和汇总 | Agent Team |
| 给任意宿主成套分发工具、Rule、Hook、Provider | SDK Plugin |

## 11. 改造检查清单

新增能力时至少验证：

1. 模型是否真的能在当前 Variant/Preset 中看到它；
2. Tool 名是否满足 Provider 长度和字符限制；
3. 输入 Schema 是否禁止意外字段并覆盖失败路径；
4. Plan/Act、Tool Policy 和 Auto Approve 是否符合风险等级；
5. 文件路径是否经过工作区、`.clineignore` 和符号链接检查；
6. 命令、网络和 MCP 输出是否设置大小及超时限制；
7. Tool Call 与 Tool Result 是否使用稳定 ID 配对；
8. Hook 的修改、阻断和错误是否有测试；
9. 并行工具是否会竞争写同一文件或状态；
10. Subagent/Team 是否能取消、超时、归集用量并保存子会话；
11. 结果是否进入聊天持久化，而不只是显示在 UI；
12. 日志、遥测和导出内容是否避免泄露密钥。
