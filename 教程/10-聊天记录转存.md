# 将聊天全过程按会话转存为 Markdown 的改造方案

> 目标：聊天过程中，把用户、模型、工具、Hook、状态和附件信息实时转存到另一个可配置文件夹；每个会话使用独立目录，所有事件记录使用 Markdown。项目有正式 VS Code 扩展和新 SDK/CLI 两套运行时，公共数据模型可以复用，但接入点必须分别实现。

## 1. 推荐方案

不要在会话结束后只读取 `ui_messages.json` 或 `*.messages.json` 再生成一个 Markdown。正确方案是在现有存储旁新增独立的 **Append-only Transcript Recorder**：

```text
VS Code Task ─────┐
                  ├── TranscriptEvent ── RedactionPolicy ── MarkdownTranscriptWriter
SDK AgentRuntime ─┘                                  │
                                                    ├── 会话 Markdown 目录
                                                    └── attachments/
```

Recorder 只旁路观察和归档，不替代现有聊天恢复存储。这样可以同时满足：

- 在 UI partial 被覆盖前记录 delta；
- 在 Tool Result 被格式化或截断前记录原始工具输出；
- 在 Context Compaction 替换消息前记录原始快照；
- 即使当前会话 JSON 后来被覆盖、回退或删除，转存仍保留旧事件；
- VS Code、CLI、Subagent 和 Team 可以共享一种 Markdown 格式。

## 2. 能做到与不能做到的范围

### 2.1 可以归档

- 用户原始文本、规范化文本和最终送入模型的文本；
- 用户图片、文件路径、读取后的文件文本及附件哈希；
- 模型返回的 text/reasoning delta 和最终聚合消息；
- Tool Use ID、工具名、输入参数、批准/拒绝、开始/结束时间；
- 模型最终看到的 Tool Result；
- 在工具边界额外采集到的完整 stdout、stderr、MCP 响应等原始结果；
- Hook 输入、输出、取消、错误和上下文修改；
- 模型、Provider、Token、费用、结束原因、压缩、回退和取消事件；
- Lead、Subagent、Teammate 的身份和父子关联。

### 2.2 无法归档

- Provider 没有通过 API 返回的隐式 Chain of Thought；
- Provider 服务端内部调度、缓存和安全处理过程；
- 改造上线前已经被截断、压缩或覆盖，且没有其他备份的内容；
- 没有在工具底层接入 Recorder 时已经丢弃的原始字节。

“记录全部”在工程上应定义为“记录客户端实际收到或产生的全部允许归档事件”，不能承诺获取模型服务端未返回的信息。

## 3. 转存目录设计

建议根目录由设置 `transcript.rootDirectory` 指定，每个会话创建一次固定目录：

```text
<export-root>/
└── <safe-title>__<session-id>/
    ├── README.md
    ├── manifest.md
    ├── 000001-user.md
    ├── 000002-assistant-reasoning-delta.md
    ├── 000003-assistant-reasoning.md
    ├── 000004-assistant-output.md
    ├── 000005-tool-call.md
    ├── 000006-tool-result.md
    ├── 000007-session-complete.md
    └── attachments/
        ├── 000001-image.png
        └── 000002-report.pdf
```

命名规则：

1. `<safe-title>` 来自会话标题；没有标题时用首条用户消息的一行摘要；
2. 去除 `/\\:*?"<>|`、控制字符和尾部点/空格，并设置最大长度；
3. 必须拼接稳定的 `sessionId/taskId`，否则同名会话会互相覆盖；
4. 目录创建后不要随着标题变化反复重命名，标题更新写入 `manifest.md` 即可；
5. 事件文件使用全局递增的六位 `sequence`，不能只依赖毫秒时间戳；
6. Subagent/Team 可写同一根会话目录，但每个事件必须带 `agentId` 和父级 ID。

### 3.1 为什么采用“一事件一文件”

直接反复追加一个超大的 `conversation.md` 实现简单，但进程在写入中断、多个 Agent 并发、需要去重或补写最终聚合消息时更难保证一致性。一事件一文件具有以下优势：

- 临时文件加 rename 可保证单个事件原子落盘；
- 序号天然定义稳定顺序；
- 可以按 Event ID 去重；
- 多 Agent 只需共享序号分配器和 Session Lock；
- 单个大工具结果不会破坏整份会话文档。

`README.md` 作为索引，可在事件写入后更新链接，或在会话结束时一次生成。若业务强制要求一个文件，可额外生成 `conversation.md` 聚合视图，但事件文件仍应作为事实来源。

## 4. 统一事件模型

建议新增一个与 UI、Provider 类型解耦的内部模型：

```ts
export type TranscriptEventKind =
  | "session-start"
  | "session-resume"
  | "session-complete"
  | "session-cancel"
  | "user-input"
  | "user-attachment"
  | "assistant-text-delta"
  | "assistant-reasoning-delta"
  | "assistant-message"
  | "tool-call"
  | "tool-update"
  | "tool-result"
  | "hook"
  | "usage"
  | "compaction"
  | "checkpoint"
  | "error"

export interface TranscriptEvent {
  version: 1
  eventId: string
  sequence?: number               // Writer 在锁内分配
  timestamp: string               // ISO 8601
  kind: TranscriptEventKind
  sessionId: string
  taskId?: string
  agentId?: string
  parentAgentId?: string | null
  conversationId?: string
  runId?: string
  iteration?: number
  source: "vscode" | "sdk" | "cli" | "subagent" | "team"
  payload: Record<string, unknown>
}
```

同一内容建议保存三层语义，避免把用户输入、界面显示和 Provider 输入混为一谈：

```ts
payload: {
  raw?: unknown,             // 客户端刚收到或工具刚产生的值
  displayed?: unknown,       // 用户界面实际看到的值
  providerVisible?: unknown, // 最终进入模型上下文的值
  truncation?: {
    applied: boolean,
    originalBytes?: number,
    retainedBytes?: number,
    reason?: string
  }
}
```

若三层完全相同，可以只写一份正文并在元数据标记 `representation: raw-and-provider-visible`，避免文件膨胀。

## 5. Markdown 事件格式

每个事件文件由 YAML Front Matter 和可读正文组成：

````markdown
---
version: 1
event_id: evt_01J...
sequence: 42
timestamp: 2026-07-14T10:20:31.456+08:00
kind: tool-result
session_id: 01J...
agent_id: lead
iteration: 3
tool_name: execute_command
tool_call_id: call_abc
is_error: false
representation: raw-and-provider-visible
sha256: 0b8...
---

# 工具结果：execute_command

## 原始输出

```text
命令输出……
```

## 模型可见结果

```text
经过限制或格式化后送给模型的内容……
```
````

Writer 必须正确处理正文中出现的反引号。可动态选择比正文最长连续反引号多一个的围栏长度，或对结构化大对象使用缩进代码块。参数对象建议稳定排序后以 `json` 围栏输出。

`manifest.md` 至少应记录：

- Session/Task ID、当前标题、创建时间、结束时间和状态；
- 来源、工作区、插件版本、Schema 版本；
- Provider 和 Model，但不写 API Key；
- Lead/Subagent/Team 关系；
- 设置快照和脱敏策略；
- 最后成功写入的 `sequence`；
- 附件清单及 SHA-256；
- 是否包含 delta、reasoning、系统提示词和原始工具 I/O；
- 已知缺失或发生截断的内容。

## 6. 建议新增的公共组件

可以先在两套实现各自建立适配层，稳定后再抽到共享包。

### 6.1 VS Code 扩展

```text
apps/vscode/src/core/transcript/
├── TranscriptEvent.ts
├── TranscriptRecorder.ts
├── MarkdownTranscriptWriter.ts
├── AttachmentExporter.ts
├── RedactionPolicy.ts
├── TranscriptSettings.ts
└── __tests__/
```

### 6.2 SDK/CLI

```text
sdk/packages/core/src/transcript/
├── transcript-event.ts
├── transcript-recorder.ts
├── markdown-transcript-writer.ts
├── attachment-exporter.ts
└── redaction-policy.ts
```

核心职责：

| 组件 | 职责 |
| --- | --- |
| `TranscriptRecorder` | 接收事件、补充 Session/Agent 元数据、去重、排队、flush/close |
| `MarkdownTranscriptWriter` | 分配序号、渲染 Markdown、临时文件加 rename、维护 Manifest/索引 |
| `AttachmentExporter` | 复制附件、识别 MIME、计算大小和 SHA-256、生成相对链接 |
| `RedactionPolicy` | 清理密钥、Authorization、Cookie、环境变量和用户配置的敏感字段 |
| `TranscriptSettings` | 解析开关、根目录、包含范围和保留策略 |

Recorder 写入失败应上报可见错误或 Telemetry，但默认不应让聊天任务失败。合规场景可增加 `failureMode: "warn" | "block"`，由管理员选择“归档失败是否阻止继续会话”。

## 7. VS Code 扩展的改造点

### 7.1 初始化与会话生命周期

在 `apps/vscode/src/core/task/index.ts` 的 Task 构造/`startTask()` 流程中：

1. 从 `StateManager` 获取 Transcript 设置；
2. 以 `taskId` 创建 `TranscriptRecorder`；
3. 用初始任务首行生成安全目录名；
4. 写 `session-start`；
5. 记录用户原始 task、图片和文件清单；
6. Task Resume 写 `session-resume`；
7. `AttemptCompletionHandler`、`abortTask()`、异常和 dispose 路径分别写 complete/cancel/error 并 `flush()`。

不要只在 `abortTask()` 中关闭，因为任务也可能正常完成、宿主退出或构造中失败。Recorder 的 `close()` 必须幂等，并在进程退出时做有超时的 best-effort flush。

### 7.2 用户消息与附件

接入以下入口：

```text
Task.startTask()
Task.handleWebviewAskResponse()
Task.say("user_feedback", ...)
恢复任务和继续任务的用户输入入口
ToolResultUtils.askApprovalAndPushFeedback()
```

记录顺序建议为：

```text
user-input(raw)
  → user-attachment(path/hash/copy)
  → processFilesIntoText 后的 user-input(providerVisible)
  → Hook 修改后的最终 user-input(providerVisible-final)
```

可以使用同一个 `correlationId` 关联同一轮输入的多个表示。必须在 `processFilesIntoText()` 之前复制附件，否则读取失败、截断或源文件变化后无法补救。

### 7.3 模型文本和 reasoning

在 `Task.recursivelyMakeClineRequests()` 的流式事件 switch、`StreamResponseHandler` 和最终 assistant content 构建处记录：

- `assistant-text-delta`：原始 delta、累计长度、Provider Call ID；
- `assistant-reasoning-delta`：显式 reasoning delta、redacted 标记和返回元数据；
- `assistant-message`：最终聚合后的 text/thinking/tool blocks；
- `usage`：Token、缓存、费用、Model、结束原因。

如果 `includePartialDeltas=false`，不要完全忽略流：Recorder 应在内存中聚合，然后只写最终事件。若开启 delta，最终聚合事件仍要写，便于阅读和校验；通过 `parentEventId` 或 `streamId` 关联，并用 Event ID 防止重试重复。

### 7.4 工具调用和结果

至少接入两层：

1. `apps/vscode/src/core/task/ToolExecutor.ts` 的 `handleCompleteBlock()`：记录模型请求的工具名、参数、Call ID、批准、开始、结束和模型可见结果；
2. 各数据源边界：在截断/格式化前记录真正原始结果。

重点边界如下：

| 类型 | 原始结果采集位置 |
| --- | --- |
| Terminal | `integrations/terminal/` 中收到 stdout/stderr chunk 的位置，早于 1 MB/行数限制 |
| MCP | MCP Client/Handler 收到 Tool/Resource 原始响应的位置，早于图片或文本转换 |
| Browser/Web | Browser Session、Web Fetch/Search 的响应构建位置，早于正文提取和截断 |
| 文件读取 | `extractTextFromFile()`/Handler 读取前后，同时保存原始附件副本或哈希 |
| 文件编辑 | Handler 应保存参数、Patch、批准结果、最终差异和错误；不要复制整个工作区 |
| Hook | 每个 Hook Executor 的输入、stdout、结构化结果、取消与错误 |

只在 `ToolExecutor.handleCompleteBlock()` 接入，得到的是“模型可见结果”，不能恢复更早被截断的完整 Terminal/MCP 输出。

### 7.5 Context Compaction 与回退

在 `ContextManager`、Condense/Summarize Handler 和 PreCompact Hook 中记录：

- 压缩触发原因、Token 阈值；
- 压缩前消息 ID/索引清单和可选完整快照；
- 删除范围、替换摘要和压缩后消息；
- Hook 对上下文的修改；
- Checkpoint Restore、消息删除和历史覆盖操作。

转存日志是 append-only，因此回退不应删除旧事件。应新增 `checkpoint-restored` 或 `history-rewritten` 事件，说明“从此 sequence 开始，活动会话回到哪个点”。这比修改旧 Markdown 更符合审计语义。

### 7.6 设置接入

建议配置：

```ts
interface TranscriptExportSettings {
  enabled: boolean
  rootDirectory: string
  includeReasoning: boolean
  includeToolIO: boolean
  includeAttachments: boolean
  includePartialDeltas: boolean
  includeSystemPrompt: boolean
  redactionMode: "strict" | "balanced" | "off"
  failureMode: "warn" | "block"
}
```

正式扩展需要打通：

```text
apps/vscode/src/shared/storage/state-keys.ts
apps/vscode/proto/cline/state.proto
apps/vscode/src/core/controller/state/updateSettings.ts
apps/vscode/src/core/controller/state/updateSettingsCli.ts
apps/vscode/scripts/generate-state-proto.mjs
Webview 设置页面与 Proto 转换代码
```

`rootDirectory` 应提供文件夹选择器。写入前用真实路径检查防止目录穿越；默认不要把归档目录放在当前代码工作区内，避免被 Agent 搜索、提交 Git 或再次作为上下文读取。

## 8. SDK/CLI 的改造点

### 8.1 优先订阅原生 `AgentRuntimeEvent`

最完整的接入方式是通过 `AgentConfig.hooks.onEvent` 或 `AgentRuntime` 原生 listener 把事件送入 Recorder：

```ts
const transcriptHook = {
  onEvent: async (event: AgentRuntimeEvent) => {
    await recorder.record(mapRuntimeEvent(event))
  },
}
```

原生事件已经包含：

- `message-added`；
- text/reasoning delta；
- `assistant-message`；
- tool started/updated/finished；
- usage、状态、Turn、Run 完成与失败；
- Snapshot 中的 agent、conversation、run、iteration 信息。

不要只订阅 `SessionRuntime.subscribeEvents()` 暴露的旧 `AgentEvent`：`RuntimeEventAdapter` 会丢弃 `message-added`，并把部分原生语义投影成兼容事件，无法满足全量转存。

### 8.2 在 Host 层注入 Recorder

建议由 `LocalRuntimeHost`/CLI Session Host 创建 Recorder，并把 Hook 合并进用户 Hook：

```text
LocalRuntimeHost.startSession()
  ├── 根据 sessionId/metadata.title 创建 Recorder
  ├── 合并 transcriptHook 与 bootstrap.hooks
  ├── 传入 SessionRuntime / AgentRuntime
  └── 成功、失败、取消时 flush/close
```

不能让用户配置的 `onEvent` 覆盖 Recorder Hook。应像 `mergeRuntimeHooks()` 一样组成 Hook 数组，并明确调用顺序：Recorder 记录原始事件，用户 Hook 执行，若 Hook 改写输入或结果，再记录修改后的事件。

### 8.3 用户原始输入和附件

`LocalRuntimeHost.prepareTurnInput()` 会规范化文本、展开 Mention、解析绝对文件路径，随后 `agent.run()`/`continue()` 构建消息。应分别记录：

1. `send()`/Start 输入中的原始 `prompt`、`userImages`、`userFiles`；
2. `prepareTurnInput()` 生成的规范化/展开后提示；
3. 文件加载器真正读到的文本；
4. `message-added` 形成的最终 AgentMessage。

Queued/Steer 输入要在入队和真正消费时各写一个事件，并用 Queue Entry ID 关联，避免误以为“入队”就等于“已被模型处理”。

### 8.4 压缩前快照

`AgentRuntime.prepareModelRequest()` 接受 `prepareTurn` 返回的新 messages 后，会替换 `this.state.messages`。Recorder 必须在以下位置记录：

```text
prepareTurn 调用前：compaction-before（原始消息 ID/可选正文）
prepareTurn 返回后：compaction-after（替换消息、摘要、策略）
this.state.messages = preparedMessages 之前：确保 before 事件已落入队列
```

可在 `session-runtime-orchestrator.ts` 的 `createRuntimePrepareTurn()` 包装 Host 的 Compaction Callback，避免侵入 Context Compaction 算法本身。

### 8.5 Subagent 与 Agent Team

每条事件必须带：

```text
sessionId
agentId
parentAgentId
conversationId
runId
iteration
```

建议同一根会话共享 `TranscriptSessionCoordinator`：

- 一个 Session Lock；
- 一个持久化 `nextSequence`；
- 各 Agent 独立的流聚合缓存；
- Tool Call ID 和 Agent ID 组成复合关联键；
- 子 Agent 结束时只 flush 自身队列，不关闭根会话 Writer；
- 根会话完成且所有子 Agent 都结束后才写最终索引。

如果每个子 Agent 单独建立目录，则根目录 `README.md` 必须列出子目录和父子关系；审计和阅读体验通常不如共享有序事件目录。

## 9. 附件如何处理

二进制文件无法真正“转换成可读 Markdown”。推荐策略是：

```text
attachments/ 保存原始字节
Markdown 保存元数据、哈希和相对链接
```

示例：

```markdown
# 用户附件

- 原始名称：`设计稿.png`
- MIME：`image/png`
- 大小：`248193 bytes`
- SHA-256：`f96...`
- 原始路径：已按脱敏策略隐藏
- 归档文件：[000012-design.png](attachments/000012-design.png)
- 模型可见表示：Base64 image block
```

复制时要求：

- 使用流式复制并限制最大体积；
- 先写临时文件，再 rename；
- 计算 SHA-256，重复内容可去重；
- 文件名只使用安全 basename，不接受用户路径直接拼接；
- 符号链接按策略拒绝或解析后重新校验允许范围；
- 记录复制失败、权限错误和已截断标志。

如果业务强制“目录下只能出现 `.md`”，可以把二进制 Base64 写入 `attachment-xxxx.md`，但体积约增加三分之一、难以预览、Git 和编辑器性能差，也更容易泄露敏感文件。推荐把“事件记录必须是 Markdown”和“附件保持原始格式”分开定义。

## 10. 安全与脱敏

Transcript 比普通聊天历史更完整，风险也更高。默认至少处理：

- `Authorization`、`Proxy-Authorization`、Cookie；
- `apiKey`、`token`、`secret`、`password`、私钥；
- Provider 配置和环境变量中的凭证；
- URL Query 中的签名、Token；
- 命令输出中命中的用户自定义敏感正则；
- 用户配置的禁止导出路径；
- System Prompt 中的企业机密规则。

建议 Redaction 顺序：

```text
结构化字段名过滤
  → 已知 Credential 值精确替换
  → Header/URL 规则
  → 用户正则
  → 路径匿名化
  → 写入 Markdown
```

不要记录 API Key、Authorization Header 或完整 Credential Store。`includeSystemPrompt` 和 `includeReasoning` 默认应关闭或由企业策略管理；开启时在 UI 明确提示潜在敏感信息。

## 11. 一致性、并发和性能

### 11.1 写入协议

单会话 Writer 应执行：

```text
record(event)
  → 内存有界队列
  → 获取 Session Lock
  → 读取/分配 nextSequence
  → 渲染并脱敏
  → 写 <filename>.tmp
  → fsync（严格模式可选）
  → rename 为 .md
  → 原子更新 sequence state
  → 释放锁
```

`eventId` 必须在采集点生成。若重试写入相同 `eventId`，Writer 返回已有 sequence，不能再生成重复事件。

### 11.2 Delta 采样与背压

逐 Token 写一个文件会产生大量小文件。建议：

- 在 50～200 ms 时间窗内合并同一 Stream 的 delta；
- 保留首尾时间和 chunk 数；
- 单独写最终聚合消息；
- 队列满时优先合并 delta，不能静默丢弃 user、final message、tool call/result 和 error；
- 记录 `dropped_or_coalesced_delta_count`；
- 大 Tool Result 采用流式附件/文本分片，不阻塞模型主循环。

### 11.3 崩溃恢复

启动时扫描：

- 删除或隔离未完成的 `.tmp`；
- 从现有最大 sequence 和状态文件恢复下一个序号；
- 校验重复 Event ID；
- 将未正常关闭的会话标记为 `interrupted`；
- 不自动覆盖已存在的合法 Markdown。

## 12. 历史会话回填

除了实时记录，还应提供一次性导出器：

### 12.1 VS Code 历史回填

输入：

```text
ui_messages.json
api_conversation_history.json
context_history.json
task_metadata.json
HistoryItem
```

流程：

1. 枚举 `{globalStorage}/tasks/*`；
2. 以 Task ID 建立目标目录；
3. API History 作为模型语义主线，UI History 补充显示、批准和状态；
4. 用 `conversationHistoryIndex` 关联两条历史；
5. 记录 Context 删除范围和改写；
6. 文件路径仍存在时可选择复制，但必须标注“回填时版本”，不能冒充“会话时原件”；
7. 输出 `source: backfill-vscode` 和缺失清单。

### 12.2 SDK/CLI 历史回填

输入：

```text
sessions.db
<sessionId>.json
<sessionId>.messages.json
子 Agent / Team 消息工件
```

流程：

1. 从 SQLite 读取标题、状态和父子关系；
2. 使用 `messages_path`，不要猜测固定路径；
3. 解析 v1 并容忍未知字段；
4. 用 Tool Use ID 配对 Tool Result；
5. 合并 Subagent/Team 工件；
6. 以消息 ID 和时间戳生成稳定 Event ID；
7. 标注 `source: backfill-sdk`。

历史回填无法恢复：

- 流式 delta；
- UI partial 的所有版本；
- 截断前的工具输出；
- 原始附件字节；
- SDK 压缩前已被覆盖的消息；
- Provider 未返回的隐式思考。

必须把这些限制写入 `manifest.md`，不能把回填结果标成“全量原始记录”。

## 13. 测试方案

### 13.1 单元测试

- 安全目录名、同名会话和超长标题；
- Front Matter 转义、反引号围栏、Unicode 和超大正文；
- Event ID 去重、序号恢复和并发分配；
- 临时文件、rename 失败和磁盘满；
- Credential、Header、URL 和用户正则脱敏；
- 附件哈希、重复附件、符号链接和越界路径；
- unknown event/content block 的无损降级；
- Delta 合并与最终消息一致性。

### 13.2 集成测试

至少构造以下会话：

1. 纯文本问答；
2. 图片、PDF、Office 和文本附件；
3. Terminal 大于 1 MB、超过 500 行的输出；
4. MCP 文本、图片、错误和二进制资源；
5. reasoning、redacted thinking 和普通非 reasoning 模型；
6. Tool 批准、拒绝、用户补充反馈；
7. Hook 修改、取消和失败；
8. Context Compaction、Checkpoint Restore 和删除消息；
9. Provider 重试、流中断、用户取消和进程异常退出；
10. Subagent/Team 并发工具调用。

逐项比较：运行时实际事件、现有 JSON 存储、Markdown 事件及附件哈希，确认“原始值、显示值、模型可见值”没有混淆。

### 13.3 安全测试

- 在 Prompt、工具参数、stdout、MCP 响应和系统提示词中放入测试 Secret；
- 归档目录执行全量搜索，确认默认模式下 Secret 不存在；
- 检查文件权限，Unix 下目录建议 `0700`、文件建议 `0600`；
- 确认归档根目录不会被自动加入模型上下文或代码仓库。

## 14. 推荐实施顺序

### 第一阶段：建立可靠的 Markdown Writer

1. 定义 `TranscriptEvent v1`；
2. 实现安全目录、序号、Event ID、原子写入和 Manifest；
3. 实现脱敏和附件复制；
4. 完成崩溃恢复与并发测试。

### 第二阶段：接入最终语义事件

1. 用户最终输入；
2. Assistant 最终消息；
3. Tool Use 与模型可见 Tool Result；
4. 会话完成、失败、取消和用量；
5. VS Code 与 SDK 各完成一条端到端链路。

### 第三阶段：补齐全量过程

1. text/reasoning delta；
2. Terminal/MCP/Browser 原始 I/O；
3. Hook；
4. Compaction 前快照和 Checkpoint；
5. Subagent/Team 并发序列。

### 第四阶段：历史回填和产品化

1. VS Code 历史导出命令；
2. CLI `cline transcript export <sessionId>`；
3. 设置页面、目录选择器和状态提示；
4. 企业策略、保留期限和自动清理；
5. Schema 版本迁移说明。

## 15. 验收标准

完成改造后，至少应满足：

- 每个会话有唯一、稳定且可读的目录；
- 所有事件正文均为 Markdown，附件通过相对链接和哈希关联；
- 用户输入、显式 reasoning、模型输出、工具调用/结果可以按 sequence 完整排序；
- Delta 和最终聚合消息可关联且不会重复计算；
- Tool Call 与 Tool Result 可通过 ID 配对；
- 发生截断时明确记录原始大小、保留大小和原因；
- 压缩、回退不会删除旧事件，只追加状态变化；
- 多 Agent 并发不会产生重复序号或覆盖文件；
- 崩溃后可继续写入；
- 默认归档中不存在 API Key、Authorization 和已配置 Secret；
- Recorder 故障策略符合设置，不会无提示丢记录；
- Manifest 明确说明不可获得的隐式 Chain of Thought。
